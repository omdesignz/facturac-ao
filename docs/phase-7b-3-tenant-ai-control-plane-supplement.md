## 1. Authority, inspected evidence and decisions

Governing documents are the [7B architecture](phase-7b-multi-provider-ai-gateway-contract.md), [7B.1 report](phase-7b-1-gateway-implementation-report.md) and its evidence, [7B.2 report](phase-7b-2-anthropic-gateway-migration-report.md) and its evidence, [Phase 7 security contract](phase-7-live-inference-security-contract.md), [provider/privacy decision](phase-7-provider-privacy-decision.md) and [activation decision](phase-7-production-activation-decision.md). No governing document is amended. The accepted independent reviews supplied in this conversation are acceptance context; implementation reports alone are not proof.

Repository inspection establishes these constraints:

- `AssistantProviderLedger::reserve()` currently locks the budget control, then windows in **deployment_month, deployment_day, workspace_month, workspace_day, user_day** order. `finalize()` takes the same locks, then the attempt. Recovery uses that finalizer. The five metadata tables and their integrity triggers are defined in `2026_10_08_183139_create_assistant_provider_metadata_tables.php`.
- Attempts already preserve A1 actor snapshots, workspace/entity binding, unique interaction, exact **552,816 micro-USD** reservation, immutable admission and terminal outcomes. Windows are monotonic. These are not disposable telemetry.
- Workspace public identifiers are ULIDs; internal workspace/entity/user keys are big integers. `users.attribution_id` is a globally unique immutable UUID. Creator snapshots must copy that identifier, not a name or sequential ID.
- `AgtConnection` uses automatic encrypted casts. That existing convention is **not** the customer AI secret boundary. Do not change AGT storage.
- `IntegrationManagementContext` permits owner **or administrator** and has work-session/MFA/reauthentication checks. Its role predicate cannot be reused unchanged: AI configuration is **owner only**.
- `RequiredAudit::record()` rejects deferred/missing activity persistence. `activitylog.default_except_attributes` is an exclusion list, not sufficient protection for new ciphertext fields. `bootstrap/app.php` currently adds only `basic_auth_password` to the inspected custom `dontFlash` rule. New credential inputs need their own protection before any submission path exists.
- `DeleteUserAccount` has integration/fiscal retention checks but no new AI control-plane retention check. Add that narrow check before storing credentials; do not let its preview promise deletion that a new restrictive FK will reject.
- No direct Telescope/Nightwatch dependency appears in `composer.json`; production proxy/APM capture cannot be established from that absence. Installed Laravel 13 / AI SDK 0.11.2 remain unchanged. The SDK owns protocol integration; it is not the secret store or authorization engine.

**Answers to the six decision questions:**

1. Customer credentials can preserve the boundary, provided storage does not confer execution authority and every send retains the complete policy/permission/accounting intersection below.
2. Subdivide into **7B.3a storage**, **7B.3b lifecycle**, **7B.3c policy/accounting resolution**. Each requires independent review. Administration routes/UI remain **7B.7**, not a new 7B.3d shortcut.
3. Initially use dedicated envelope encryption with a protected versioned KEK file backend. No APP_KEY-only casts; external KMS integration is a separate operational review.
4. Generalized transactions use root deployment control → sorted control/account rows → settings → connections → credential versions → approvals → windows → attempt. Section 7 specifies ordering and coexistence precisely.
5. A revoke/disable committed before the final send prerequisite check prevents transmission. After that check, bytes may already be sent; authority loss prevents subsequent tools/disclosure. Retain reservation and finalize/recover without resend or refund.
6. Yes: configuration is inert state. It neither verifies the key nor approves the provider/account/model nor enables production. Defaults and deployment egress remain disabled.

## 2. Implementation boundary and schema notation

The following is an **equivalent migration specification**, not executable migrations. Every listed column has explicit type, nullability and default. `!` means NOT NULL; `?` means nullable with default NULL. Unless specified, a NOT NULL column has **no database default** and must be supplied explicitly. All dates are `timestamptz`, UTC. All revisions are positive `bigint`; increment with checked arithmetic. UUIDs are random canonical v4, including copied A1 values. IDs are never secrets. External metadata uses public IDs, not internal big integers.

All FKs use **ON UPDATE RESTRICT / ON DELETE RESTRICT**, except the optional current creator relationship, which uses ON DELETE SET NULL. Index every referencing FK tuple unless a stated PK/unique/index already provides its left prefix. No cascade deletion, soft-delete authorization shortcut, or polymorphic owner string. All identity columns and creation times below are immutable; operational timestamps are monotonic. Ordinary application DB credentials cannot disable triggers. DBA/root compromise is outside the integrity guarantee.

The concrete minimum for **3a** is five new tables: materialized profiles, gateway controls, settings, stable connections and credential versions. A stable connection row is justified: a version collection without a parent cannot enforce immutable ownership or serialize rotations. Versions do not each create new payer identities. Existing budget controls are referenced, never provisioned automatically. No changes to the five legacy accounting tables occur in 3a/3b.

The prospective ledger/approval extensions in section 6 belong to 3c. Its detailed migration diff and populated-data rehearsal must receive independent review **before execution**; this is an implementation acceptance gate, not permission for Sol to invent different accounting. Future endpoint approval persistence is expressly deferred to 7B.5 by this task. No endpoint URL or unvalidated endpoint UUID is stored now.

Mandatory checks/triggers:

- Initial insert is pending/unverified with complete envelope, no test/use/terminal timestamps. Secrets 1..512 ASCII non-control bytes in service; encrypted text each 1..8192 ASCII bytes in DB. Exact envelope parser has independent size/schema limits.
- Ciphertext/wrapped DEK/KEK version are all present iff secret_destroyed_at IS NULL. When destroyed, all three NULL, terminal state required. Destruction is irreversible. KEK version matches `[A-Za-z0-9_-]{1,80}`. No plaintext preview, suffix, hash or fingerprint column.

- Identity, creator snapshot, secret ciphertext and encryption_schema immutable until permitted destruction. A KEK rewrap changes only wrapped_dek/kek_version/wrap_revision (old+1); never secret ciphertext or credential identity. Rewrap forbidden after destruction. Service verifies both envelopes before committing rewrap; audit required.
- Verification updates require a matching finalized, successful probe of this exact version/profile/revision in 3c. 3a has no production writer for verification/activation; tests must not supply an application “verified=true” bypass. Last-used only increases when transmission was attempted; it is not proof of receipt.
- Selected-version consistency is checked on settings **and credential** changes with a DEFERRABLE INITIALLY DEFERRED PG constraint trigger, so rotation can retire old then activate new then switch settings in one transaction. SQLite must use equivalent service sequencing plus explicit triggers/checks where supported; it is not evidence for deferred PG semantics. Direct SQL with a dangling selected terminal version must fail at commit.

These triggers enforce data integrity, not application identity or production authorization. A stored active row alone is never a send permit.

**PA1 stage restriction:** The preceding full state machine remains the eventual contract. In 3b, only pending/unverified creation, pending→revoked and the explicitly bounded maintenance in section 5.1 may execute. `active`, `replaced`, verification `failed`/`verified`, and all probe/use metadata remain unreachable through new lifecycle operations. The accepted initial-insert guard, active CHECK and `no_probe` predicate stay byte-identical. No new pre-active state is needed: `pending` already means stored without verification or execution authority.

## 4. Encryption and disclosure decision

| Option                      | Decision and threat/operations assessment                                                                                                                                                                                                                                                                                                                                                                  |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| APP_KEY encrypted casts     | Rejected here. A DB-only thief lacks the key, but APP_KEY compromise exposes all such secrets; implicit hydration/serialization and coupled application-key rotation widen risk. Existing AGT usage is not precedent to copy.                                                                                                                                                                              |
| Dedicated envelope KEK      | **Initial choice already required by signed section 8.** Fresh 32-byte DEK/version; AES-256-GCM encrypts bounded scalar JSON; dedicated versioned KEK wraps DEK plus binding. DB/backups alone reveal no plaintext. APP_KEY alone is insufficient. Rewrap independently of secret rotation. An application worker compromise that can access KEK still exposes usable secrets; do not claim HSM isolation. |
| External KMS/secret manager | Stronger key access separation/audit and managed recovery, but new IAM/network/availability/portability responsibilities. Later reviewed backend may wrap DEKs; no dependency, fallback vault or external lookup introduced now.                                                                                                                                                                           |

Use installed Laravel Encrypter explicitly configured AES-256-GCM with supplied DEK/KEK, string encryption without PHP serialization. Independently generated nonces and authenticated tags come from the crypto implementation, not hand-rolled crypto. Both authenticated plaintext envelopes contain exact schema, deployment UUID, workspace public ULID, connection UUID, version UUID, provider/family and fixed endpoint policy identity. Compare to independently resolved expected context after unwrap and decrypt; do not trust context copied from the ciphertext itself. A whole envelope-pair swap between versions/tenants/deployments must fail. Envelope stores no mutable mode/revision/payer so approved rewrap/selection changes do not require secret re-encryption; payer/account verification remains separately mandatory.

KEK resolver accepts only a deployment-owned allowlisted version→absolute-file mapping outside DB/webroot. Apply existing secret-reader regular-file/no-symlink/permission/inode-before-after rules to KEKs and verify protected parent directories. Exact 32-byte key material, no ambient APP_KEY fallback, no user-controlled path, no key content in exceptions. Missing/unknown/retired key denies. Use inert test keys only during implementation. Production needs named custody, protected backup, restore drill, key rotation and incident procedure before real customer import. Back up wrapped data and KEKs through separate access-controlled processes; retaining either alone is not recovery. A restored DB starts disabled until current revocations/liability reconcile.

Raw credentials are accepted only by a narrow sensitive-input object/repository method, encrypted before database write, never retained in model attributes/DTOs/session. Maximum 512 ASCII bytes, no CR/LF/control; adapter validation can narrow further. Generic persistence does not encode Anthropic prefixes. Reject known VAP key reuse inside the restricted secret boundary without logging comparisons; do not promise exhaustive detection or account ownership from string format.

No secret read-back even once. Metadata resource allowlist: connection/version opaque IDs, fixed configured/verification/state flags and approved timestamps. No suffix/fingerprint. `$hidden` must include ciphertext/wrapped DEK/KEK metadata as defense in depth; no `encrypted` casts or decrypting accessors, automatic model activity logging, event payloads containing rows, queue serialization or `toArray()` returns. Mark sensitive parameters and make secret-bearing objects nonserializable/non-debuggable. Explicitly scrub input from validation old-input, exception/report context, HTTP client traces, SDK events, SQL query listeners, proxy/APM/debug tooling. Hashing the submitted secret does not solve outbound authentication and is not a substitute for encryption.

## 5. Authority and lifecycle

Configuration requires explicit workspace argument, authenticated web actor, primary fresh active **owner** membership, verified email, confirmed MFA, valid work session, CSRF and recent reauthentication ≤300 seconds. No browser current-workspace fallback, administrator substitution, integration bearer token, impersonation, support delegation, queue actor or CLI provisioning. Emergency disable/revoke still needs fresh owner/MFA/work session but not recent password confirmation, commercial approval or provider availability. Platform operations have no new administration interface in this stage; reviewed deployment provisioning is distinct from tenant ownership.

Storage, verification, promotion and execution are different permissions. Save only creates pending encrypted candidate. Verification uses a separate probe permit and fixed synthetic payload, never automatic on save. One active probe/connection, one/minute/connection, five/hour/workspace, plus shared budgets; no local tools or arbitrary prompt. No real probe occurs in this implementation series without separate authorization. Tests substitute the transport only in test processes and exercise the real permit/serialization boundaries.

Promotion requires successful exact-version/profile probe, still-current approval/account evidence, owner freshness and expected settings/connection revisions. Under locks, retire old active version (replaced + locally revoked), promote candidate, update selected version and revisions, audit and commit. A bad candidate leaves previous active version/selection unchanged. Two rotations from one revision cannot both win. Existing active authentication failure circuits that connection/account as appropriate; it does not silently pick another key or reclassify an unverified candidate. Temporary probe failure does not revoke the old version. Revocation clears any selection and disables affected policy before commit. Replaced/revoked keys are not fallback candidates.

Immutable copied A1 creator identity survives rename, deactivation, membership removal and user deletion. Nullable creator_user_id is only a current relationship. ## 8. Races, execution and failure semantics

Resolve one immutable tuple: actor A1/workspace/entity/production/deployment, permissions ceiling, settings revision, provider/profile/manifest, ownership/account, credential version or protected VAP reference, approvals/disclosure/entitlement. Capture once, revalidate; never silently re-resolve or fall back.

| Race                             | Required outcome                                                                                                                                                                                                                      |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Admission vs revoke/disable      | Root orders commits. Change first: deny admission. Admission first: reservation survives; final send prerequisite recheck denies if change has committed.                                                                             |
| Revoke after final send check    | In-flight bytes cannot be recalled. Do not send again; recheck after response, before every local tool and before final disclosure. Changed authority discards buffered results; finalize usage or unknown with reservation retained. |
| Rotation/mode/profile switch     | Exact version/revision mismatch denies old permit. Never combine old body/account reservation with new key or reinterpret VAP as customer. Already sent attempts finalize original immutable allocations.                             |
| Two rotations                    | Both may prepare ciphertext; one pending insert/CAS/promotion wins. Loser is safe conflict, no partially retired key, no lost old selection, no plaintext in error.                                                                   |
| Candidate fails verification     | Keep candidate failed/pending and old active selection unchanged; no inferred provider approval.                                                                                                                                      |
| Cap/entitlement decrease         | Fresh limits/revisions can deny before send; consumed totals never decrease. Increase requires independent upper policy and does not erase consumption.                                                                               |

| Rollback/audit failure           | No partial configuration/promotion/reservation. A failed terminal audit prevents tools/disclosure; attempted liability remains and recovery handles unknown without resend.                                                           |
| Rewrap vs rotation/revoke        | Same locks/CAS; rewrap preserves identity/selection/budgets, cannot resurrect destroyed/terminal secret or overwrite a later wrap revision.                                                                                           |

Add a narrow reviewed production consumer using the **same** AES-GCM format, KEK rules and parser constraints. Do not redesign crypto or add APP_KEY fallback. Sensitive arguments, captures and return containers remain nondumpable/nonserializable. Transport owns the plaintext/header lifetime; release in `finally` on every result. PHP does not guarantee memory zeroization, so promise bounded retention and absence from application persistence, not erased process memory.

**Three distinct objects are required:**

1. `VerificationRequestPermit`: private, one-use decrypt/send authority for an admitted attempt and exact request/fiber. It authorizes one metadata GET, never promotion or inference.
2. `CredentialVerificationEvidence`: a fixed typed observation with no methods that execute requests. The verifier derives it only from the admitted pinned exchange and strict parser. Success/failure is not accepted from lifecycle code.
3. `CredentialPromotionPermit`: opaque request-local authority owned by that verifier session. Consuming it requires both the finalized successful receipt and all current locks/rechecks; it cannot be recreated from persistent evidence.

The concrete issuer boundary must be inspectable: a final verifier session owns a **private in-memory identity registry** of its issued opaque handles. Only its private successful-exchange path can register promotion authority. A public entry may perform the complete authorized verification operation, but no public factory accepts an outcome, row, DTO, UUID, signature, arbitrary transport or `verified=true`. Lifecycle validation asks that same session to consume its registered identity, checking the exact context object, request, process PID, fiber and operation. A correctly shaped unregistered handle fails. Registry entries are removed on claim even if promotion rolls back. No singleton/static registry or container binding that accepts a caller-selected issuer. Private construction plus an unrestricted public factory is explicitly insufficient.

Durability also needs authenticated provenance: add a **domain-separated HMAC-SHA-256 receipt** to the existing finalized attempt (no permit/evidence table, JWT or bearer token). A dedicated 32-byte verifier receipt key lives in the same class of protected canonical private-file custody as KEKs, but is a **different key, file and allowlist** from KEK, APP_KEY and VAP credential. Missing/retired/unknown trust key denies. The signer is private to the verifier, accepts only its validated in-memory observation, and has no generic public `sign(array)` entry point. Verification uses `hash_equals`; DB contents never select a filesystem path or algorithm. Root configuration defines deployment, policy digest, trusted key IDs and validity; key IDs are bounded metadata. An application process with access to this key can forge receipts: arbitrary application-code/host compromise is outside this boundary, while a DB-only writer cannot.

Canonical receipt input is a fixed-order, versioned JSON **array** with exact types, UTC microsecond strings, canonical identifiers, decimal strings for bigint values and explicit nulls. No floats, unordered maps, optional omission or executable serialization. Prefix bytes are `facturac:tenant-ai:verification:v1\n`. Hash includes all of:

- schema/issuer-policy version, evidence UUID/attempt UUID, deployment, provenance realm, workspace public ID, legal-entity public ID and production environment;
- connection UUID, credential UUID/version number, immutable credential creation timestamp and current wrap revision; no key/ciphertext digest or fingerprint;
- expected settings/connection revisions, prior selected version or null, expected prior active generation and proposed activated generation;
- actor A1 and original membership identity, exact customer profile ID/digest, provider/family, endpoint-policy ID and verifier-manifest digest;
- sorted control/budget/approval IDs and revisions, owner grant/account-mapping digest, disclosure ID, acknowledgement ID, selection/entitlement revision;
- typed observed organization/workspace IDs and claim strength, exact returned model ID, fixed `provider_authenticated_model_visible` outcome;
- admitted/send-authorized/observed/finalized times, promotion expiry, final promotion disposition, committed activated generation (null unless promoted) and signer key ID.

The allowlist is closed and bounded (at most 16 control/budget/approval references; serialized receipt input at most 8 KiB). Public metadata uses A1/public IDs; the original membership identifier remains internal evidence only. The provider observation does not include model description, capabilities tree, name, raw payload, request ID, arbitrary headers or error text.

Promotion authority expires at the earlier of **5 seconds after observation**, the **10-second operation deadline**, credential/profile/approval expiry, or any relevant authority change. Check monotonic time in memory and primary database time for persisted expiry; require both. It cannot move to another request/process/fiber or survive a crash, including a fork that copies PHP memory. Persisted expiry limits promotion, not the historical truth of a committed observation. An active receipt remains historical evidence after those five seconds; every later use still needs current policy/expiry/generation and fresh inference authority. No automatic periodic inference or silent re-verification is introduced.

At future consumption, verify the receipt MAC and stable credential/provider/profile/account tuple plus its committed activated generation, not just `state=active`. Historical admission revisions are proof of the promotion's preconditions; do **not** require them to equal today's connection revision forever, since storing a later pending candidate must not invalidate an otherwise legitimate old active credential. Today's revisions are captured anew in each invocation permit. A malformed/forged/unknown-key receipt, or an authentic receipt whose signed disposition is not promoted, makes the row unusable regardless of DB flags. An old valid receipt cannot activate another version, another connection or a later generation.

Use new additive migrations; accepted migrations and `TenantAiSchema` stay historical and byte-identical. Do not remove constraints in tests or edit historical guard code to make active fixtures possible. Proposed changes, under the section 6 concrete-DDL checkpoint:

The `no_probe` successor is **`verification_authority_v1`**, not absence of a guard. Pending inserts remain unverified, no test/use/activation fields. The initial guard continues to reject active insertions. A pending→active update must reference a finalized successful `gateway_v1/connection_probe` attempt, exact admitted candidate tuple, authenticated receipt fields and `promotion_disposition=promoted` in the same committing transaction. Require `last_verified_at=observed_at`, `last_tested_at=observed_at`, outcome success, exact profile/operation and assigned generation equal to the connection's new generation. The deferred selected-version trigger must still hold at commit; selecting a forged active row additionally requires the application MAC/authority check.

Database constraints validate structure, binding, chronology, unique use and state transitions. **They do not claim to verify the HMAC or prove provider contact.** The verifier's private live issuer and the receipt authenticator are mandatory application protections. Handwritten SQL that supplies superficially coherent evidence must never cause an application promotion or usable credential; adversarial tests must exercise that distinction instead of claiming SQL shapes are authentication.

Only finalized current-candidate failure, matched through `last_test_operation_id` to the same version/context/profile/outcome/time, may update failure/test metadata: a definitive authenticated rejection can set pending/failed; unavailable/timeout/policy/malformed/unknown does not assert invalidity. If a candidate already had a definitive failed observation, a later transient failure must not turn it into verified; retain its prior verification state. Successful observation and promotion happen through the prescribed sequence, never through a save/update method. Stale observations only finalize their attempt; they cannot write test fields on a replaced/revoked candidate. `last_used_at` remains forbidden in 3c-1: verification updates test timestamps only. A future 3c-2 successor must tie use to its own admitted/transmission-marked inference attempt.

For `gateway_v1/connection_probe`, separate authentication from accounting explicitly: `verification_outcome` is `not_observed` on admission and one fixed outcome from 13.9 or `provider_authenticated_model_visible` at finalization. A successful metadata observation uses existing attempt state `usage_unknown`, with token/money actuals NULL, because no billing usage was reported; it can nevertheless carry successful verification and a promoted disposition. Never require accounting state `received` as a substitute for verification success. Pre-send refusal may finalize `failed`; recovery uses `usage_unknown` and `abandoned`. The successor guard tests the typed verification outcome, receipt and disposition, not the accounting state alone. Map credential `last_test_outcome` only to its existing vocabulary: success, auth_failed (401), protocol_failed (malformed/model/account mismatch), unavailable (transient provider failure), or unknown (timeout/local failure). Stale targets receive no credential metadata update. Attempt admission fields and receipt are immutable once finalized. Promotion disposition is `not_applicable` for failure, or one of `promoted`, `rejected_stale`, `rejected_policy`, `expired`, `abandoned` for success. The successful finalization transaction records the final disposition; a receipt cannot be later “approved” by updating the row. The only exceptional path is recovery of an **unfinalized admitted** attempt to unknown/abandoned, never received/verified/promoted. Terminal outcomes cannot be overwritten by a delayed worker.

No active/verified backfill. Pre-existing rows must satisfy the accepted below-active guards; any violation stops migration, never reconstructs verification from a selected UUID. New defaults preserve disabled state and generation zero. Payer assignment is still only NULL→a reviewed matching customer account budget, once, then immutable; no VAP account substitution. No real profile, account grant, credential, approval, acknowledgement or activation is provisioned by migration.

### 13.7 Admission, budget and transaction protocol

Use section 6's **single ledger and immutable allocations**. Do not create a verification usage/billing ledger beside it. 3c-1 owns the necessary gateway-v1 customer `connection_probe` branch, exact account/disclosure approvals, allocation guards, monotonic shared usage reconciliation, root fencing for mixed legacy writers and metadata-only recovery. The inference admission consumer remains absent until 3c-2.

VC1 changes the probe's operation, **not** the signed conservative reservation rule. Each admitted metadata check consumes one shared attempt and the selected profile's full conservative reserved output units and strictly positive monetary reservation in the same shared/customer account ceilings. For the unchanged numeric envelope that reservation is **552,816 micro-USD**. These are local safety reservations, not a claim that this GET generated tokens or cost that amount. No refund on failure, unsent, timeout, cancellation or successful metadata response. No price/usage is invented from the model metadata body. Actual token/money fields remain NULL, accounting outcome unknown/not-reported under an explicitly versioned verification branch, and unknown-usage counters advance once. `request_bytes=0` means no body for this GET; the gateway-v1 verification branch alone permits it and null estimated tokens. Legacy inference bounds remain equivalent, including explicit non-null requirements if shared columns become nullable for the verification branch. SQL UNKNOWN must not make a nullable legacy CHECK pass. This narrow branch avoids bogus token estimates or fabricated zero-price evidence. A separately approved provider request-cost ceiling remains necessary before real verification egress; this design does not assert that the Models API is free.

Local additional hard limits: at most **one admitted unfinished verification per connection**, **one admission in the trailing 60 seconds per connection**, **five in the trailing 3,600 seconds per workspace**, and **five per actor A1 across workspaces in the trailing 3,600 seconds**. Count all admitted outcomes, including unsent/unknown, on primary under root, using indexed `(connection_id, admitted_at, id)`, `(workspace_id, purpose, admitted_at, id)` and `(actor_attribution_id, purpose, admitted_at, id)` with bounded limit probes. Query at most the limit needed to deny; do not scan unbounded histories. Per-credential usage is bounded by its stable parent; replacement, new connection, actor switch or mode switch cannot reset workspace/shared ceilings. Quota timestamps use database UTC; no IP-only identity. No local retries. A 429/unavailable result requires a fresh owner action after the ordinary cooldown; provider Retry-After text never controls a sleep or grants authority.

The transaction sequence is normative:

1. **Preflight/admit:** authorize context; discover IDs without locks; acquire canonical root → provider/model controls → budget IDs → settings → connection → credentials in UUID order → approvals/acknowledgements → windows → attempt/allocations → audit. Reload all bindings, exact expected revisions/pending ID and current active identity/generation. Require settings already in approved customer mode, selected matching connection/profile, connection enabled/not revoked, valid customer grant and verification approval. Null selected credential is allowed for first activation. Disabled settings/connection deny, even if encrypted candidates exist. Atomically reserve quotas and commit `verification_attempted`. No decrypt or network before commit.
2. **Prepare/send:** obtain the purpose-specific protected handle; release all DB locks. Load/decrypt only this version inside the restricted transport scope. After DNS/TLS and immediately before request bytes, cURL prerequisite performs a short canonical-order transaction, repeats authority/generation/approval checks and marks `send_authorized_at` plus required audit. Commit, then send once. A lifecycle change committed first denies; a change committed after this point cannot recall the authorized request. The key is never exchanged for a newly selected one. No broad lock spans the remote exchange.
3. **Observe:** strict parse and exact account/model match. Keep only typed observation in memory; discard raw response. This step cannot write credential state or issue a freely reusable permit.
4. **Finalize/promote:** consume verifier-owned authority once, acquire the canonical locks again, validate all captured revisions, original owner/membership, settings/mode, connection, pending candidate, current active identity/generation, profile, account, approvals and deadline. Validate reservation/attempt not terminal. Generate the signed receipt only from the trusted observation. Finalize success and promotion disposition, atomically perform allowed active transition and commit required metadata audit. The promotion capability is issued after successful observation; lifecycle consumption is conditional on this same transaction finalizing the matching successful evidence. There is no earlier durable receipt that another process can redeem.
5. **Failure/stale:** finalize a fixed outcome and audit without touching a newer candidate or old active authority. If promotion fails stale/local policy, persist successful remote observation with rejected disposition, never verified on the credential. If DB/audit commit fails, roll everything back; return fixed unavailable, consume the in-memory authority anyway and retain admitted liability for recovery. Do not automatically retry the transaction or reissue the request.

At 10 seconds the worker loses all send/promotion authority. Recovery after **30 seconds** may finalize an admitted attempt to unknown/abandoned under the same locks, without decrypt/send/receipt issuance. It never refunds or promotes from persisted evidence. A stalled old worker cannot commit after recovery. Idempotency of finalization means the same terminal outcome is no-change; divergent replay fails. All deadlines and attempt counters survive browser disconnects and credential replacement.

### 13.8 Active lifecycle and races

Add a separate internal active-aware lifecycle service; preserve accepted `TenantAiLifecycle` below-active behavior and its tests unchanged. Reuse accepted seal/insert/context/KEK/audit primitives, not a second secret format. The new service is the only eventual path for candidate allocation in a connection with active/replaced history, active revoke/disable and promotion. It must preserve 3b's owner/CAS/terminal-destruction semantics. No routes, UI, command or background enablement is introduced. Workspace disable may reuse the already safe selection-clearing operation; never make emergency authority able to verify/enable/decrypt.

During rotation, lock both candidate and old active **in UUID order**. Verify the old active's authentic receipt and current activated generation; unknown/forged active history denies promotion and enters operator reconciliation, while authorized emergency revocation still works without decrypt or a valid receipt. With the same expected selection/generation, retire old A (`replaced_at`, `revoked_at`, terminal state), destroy its three envelope fields immediately, promote B, set activated generation to old generation+1, update connection generation/revision and settings selected version/revision once, and commit all audits. Deferred constraints allow intermediate SQL ordering but reject inconsistent commit. Retiring A and promoting B can never commit separately. Failed verification of B leaves A's state, envelope, activated generation and selection unchanged; writing current B failure metadata may advance connection revision and intentionally stale pending invocations, not invalidate A's historical receipt.

Revocation of an active credential increments active generation and connection revision, clears its selection and disables affected settings in the same transaction, with immediate destruction and no provider-side revocation claim. Emergency disable clears selection/advances settings or connection revision and denies future use; it need not destroy an active credential or erase its historical verified state. Re-enabling/selection requires a later separately authorized management operation and complete fresh policy; it is not implicit on save. Candidate revoke leaves A intact. Exact-version revoke after A has already been replaced cannot follow selection and revoke B. Current-authority workspace/connection disable is a separate operation and must be retried with fresh expected revisions after a conflict, never silently treated as an exact-old-version revoke.

| Race / serialization                                                                     | Required result                                                                                                                                                                                                                                                                           |
| ---------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A candidate verifies; replaced by B before completion                                    | A's receipt is stale; no A promotion or test metadata write. B remains pending.                                                                                                                                                                                                           |
| Candidate verifies; candidate revoke commits first                                       | Destroyed candidate stays revoked, no resurrection even after remote success.                                                                                                                                                                                                             |
| Workspace/connection disable commits before promotion                                    | Promotion denied. Enabled→disabled→enabled is still a revision mismatch.                                                                                                                                                                                                                  |
| Promotion commits before exact active revoke                                             | Fresh exact-new-version revoke may revoke it; stale exact-old-version request conflicts/no-change according to 3b CAS rules and cannot target new selection.                                                                                                                              |
| Promotion commits before current-authority disable                                       | Disable with current revisions clears selection and prevents subsequent use. A stale concurrent disable returns explicit conflict; it is never reported as successful disablement.                                                                                                        |
| Revoke/disable wins lock before promotion                                                | Revalidation denies promotion; no partial retirement of old A.                                                                                                                                                                                                                            |
| Two submissions of the same successful evidence                                          | One operation may commit; consumed permit/unique operation/disposition/state prevents the second.                                                                                                                                                                                         |
| Candidate B and C observations both exist                                                | **One pending still applies.** B may return remotely after its replacement by C. Only the current candidate with current CAS can promote; B's evidence cannot be rebound. If B already promoted before C was admitted, C is a later generation, not a second winner of the same rotation. |
| Rollback at receipt, retirement, destruction, activation, selection, generation or audit | A and selection/envelope/generation restore exactly; no partial B authority. Attempt liability remains admitted if the completion transaction rolled back.                                                                                                                                |

The literal state “two fresh independently verified current B/C candidates” is unreachable under one pending, one unfinished attempt, the 60-second admission interval and five-second promotion lifetime. Preserve these protections rather than weakening them to stage that state. Two prepared A→B/A→C management proposals race at candidate/admission CAS; one proceeds to verification/promotion. A late B observation after replacement/recovery is explicitly stale when C later verifies. Duplicate calls within one verifier session test one-use consumption; cross-process copied authority is invalid. Do not create simultaneous B/C pending rows by disabling the unique index to stage a test. The original A→B/A→C same-generation obligation is fulfilled by racing proposals/admissions, controlled stale-evidence timelines and duplicate consumption attempts, with **one active winner** and exactly one retirement audit for A. Final tests must identify which preconditions were possible under the real schema.

No finalizer needs a retired secret. Already transmitted work has its own bounded in-memory copy; immediate at-rest destruction is safe, does not recall those bytes and cannot extend authority. Untransmitted old handles fail the final generation/revision prerequisite. Production rewrap and key-retention tooling are not added in 3c-1; unknown/retired KEK or concurrent wrap revision change denies verification. Maintenance implementation needs its own bounded review.

A required-audit failure rolls back the associated mutation and prohibits send or subsequent disclosure as applicable. No deferred audit.

Verification disclosure says that a credential and fixed model/account routing metadata go to Anthropic, with no business data or model prompt. It is not inference consent. VAP/customer and Anthropic/future OpenAI acknowledgements cannot substitute for one another. Production/provider/privacy/geography/budget approvals remain independent; a successful verification never satisfies them retroactively.

### 13.10 Offline evidence and test composition

Synthetic wire tests are necessary to prove the real state machine without live keys, but they are not provider validity evidence. Production contains only the fixed reviewed verifier composition; no HTTP parameter, `APP_ENV`, configurable class name, database verifier name, generic DI override hook or `verified=true` selects a test issuer.

Tests may substitute **only the lowest wire exchange**, with inert secrets, an explicit test deployment identity and ephemeral test receipt key; they run the actual admission, auth, deadline, parser, signer, lifecycle, DB constraints and audit. Production trust configuration does not contain test keys/deployments. Receipt provenance is `provider_tls` or `offline_fixture`; the latter is cryptographically bound and rejected by production consumers even if other metadata looks valid. An explicit test harness under autoload-dev authorizes fixture transport only inside PHPUnit/Pest CLI with isolated test DB and fixture trust roots. Changing environment name alone is insufficient. Production must never load that harness. No public permit factory or synthetic success writer is added for tests.

For active concurrency fixtures, establish A by exercising that complete offline verification/promote path before racing workers. Never raw-insert active rows, drop `no_probe` without the replacement, disable constraints, mock row locks or manufacture a “provider verified” receipt from a fixture array. Tamper tests may attempt those writes and must demonstrate that no application authority results. Isolate/reject exported fixture receipts in a production-composition test. Evidence reports must label positive-active tests **offline protocol/lifecycle proof**, not live account/model verification.

### 13.11 Required 3c-2 consumption design boundary — not an implementation grant

The next design must preserve this required sequence: fresh explicit actor/workspace/entity/production/deployment → original/current permission intersection → tenant mode and exact five-tool ceiling → registered provider/model/ownership/account selection → active receipt/generation validation → current approvals/disclosure/acknowledgement → atomic shared/account admission → purpose-bound one-use invocation authority → JIT decrypt → final send prerequisite → one bounded inference → untrusted provider-plan validation → fresh tool/disclosure checks. Retrieved tool results remain outside model inference. All Phase 6/7 question limits, plan bounds, deterministic factual authority and tools remain unchanged.

**VAP Managed:** only the approved protected deployment reference/path. No customer credential lookup/copy and no tenant-selected path. **Customer Managed:** only the exact selected active version on the resolved tenant connection, authentic receipt, correct current activated generation and full context binding. The gateway accepts no caller/model-supplied credential ID or provider client. A missing/expired/revoked/replaced/forged/unverified selection denies, never falls back to VAP or another key/provider/model/ownership mode.

`CredentialInvocationPermit` is distinct from verification send and promotion authority. It binds one assistant interaction/request/fiber, actor and permissions ceiling, tenant/entity/environment/deployment, mode, profile/manifest/provider/account/endpoint, selected version and activated generation, all current lifecycle/policy/approval revisions, disclosure/acknowledgement, immutable attempt/allocations, exact input digest and deadline. One send maximum within the existing 10-second interaction and 8-second wire budgets. A verification permit must fail at inference consumers and vice versa. A durable signed verification receipt proves past verification, **not** permission to mint an invocation permit.

Choose **generation validation immediately before transport handoff**, with a durable one-use send-authorization mark, not broad DB locks held across inference. The precise linearization point is the commit of the short prerequisite transaction executed by the pinned transport just before HTTP request bytes. Under canonical locks it revalidates all current authority and records transmission committed/last-used/metadata audit atomically. If revoke/rotate/disable commits first, no send. If that transaction commits first, one already-authorized send may occur even if revocation commits in the few instructions before the first byte; there is no honest atomic DB-and-network cancellation guarantee. Record **send authorized/possibly transmitted**, not proof of receipt. A worker that fails before issuing that one request does not recover/retry it. Deadline still applies after commit. After response, authority changes deny tools/disclosure while the original attempt finalizes usage/unknown without refund or key reselection.

No secret-bearing provider/SDK client is cached by tenant name, static property, singleton, Laravel configuration, SDK manager, queue worker or Octane container. Construct a narrowly scoped client/transport for that invocation, never mutate `config('ai.providers')` or register a customer secret in `AiManager`. Release plaintext and client on success/denial/exception/disconnect. The accepted SDK quarantine remains; use only the reviewed explicit protocol seam. Octane/long-lived worker enablement requires explicit isolation rehearsal, not assumed request teardown. Sequential tenants A→B→A, interleaved fibers, container reuse and exceptions must show no identity/secret bleed. No queued customer invocation is authorized.

Active eligibility does not widen an actor's role, tool scope, financial access, sponsor grant or entity grant. True tenant flags cannot grant unknown capabilities; the entire plan is validated before any tool. Provider output is untrusted; it cannot choose URLs/credentials/permissions, call generic services or override deterministic answers. All production activation gates remain separate.
