## Atomicity and concurrency assessment

The actual path is `ExternalCommandBoundary → ExternalCustomerCreateController → ExternalCustomerCommand → CommandIdempotency → CustomerCommands`. The browser store shares the last action through its distinct captured human context. The machine adapter cannot pass the broader human DTO or persist without a correctly bound executing reservation.

The PostgreSQL command uses a real outermost primary READ COMMITTED transaction. User/original membership SHARE locks precede integration/current credential UPDATE locks, exact grant SHARE locks and workspace/entity KEY SHARE locks. Identity, binding, expiry, original membership, role, verification/MFA and both grants are revalidated after waiting and again before commit. Integration serialization is intentional; independent process barriers do not serialize the harness in place of database locks. Different integrations can race on the authoritative entity/NIF constraint.

Reservation, actual customer insertion, required authorized/created audits, immutable result finalization, trigger-maintained capacity and last-used update commit together. The attempted event precedes that transaction and does not claim an effect. PostgreSQL rejects a durable executing reservation at commit. Failures after customer insert, audit, finalization/counter and immediately before commit roll back all successful-state effects; precommit worker death also rolls back. R1 closes the non-throwing save-failure hole. There is no normal customer-commit/result-not-commit window in this shared transaction.

After commit, transport failure cannot undo the effect. The new worker-death case observes the committed row from a separate connection, kills the first process before it returns its response, and retries through actual authentication/middleware. The original body/operation/customer are replayed; there is one creation audit and a distinct replay audit. No mocked repository or SQLite transaction stands in for this evidence.

Withdrawal serializes against the locked authorization boundary. A withdrawal that wins before the command's locked revalidation denies execution/replay; one blocked behind the command can commit afterward without retroactively invalidating its already committed effect. The new postcommit cases allow that original 201, then require 401 for a subsequent retry after credential/parent revocation and preserve every historical ledger field. Expiry is checked using database `clock_timestamp()`, including after lock waits. The final two implementation default-price-list deletion cases exercise both writer orders and preserve either valid assignment followed by FK nullification or creation with no deleted default.

This proves one local durable business effect within the approved path and database assumptions. It does not promise delivery of one HTTP response, unlimited replay availability after authority loss, remote exactly-once execution, or safety against a privileged database administrator disabling guards.

## Next bounded phase recommendation — not executed

The original master roadmap's safe-mutation stage names customer/catalogue writes before draft preparation and separately gates fiscal issuance. Phase 5A already crossed from external reads to one non-fiscal write. The smallest useful next substrate exercise is **Phase 5B: create one non-stock catalogue service**, with Astra design first. It adds a second domain/command namespace and tests generality without stock movements, document revisions, numbering, receipts or AGT operations. Customer update would immediately require stale-write and changed-record semantics; draft creation adds substantially more fiscal calculations and relationships.

Inspected current `CatalogueItemController`, `StoreCatalogueItemRequest`, `CatalogueItem`, `CatalogueItemPolicy` and entity/code uniqueness. Creation currently resides in the UI controller. Service type already forces stock tracking off, while pricing, currency, units and supported tax treatment require intentional command rules. Catalogue creation must not silently claim tax-law or issuance certification.

The **idempotency semantics can be reused; the current code cannot be reused unchanged for a second command**. Its enabled command/scope/version, canonical defaults and database CHECK/result guards are deliberately customer-specific. Astra must specify a closed second registry entry, an additive guarded migration and command-specific canonical input/result while preserving every existing customer byte/namespace. It must also decide that capacity and quota stay shared per integration/workspace across command types, so another route is not an allowance reset. No generic caller-selected command/effect or wildcard authority is implied.

Proposed new boundary: an independently granted service-create capability/scope, fixed service/no-stock defaults, exact integer money/base-currency semantics, supported persisted tax configuration, entity/code uniqueness and minimal historical acknowledgement. Same-code races, UI/API races, entity currency changes, grant withdrawal, postcommit loss and same key across two commands require PostgreSQL coverage. No optimistic revision is needed for a new row; update remains excluded.

Recommend a deliberate standing human scope grant under the existing owner/admin/MFA/recent-auth lifecycle, subject to Astra's explicit design decision; no automatic grant and no agent authority. Per-service approval is not recommended for this narrow preparation step, but this recommendation grants no implementation authority. Required creation/replay/denial/failure audit must retain current/origin actors and omit service text, price and tax payloads. Existing operational and external-disable holds continue.
