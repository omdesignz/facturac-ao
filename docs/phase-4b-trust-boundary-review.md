## SA1 and receipt entry-path evidence

The route/controller, issuance FormRequest/policy, `IssueFiscalDocument`, receipt preparation/calculation, document capability/source-selection paths and recurring action callers were inspected. Existing fiscal issuance converges on `IssueFiscalDocument::execute`; every document type that settles other documents reaches its final receipt integrity check. Preparing or recalculating a draft cannot issue it. Existing recurrence calls the same issuer rather than a separate fiscal engine. Direct action tests exercise the gate without relying on a controller badge or selection result.

The final action retains revision, source type, customer, currency, amount, balance/allocation, context and series/integrity checks. It takes existing draft/series locks, then source document/submission locks in ascending order and retains them through commit. A source must have properly bound authoritative V, known/idle current evidence, consistent Valid workflow, no outstanding claim/due work and a replay-consistent projection. The qualifying protected attempt is reinterpreted, not trusted solely because its journal says valid. Unknown, incomplete, contradictory, rejected, transport-only, unsupported, future or local-only evidence denies. Passage of 15 minutes alone does not deny proven acceptance.

The required denial audit is outside the action's own rolled-back issuance transaction. Inspected receipt entry paths do not surround the action with a separate rollback-only transaction. This is not a promise that an arbitrary future caller can wrap and roll back a database audit; any future consequential capability must preserve the required audit transaction contract. No such capability is added here.

Receipt-first versus evidence-first is intentionally different: if issuance locks proven evidence first, a later contradiction cannot retroactively rewrite the committed receipt; if uncertainty commits first, issuance denies without consuming a number/signature/outbox. New PostgreSQL barriers prove both orders and preserve the denial audit in the latter.

## Evidence, ordering and durable recovery

The new journal rejects UPDATE/DELETE at model and database boundaries. Scoped composite foreign keys, operation/sequence references, replay uniqueness, closed shapes and same-aggregate projection references constrain writes. The pre-existing attempt model remains application-immutable; this review does not claim that a privileged database administrator cannot alter legacy tables or disable database triggers. The receipt gate verifies hashes and rebuild equality rather than trusting a raw cache assignment.

Encrypted original request/response attempts and separately encrypted differing-duplicate bytes remain protected storage. Normalized journal/projection/audit JSON contains no raw gateway messages, signing material or infrastructure details. Exact duplicate completion is idempotent; differing duplicate evidence is retained and conflicts. Older consistent evidence cannot replace newer knowledge or advance freshness; opposing terminal evidence remains conflict regardless of arrival order. Rebuilding identical journal inputs reproduces the same projection.

Claim, evidence and projection writers lock bound document then submission, verify immutable context, and never acquire a receipt/series lock afterward. Network I/O occurs after claim commit and outside the database transaction. Claims use increasing generations and database-clock two-minute leases; completion is bound to the captured operation. Failure callbacks cannot fail a newer claim. Evidence/projection/audit persistence is one transaction; worker death before commit rolls back, while death after commit preserves one idempotent result. Expired abandoned work can recover without giving the original worker authority over a newer generation.

The local reservation added for legacy Sending is a present maintenance/recovery event, with null observed-at. It is not a fabricated historical submission attempt, response or acknowledgement. It preserves existing workflow/due counters, never acts on acknowledged/terminal/conflicting work, and performs no I/O. It makes the already-approved abandoned-Sending recovery reachable after migration.

## Reconstruction and migration review

Both migrations were inspected against PostgreSQL. The first adds the journal/control fields and integrity guards; the second invokes shared reconstruction. The review strengthens the first **unreleased, uncommitted** additive migration rather than adding a third corrective migration. No application or production database was migrated. If any deployment has already applied that original migration, stop rollout and prepare an explicitly reviewed forward migration; changing its source alone is not an upgrade path.

Backfill does not rewrite issued fiscal rows, workflow history, attempts/events or frozen bytes. Absent/local evidence remains unknown; incomplete linkage/hash/times/decryption/order remains partial; binding/hash/terminal contradiction remains conflicting. A legitimate sequential transport failure followed by complete bound acceptance is distinct from missing historical evidence. Imported timestamps retain original observation time; reconstruction time is not evidence time. Multiple attempts require defensible order; unsupported old labels do not fill gaps. A new qualified result may resolve ordinary uncertainty but not sticky conflict.

Populated migration/preflight, interrupted rollback/resume, repeat rebuild, cross-context constraints, earlier migration roundtrip and populated downgrade refusal are covered by existing and expanded PostgreSQL gates. Chunking bounds the input query, but it does not establish a production transaction/lock budget: Laravel's PostgreSQL migration transaction can encompass the backfill. Operators must measure the actual complete migration, not extrapolate per-row timing. An evidence-bearing downgrade deliberately refuses destruction; use reviewed forward repair.

The earlier implementation report's 300-row measurement is journal fixture insertion plus projection under a transaction, not a representative full legacy import. Query plans and that synthetic measurement were rerun, but production throughput, full-import memory/decryption cost, WAL and downtime are still rehearsal requirements. The final 300-row journal fixture used **1,211 SQL statements / 933.294 ms** inside its measured transaction. Replay used Sort (planning 0.334 ms, execution 0.100 ms); scoped projection lookup used Seq Scan for one aggregate (planning 0.413 ms, execution 0.010 ms). These small-fixture plans are not production index/capacity guarantees. No production benchmark is claimed.
