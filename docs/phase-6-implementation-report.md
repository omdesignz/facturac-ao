## Narrow customer-search remediation after Astra final review

Astra's independent final review returned **CHANGES REQUIRED** with exactly one new **BLOCKING** finding: customer search can traverse other tenants' rows beyond its signed bound. Phase 6 remained open. The previous SDK1 closure results above are retained as historical validation, not evidence that this defect was absent.

Root cause: candidate discovery expressed equality predicates on workspace/entity but ordered only by the global `id`. PostgreSQL could satisfy that order with a backward primary-key scan, treating the context as a filter. Astra's actual migrated-table reproduction returned 10,001 authorized keys after rejecting 20,001 newer foreign rows, inspecting 30,002 rows. The original favourable fixture seeded foreign rows first and masked this access path.

The only production correction is in `app/Fiscal/CustomerSearchQuery.php`: candidate discovery now uses the inclusive lexicographic range `(workspace, entity, PHP_INT_MIN)` through `(workspace, entity, PHP_INT_MAX)` and orders by all three columns descending. On the verified 64-bit PHP/PostgreSQL bigint domain, this interval includes every ID of precisely that workspace/entity and no other tuple. Within it, workspace/entity are constant, so the deterministic order remains descending ID. The full ordering retains the scope-prefix index path instead of allowing the global ID ordering shortcut. See [PostgreSQL 18 index ordering](https://www.postgresql.org/docs/18/indexes-ordering.html) and [row comparisons](https://www.postgresql.org/docs/18/functions-comparisons.html). Existing signed-int bounds also cover SQLite IDs without truncating the population.

No migration/index change is required. The approved `(workspace_id, legal_entity_id, id)` index already supplies the range/order. PostgreSQL may use another scoped bitmap path for smaller admitted populations; acceptance measures actual returned plus filtered/rechecked table rows and follows the child bitmap index conditions instead of requiring a named index or rejecting bounded sorts. Large adverse populations use the ordered context range; empty/over-cap results do not execute payload lookups. No planner feature is disabled.

The materialized candidate/admission/matching stages remain one SQL snapshot. Population cap 10,000, detection-only key 10,001, eleven-match detection, ten-result output, literal case-sensitive name/status filtering, explicit repeated payload context predicates, minimized four-field projection and safe over-cap refusal are unchanged. Authorization, work-session/context/permission freshness, audit, quotas/replay/lease, deadlines, billing/SA1/V1/V2 and SDK quarantine are unchanged.

Only five existing repository files are changed by this remediation: the query; `tests/Unit/PostgresAssistantTest.php`; `tests/Feature/AssistantFoundationTest.php`; this report; and its evidence JSON. Existing tests/assertions remain and are strengthened. No dependency/configuration/route/UI/service/migration or signed contract is changed.

Sixteen new cases: eleven actual migrated-schema PostgreSQL plan cases (newer foreign rows; interleaving; 20,001 versus 200,001 foreign rows; sibling entities; 9,999/10,000/10,001 boundaries; empty/sparse context) and five HTTP confidentiality cases (foreign exact/partial matches, populated foreign plus empty authorized context, equivalent names, foreign public-ID detail). Tests count returned + filtered + index-rechecked table rows, require scope conditions in the access-path tree, reject global sequential scans/lossy bitmaps/prohibited spill, verify complete expected descending result IDs, and prove zero payload loops above cap.
