## D1 — environment and ownership

Customers and catalogue items are **legal-entity master data shared by existing UI workflows**, not fiscal evidence partitioned by environment. Their creation history does not reliably distinguish sandbox from production records. Neither document associations nor an AGT connection can establish that distinction.

For these four new operations only, require `environment = production` in both the explicit execution context and, for machines, the immutable integration binding. Return generic 403 in homologation before any master-record lookup, count or search, even when the caller knows a public ID or a stored grant was manually inserted. Apply this rule to session and direct capability callers too. Credential creation/rotation/expiry replacement must reject a requested customer/catalogue scope in a homologation binding before secret generation/disclosure; runtime authorization remains the final defense.

This is an explicit conservative resource-access policy, not a claim that every master record originated in production, and not production AGT enablement. No AGT connection or outbound AGT operation is required to read these records. Existing homologation document reads are unchanged. Tests may use production-bound contexts in isolated test databases with all outbound fiscal effects forbidden.

Response metadata adds `data_scope: legal_entity_master`; its `environment: production` identifies execution context, not a new property of the resource. Do not add or backfill an environment column, infer row environments, copy live data into a sandbox, or silently grant homologation access. Sandbox customer/catalogue access requires a later Astra decision about partitioned or synthetic data.

Every query, including counts and detail resolution, must apply **both** verified workspace and legal-entity IDs. Never resolve a public record globally and authorize afterward. Use the primary database for final authority and these reads; do not permit replica lag to restore authority. ULIDs are opaque references, not secrets or authorization. Existing lowercase storage/canonicalization conventions remain; never substitute NIF, code or an internal sequential ID as the resource identity.

Place the additive capability/command classes alongside existing `app/Fiscal` capabilities. Reuse `DocumentReadContext` unchanged as the existing read-only authority interface despite its historical name; no rename, generic command bus or principal redesign is needed. Both existing context implementations must explicitly recognize the new permissions. Recurring approval retains its concrete human `ExecutionContext` requirement.

Human reads require fresh verified email, MFA, active membership and the existing customer/catalogue view-role eligibility in the explicit workspace: Owner, Administrator, Accountant, Billing or Viewer. Extend the human read-only permission allowlist by these two exact names, preserving real/effective actor and impersonation restrictions. Never call browser-dependent policies with machine sponsorship or mutate `current_workspace_id` to make a policy pass.

Machine effective authority remains the intersection of: authentic/live credential, live integration, immutable workspace/entity/environment binding, integration grant ceiling, credential grant, current original sponsor membership, current verified/MFA Owner or Administrator eligibility, capability permission and resource scoping. The scope set becomes exactly `documents:read`, `customers:read`, `catalogue:read`. Scopes are independently grantable and combinable. Existing document credentials gain **zero** authority. No wildcard, `read`, `read-all`, `admin`, `write`, `customers:*`, alias or implied cross-resource grant. ## D3 — customer representation and privacy

List and detail return the same four keys, all required, with no relationships:

| Key            | JSON/schema                         | Meaning                                                                                                                                                |
| -------------- | ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `public_id`    | string, canonical stored ULID       | Stable opaque record reference; never integer `id`.                                                                                                    |
| `name`         | string, 1–255 characters            | Stored customer display/legal name. It may identify a person or business; no independent business-name field or customer classification is fabricated. |
| `country_code` | string, two uppercase ASCII letters | Stored customer country code. Not nationality, tax residence or a verified address assertion.                                                          |
| `is_active`    | boolean                             | Current master-record active flag. Not creditworthiness, account approval or AGT validation.                                                           |

NIF/tax identifier, email, phone and address are **absent**, not null placeholders, masked values, hashes, suffixes or presence flags. Also exclude payment terms, credit limits, price-list IDs/links, customer prices, auto-send preference, withholding defaults, balances, document lists, aggregates, timestamps, internal IDs and all unlisted/future fields. Do not permit search, filtering, sorting or validation messages to disclose excluded values.

Names remain confidential and can be personal information. `customers:read` is an explicit grant to this limited directory, not permission to customer contacts or fiscal identity. Contact/address and NIF disclosure would need separately reviewed purpose-specific capabilities/scopes and minimization; **none are introduced or reserved as accepted aliases here**. Catalogue grants never imply customer access. Treat free-text names as untrusted plain text; do not claim automatic PII removal or distinguish natural persons from businesses without supporting data.

## D4 — catalogue representation, price and tax

List returns exactly these thirteen keys; detail adds only `description`:

| Key                         | JSON/schema                                | Meaning                                                                                                                            |
| --------------------------- | ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| `public_id`                 | string, canonical stored ULID              | Stable opaque item reference.                                                                                                      |
| `code`                      | string, 1–60 characters                    | Stored entity-local code, mutable business label; not globally unique identity.                                                    |
| `type`                      | enum `product`, `service`                  | Existing `CatalogueItemType` value.                                                                                                |
| `name`                      | string, 1–255 characters                   | Stored item name, plain text.                                                                                                      |
| `unit_of_measure`           | string, 1–32 characters                    | Stored unit label; no conversion or stock-scale interpretation.                                                                    |
| `unit_price_minor`          | string matching `^(0                       | [1-9][0-9]{0,18})$`, value at most 9223372036854775807                                                                             | Nonnegative base unit price in hundredths, transported as decimal digits to avoid JavaScript integer precision loss. No sign, grouping, exponent or decimal point. |
| `price_scale`               | integer, constant `2`                      | Existing application's amount convention: `123456` means 1234.56 currency units. This is not a new per-currency conversion engine. |
| `currency_code`             | string matching `^[A-Z]{3}$`               | Stored item currency, not silently replaced by entity currency.                                                                    |
| `tax_type`                  | string, 1–8 characters                     | Stored tax component, not inferred legal treatment.                                                                                |
| `tax_code`                  | string up to 8 characters or null          | Stored component; preserve null.                                                                                                   |
| `tax_percentage`            | string matching `^-?[0-9]{1,3}\.[0-9]{2}$` | Stored decimal with two fractional places; e.g. `14.00` means fourteen percent, not 0.14.                                          |
| `tax_exemption_code`        | string up to 8 characters or null          | Stored exemption component; preserve null.                                                                                         |
| `is_active`                 | boolean                                    | Current master-record status.                                                                                                      |
| `description` (detail only) | string up to 500 characters or null        | Stored description as plain text; omit the key entirely from list results.                                                         |

The price string is a deliberate new catalogue wire contract, not a change to PHP/domain storage or existing document API numeric fields. Preserve exact large amounts; never use floating point. Base unit price is the existing catalogue supply-price input before line tax, discounts and withholding, not a quote, tax-inclusive final amount, stock valuation or amount owed. No FX, conversion date, customer-specific price resolution, price-list fallback or aggregate sum. No customer parameter is accepted.

Tax fields report persisted configuration, including representable legacy/inconsistent combinations. Do not invoke legacy repair, recompute codes, reject a row solely because its tax combination is unsupported for issuance, or imply AGT validation. Schema shape bounds are representation bounds, not tax-law approval. Malformed/unrepresentable storage that cannot satisfy the schema yields sanitized 500 and no partial page, no successful-use update and no success audit; do not silently truncate, replace or repair it. The existing UI's description validation permits 500 characters whereas the original string column may be narrower on PostgreSQL; this design accommodates existing accepted values without changing that writer/schema behavior.

Exclude `tracks_stock`, `stock_scale`, reorder thresholds, quantities, warehouse/balance/valuation data, internal ownership/relationship IDs, timestamps, price-list/customer overrides and every unlisted field. Free-text names/descriptions are intentionally disclosed business content, not guaranteed free of accidentally entered personal data. Detail-only description reduces bulk disclosure; no description search or expansion exists.

## D5 — routes, query contracts and consistency

Add four GET routes (each also supports HEAD) under **each** existing prefix:

- Session: `/api/v1/workspaces/{workspacePublicId}/legal-entities/{entityPublicId}/environments/{environment}`.
- External: `/api/integrations/v1/workspaces/{workspacePublicId}/legal-entities/{entityPublicId}/environments/{environment}`.

Suffixes are `/customers`, `/customers/{customerPublicId}`, `/catalogue-items`, `/catalogue-items/{itemPublicId}`. Keep the existing document paths unchanged. Do not add exports, batch lookup or public root discovery.

| Parameter  | Customer list | Catalogue list | Exact semantics                                                                                                                                                                                |
| ---------- | ------------- | -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `page`     | yes           | yes            | Integer 1–10000, default 1.                                                                                                                                                                    |
| `per_page` | yes           | yes            | Integer 1–50, default 25.                                                                                                                                                                      |
| `status`   | yes           | yes            | `active`, `inactive`, `all`; default `active`.                                                                                                                                                 |
| `q`        | yes           | yes            | Optional literal case-sensitive substring, 2–80 Unicode characters after trimming leading/trailing ASCII spaces; valid UTF-8, no control characters. Present empty/null/array inputs fail 422. |
| `type`     | no            | yes            | Exact `product` or `service`.                                                                                                                                                                  |
| `code`     | no            | yes            | Exact case-sensitive stored code, 1–60 characters; no case folding or whitespace normalization.                                                                                                |

All filters combine with AND. Customer `q` examines **name only**. Catalogue `q` examines `(name OR code)` inside a grouped predicate beneath both ownership predicates. `%`, `_`, backslash and quotes are literal, never SQL patterns. No accent folding, transliteration, stemming or Unicode normalization. Implement bound-parameter substring matching with PostgreSQL `strpos` / SQLite `instr`, and deterministic case-sensitive exact code comparison (PostgreSQL deterministic `C`/SQLite binary semantics where necessary), rather than relying on database-dependent LIKE behavior. Unsupported production drivers remain unsupported, not silently weaker.

Sort only by internal primary key descending; never expose the key. This gives a unique deterministic tie-break and avoids rename-based reordering. No `sort` parameter. Page counts are authorized, filtered counts; no global totals. A page beyond results returns 200 with empty `data`. Offset pagination is not a snapshot across requests: concurrent insertion/deletion can move pages and count/data statements can observe different committed states. No export-completeness guarantee, cursor or long-lived transaction is promised.

Detail accepts no query keys. An authorized inactive record remains available by detail ID; inactivity is a selection status, not an access revocation boundary. Unknown parameters, arrays in scalar fields, `fields`, `include`, `expand`, tenant overrides, contact/tax filters and credential/delegation inputs fail validation. Follow the signed body rejection behavior for authenticated GET/HEAD; no input-bearing GET body is a second parameter channel.

Return `data` plus `meta`, with existing request/workspace/entity/environment public metadata and `data_scope: legal_entity_master`. Lists additionally include `page`, `per_page`, `total`, `last_page`; detail does not. No pagination URLs that echo search terms, no model relationship links, no ETag/304 path or cache shortcut around authority. HEAD performs the same validation, authorization, query, quota and mandatory audit as GET, but has no response body on success or error.

## D6 — error, audit, redaction and quota behavior

Preserve existing session authentication/MFA and external boundary semantics. External disabled returns the existing 404 before credential/resource processing. Invalid, expired, revoked or unrecognized credentials retain indistinguishable 401/challenge behavior. Well-formed foreign/absent workspace/entity bindings both deny 403 before target lookup. Missing permission, removed sponsorship, scope mismatch or homologation master-data access deny 403. An authorized detail lookup for missing or foreign resource IDs returns the same 404. Invalid syntax/filters return sanitized 422 without reflecting values. Unsupported methods retain 405; quota exhaustion 429; unavailable quota/audit dependencies fail closed with existing sanitized 5xx behavior. Do not introduce redirect/login HTML externally or reveal which grant/sponsor test failed.

Authorization precedes master queries, including counts; syntactic validation need not reveal resource existence. No name, tax ID, code or search term in errors. All responses retain fresh server correlation, private/no-store policy and existing Retry-After/challenge semantics. Validated client correlation stays separate; arbitrary inbound correlation cannot become server request identity.

Successful capability events are exactly `customers.list`, `customers.read`, `catalogue.list`, `catalogue.read`, version 1, using `RequiredAudit`. Build/validate the minimized projection before success recording; data may leave only after durable audit persistence, then successful-use metadata. Disabled, buffered, cancelled-save or failed audit must withhold the data. Preserve all existing actor fields: machine Integration causer, credential and immutable context, separate sponsor authority, null human executor/delegation/approval/automation; humans retain real/effective attribution. Do not turn the sponsor into an executing user.

Success metadata may include page/per-page/result_count and `search_applied` boolean, plus known status/type enums. Detail may record the public ID only after scoped resolution. No raw query, searched code, search hash, customer name, NIF/contact/address, description, response body, price or full URL. Internal audit subject keys remain permitted by the signed audit contract but never become response fields. Record `data_scope` on these new events.

Use trusted server route identity to assign customer/catalogue denial event families (`customers.read.denied`, `catalogue.read.denied`) and explicit operation metadata where resolved. Preserve existing document denial events. Unsupported/unmatched paths without trustworthy operation resolution use `integration.read.denied`, never a client-supplied capability label. Verified-context denials, including 401 after final revalidation, 403/404/405/422/429, retain mandatory durable audit. Anonymous failures remain unclaimed telemetry. Do not store a foreign/missing requested target identifier as a resolved subject.

Because name/code searches place confidential text in SQL bindings, protect query execution on both adapters and direct capabilities: suppress query-event/query-log capture around the new bounded read operations and replace binding-bearing database exceptions with sanitized exceptions without an unsafe previous exception. A small `SensitiveReadQuery` guard alongside the existing sensitive credential guard is allowed; it must restore connection settings on every exit and must not change credential persistence behavior. Test actual query listeners, exception reporting and log formatting. Do not log raw request URLs/query strings at the application layer. Ingress/APM/access-log query-string and response capture suppression remains an explicit operational enablement gate; application suppression alone cannot certify infrastructure.

Keep the same external quota identities and shared budgets across **all** document/customer/catalogue paths: pre-auth IP 120/minute, integration 60/minute, workspace 300/minute, using approved database-backed atomic locking. No per-resource fresh buckets, public-ID buckets or credential-rotation reset. Denials and HEAD consume the applicable buckets. Preserve the existing session user throttle. Do not introduce a new rate-limit backend or positive authority cache.

## D7 — proposed implementation and migration boundary

Permitted additions: two capability classes, four typed immutable command classes, minimized resources and thin session/external controllers/requests, new routes, explicit permission mappings, new audit operation attribution, sensitive read-query guard, tests and specification/report updates. Reuse existing context resolvers, required audit, limiter, domain casts/models and error boundary. Do not load full models then rely solely on serializer hiding: explicitly select the allowlisted columns, plus internal keys strictly needed for ordering/scoping/audit. No relationships or per-row queries; query count stays bounded independently of page size.

Propose one additive migration widening **both** scope-table CHECK allowlists to precisely the three signed scopes. Inspect actual constraint names/schema before writing it. PostgreSQL changes occur transactionally with validated replacement constraints and no commit-visible unguarded interval. SQLite may rebuild only the two scope tables as needed, preserving rows, composite/unique keys, FKs and credential-scope immutability triggers; verify foreign-key integrity afterward. Preserve every integration/credential/user identity trigger and A1 snapshot. Do not edit the historical migration or grant any new scope during migration.

Rollback must refuse rather than delete grants when either new scope is present. Also refuse if new capability audit evidence exists, including after grant removal. Use the same maintenance/backup discipline as Phase 3; forward repair is preferred once used. Test fresh install, existing document-only data upgrade, failed migration rollback, safe empty rollback/reapply and protected rollback. No customer/catalogue environment or identity backfill is approved.

Two ordinary read-support indexes `(workspace_id, legal_entity_id, id)` on customers and catalogue items may be added in this migration or a separate additive migration if PostgreSQL plans show existing indexes insufficient for scoped ordered reads. Document measured justification; do not add speculative search extensions or change uniqueness. Existing entity-local NIF/code uniqueness does not turn those values into API identity or lookup authority. No migration is applied in this design task.

## D9 — acceptance and adversarial gate

All criteria below are required implementation evidence, not claims that tests already exist:

1. **Grant separation:** every subset of the three scopes; customers-only cannot read catalogue/documents, catalogue-only cannot read customers/documents, document-only gains nothing. Missing either parent or credential grant denies. Unknown/duplicate/wildcard/admin/write scopes fail validators and database constraints. Homologation lifecycle requests for new scopes fail before secret creation/disclosure; manually injected grants still cannot bypass capability environment policy.
2. **Context/isolation:** wrong workspace, second entity within the same workspace, same sponsor with multiple memberships, foreign/absent ULIDs, all filters/counts/details, independent cookie/current-workspace changes and attempted header/query/body overrides. Homologation list/detail/HEAD return 403 before any master-table query. Production-bound test reads perform no AGT HTTP, jobs, notifications or fiscal writes.
3. **Current authority:** direct capability and both adapters; role/membership/MFA/email loss, membership recreation, sponsor deletion, parent/credential revocation and expiry, grant reduction. Independent PostgreSQL processes commit revocation or grant/sponsor changes before final authorization: deny. Preserve signed allowed completion for a read authorized before revocation commits; do not claim linearizability through response delivery.
4. **Minimization:** assert exact key sets, not just missing one field. Populate every excluded field with distinctive sentinels and check body, error, audit, query events and formatted logs. Searches matching only NIF/contact/address/description/price-list data must not find a record. Adding future fillable fields cannot expand projection. Inactive list/default/detail semantics tested.
5. **Search/pagination:** literal `%`, `_`, backslash, quotes, SQL-like text, Portuguese accents, case variants and non-ASCII text; compare SQLite/PostgreSQL results. Grouped OR cannot escape ownership. Exact code, combined filters, empty/out-of-range pages, bounds, invalid UTF-8/control characters, scalar/array confusion and unknown filters. Deterministic ordering with identical names/codes in different entities; bounded query count for one versus fifty rows.
6. **Price/tax:** base price differs from negotiated/list prices yet response stays base; multiple currencies never summed/converted; zero and values beyond JavaScript safe-integer range preserve decimal digits; int64 boundary; two-place tax strings, null codes and legacy contradictory combinations remain faithfully represented. Invalid representation fails without partial response/success audit/last-use. No hidden stock or financial joins.
7. **Audit/transport:** GET and HEAD, failures before/after context, unsupported methods, durable success/denial audit, disabled/buffered/cancelled/throwing audit, sanitized query failures, server/client correlation, no secret/PII reflection, no-store and no-body HEAD. New route denials are not mislabeled document operations; anonymous paths claim no tenant. Query guard restores connection state after success and exception.
8. **Quotas:** alternating all three resource families shares integration/workspace totals; HEAD and denials count; rotation does not reset. PostgreSQL multi-process contention across families/integrations preserves the approved ceilings; failed cache/audit dependencies deny. Existing pre-auth behavior remains intact.
9. **Migrations:** SQLite and PostgreSQL upgrade fixtures containing old credentials/grants/snapshots/audits; byte-preserve existing attribution and fiscal rows, preserve CHECK/FK/unique/immutable guards, no automatic scope grants, rollback protection and reapply. Existing A1 backfill and fiscal concurrency cases continue to pass.
10. **Compatibility:** existing Inertia register/search/import/pricing, session document API and every Phase 1–3 regression unchanged. Direct capabilities and adapters agree on minimized results and authority. Route/spec inventory contains only the approved read additions and no provisioning/mutation exposure. External flag remains false by default and no live credentials are issued.

PostgreSQL is mandatory for constraint, migration, concurrency and full new API behavior evidence. SQLite successes or skipped process tests cannot replace it. Use only a verified disposable test database, never the application/production database. Exercise the new API/adversarial suites on PostgreSQL as well as SQLite; add their files to the existing PostgreSQL CI gate. Inspect scoped PostgreSQL query plans with realistic test cardinality and report count/search cost; bounded output alone does not bound a substring scan. Do not silently add a search service to address performance concerns.

## Architectural readiness and exclusions
