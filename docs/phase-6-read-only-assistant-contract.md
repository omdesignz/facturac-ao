Decision date: 2026-10-08. Architecture and adversarial design only. Phase 5B is closed, as established by its independent final review. This document does not reopen it, authorize external access, amend A1/SA1, or implement any runtime behavior.

The handoff implements a provider port, a fail-closed unavailable adapter and deterministic test doubles. ## 2. Architecture and principal boundary

The first release is a **single-question, session-authenticated, production-context read planner**, not an autonomous agent or conversational memory service.

```text
human session + explicit workspace/entity/production tuple
  -> server authorization, limits and interaction identity
  -> bounded model planner (question + fixed tool schemas only)
  -> validate entire proposed plan against closed contracts
  -> fresh human ExecutionContext authorization for each approved read
  -> shared application capabilities -> primary PostgreSQL
  -> validated minimized results + required audit
  -> deterministic Portuguese result cards and explanations
  -> final authority revalidation -> authenticated browser
```

The model receives **no tool results or stored business data** in this initial design. It proposes a plan once; it does not receive a tool-execution loop. This deliberately eliminates indirect stored-text instructions from model input and reduces third-party disclosure. Model-generated factual prose is not an output channel. The interpretation being delegated is question-to-tool selection, not business truth or authority.

An internal `AssistantInteractionContext` composes an existing `ExecutionContext::resolve(..., readOnly: true)`. It is not a new `DocumentReadContext` implementation and is never substituted for `ExecutionContext` at the analytics boundary. Capture original active membership identity, actor, explicit tuple, initial permission ceiling, work-session deadline and server interaction/correlation IDs. Approval/automation/impersonation fields must be absent. Only the existing human principal is used; machine credential scopes are neither consumed nor minted.

Resolve workspace through the authenticated actor's active memberships on the primary. Resolve entity only inside that workspace. Require verified email, enabled MFA and valid existing work session. Reject support impersonation, delegation and scheduled principals for this channel even though earlier read adapters permit attributed support reads. This is a narrower channel policy; their existing behavior is unchanged.

At admission, before every tool and again before final disclosure: re-read actor, original membership, entity ownership and current permission. Original membership removal/recreation is not a continuation of authority. Effective authority is initial ceiling intersected with current `ExecutionContext` authorization, permitted tool registry and immutable interaction tuple. Recheck the work-session deadline during long requests. No role upgrade during a request enlarges its ceiling. Withdrawal visible at the final primary authorization check withholds all results. As in the approved read plane, this is a check-time boundary, not a promise to erase bytes already legitimately delivered before a later revocation. Do not hold database locks across inference/network calls.

All Phase 6 tools require `production`. Homologation and unresolved contexts are denied before business queries, including when IDs exist. Production reads do not enable AGT operations. Mutating `current_workspace_id`, selecting another browser tab or changing a client header never changes a running interaction's tuple. The UI labels its tuple and clears displayed results on context change; late responses whose tuple/request no longer matches are discarded.

## 4. Exact interaction and planner contracts

All objects in this document are **closed**: required keys exactly as listed, no additional keys. Reject duplicate JSON keys, invalid UTF-8, files, query parameters, coercion of arrays/objects to scalars and authority-shaped fields. String limits are Unicode characters unless bytes are specified. Normalize public ULIDs to lowercase using existing validation; reject invalid/overflowing ULIDs. UUIDs are canonical lowercase server UUIDs unless specifically identified as a client request nonce.

One internal same-origin session route is authorized for the implementation:

`POST /assistant/workspaces/{workspacePublicId}/legal-entities/{entityPublicId}/environments/{environment}/interactions`

It uses the existing web session, CSRF and work-session protections; it is not a public integration API. A minimal Inertia page may host the form under the same explicit context path. No GET/HEAD execution, streaming, SSE, downloads, asynchronous polling or additional tool endpoints. Unsupported methods do not call inference or query business data. Private/no-store responses, no shared caching, existing safe session-cookie handling and server `X-Request-ID` are mandatory.

Request body, maximum **12 KiB** UTF-8:

- `request_nonce`: required UUID generated once by the browser per submission; transport replay control only.
- `question`: required UTF-8 string, trimmed, 1–2,000 characters, at most 8 KiB; reject control characters except tab/newline. Never log it or flash it to session validation storage.
- `references`: required array, 0–2 distinct closed objects `{kind, public_id}`. `kind` is `customer` or `document`; `public_id` is a valid ULID. These are explicit user selections/pastes, not authority. The UI may pass the resource the user deliberately selected. No model-extracted arbitrary ID becomes an admitted reference automatically.

Server captures the current Africa/Luanda calendar month before planning and may pass this month to the planner. Request has no history, attachment, prompt overrides, model, endpoint, workspace override, permission or credential field. A request is independent of all preceding questions; do not persist chat memory or accept assistant/system-role messages from clients.

The planner input consists only of the bounded question, admitted reference kind/public IDs, captured current month, versioned static schemas and the subset of tool names authorized at admission. Do not send internal actor IDs, names, company profiles, session data, audits, tool results or database rows. A human can paste sensitive text into a question; explain this in the UI and subject it to the provider gate in section 12. It is not safe to claim that prompting contains no personal data.

Planner output is exactly one of:

- `{decision: "read", calls: [...]}`: 1–4 closed `{tool, arguments}` objects. Each `arguments` object must match section 5. No nested plans, expressions, dependencies, URLs, prose, citations, function names outside the registry or tool-result instructions.
- `{decision: "clarify", reason: R}` where R is `select_customer`, `select_document`, `specify_month`, `refine_customer_search`.
- `{decision: "unsupported", reason: "outside_read_contract"}`.

A detail call must reference the matching kind/public ID in the original request. Thus a search result can be selected by the user for a **new** interaction; the model cannot automatically enumerate or chain through search results. Every detail lookup still performs current ownership/permission checks. At most one search, one billing call and two total detail calls; repeated identical calls and conflicting multiple months are rejected. Entire plan is validated before executing the first tool. Malformed/unauthorized plans produce a generic unavailable result and no business query, not an automatic repair loop.

## 5. Exact tool input/output contracts

Each successful tool returns internally `{result_id, tool, read_at, data}`. `result_id` is a fresh UUID owned by this request; `tool` is the exact approved name; `read_at` is server UTC RFC3339 observation time, not legal effective time or a transaction spanning tools. No model may supply these values. Each underlying capability must independently authorize and scope its read. Zero results are successful only where explicitly defined.

### 5.1 searchCustomers

Input exactly `{q, status}`. `q` is trimmed ASCII-space at ends, 2–80 characters, valid UTF-8 without Unicode Cc control characters. `status` is exactly `active`, `inactive` or `all`; the planner must supply it (UI examples default to active). Match the existing **case-sensitive literal substring of name**; `%`, `_`, quotes and backslashes are literal bound values, not SQL wildcard or syntax. No tax-ID, email, phone or address predicate.

Output exactly `{items, has_more}`. `items` is 0–10 customer objects in descending internal ID order; ID never leaves the server. Each object has exactly:

- `public_id`: lowercase ULID;
- `name`: stored valid UTF-8 display name, 1–255 characters;
- `country_code`: two uppercase ASCII letters;
- `is_active`: boolean.

`has_more` is true iff an eleventh match exists in the complete admitted candidate population. It does not disclose an exact total. No cursor, page, offset, total or continuation token. The renderer explicitly labels this as at most ten matches, not the complete customer register. Duplicate names remain separate; never select a customer by name as if unique. Empty items means no match in this authorized, successfully inspected population, never absence from all companies.

**Work bound:** admit at most 10,000 customer rows in this exact workspace/entity, regardless of status/search. Discover at most 10,001 ordered keys using the new index in section 11. The extra key is detection only. If present, return generic unavailable with no partial matches, even if an early match exists. Otherwise apply existing status/literal-name predicate to the admitted scoped rows, obtain at most eleven matched projections and emit at most ten. One SQL statement/snapshot must cover key admission and matching; both payload lookup and keys retain workspace/entity predicates. Do not fetch 10,000 names into PHP. Over-cap is not an empty match and must not be interpreted as one. Apply the query timeouts and PostgreSQL plan gate in sections 7 and 13.

### 5.2 getCustomer

Input exactly `{public_id}` for an admitted customer reference. Output exactly the same four-field customer object as search. Active and inactive records are readable under existing permission. Same scoping and visibility as search; direct lookup has no exemption from authorization and no contact-detail expansion. A foreign or absent valid ID yields identical `not_found`; malformed ID is `invalid_input`. No pagination. Scoped unique public-ID lookup only.

### 5.3 getFiscalDocumentSummary

Input exactly `{public_id}` for an admitted document reference. Output exactly:

- `public_id`: lowercase ULID;
- `document_no`: string or null, at most 255 characters;
- `document_type`: one of `FA, FT, FR, FG, GF, AC, AR, TV, RC, RG, RE, ND, NC, AF, RP, RA, CS, LD` (the current signed read enum set; future additions require review);
- `environment`: constant `production`;
- `revision`: nonnegative integer within PHP signed-integer range;
- `workflow_state`: `draft`, `issued`, `received`, `processing`, `valid`, `invalid` or `contingency`.

This is an allowlisted subset/rename of the existing V1 `issue_status` summary, **not** a redefinition of V1. Deliberately exclude amounts, currency, customer, lines, dates, AGT legacy status/source and all fiscal payload/evidence. A separate billing tool supplies bounded monetary summaries. Drafts may be identified as drafts; no draft contents. Render workflow enum values as “Estado registado no documento: …” with a fixed warning that they are not current AGT evidence or legal validity. Do not use `FiscalDocumentStatus::label()` to say simply “Válido” as a fiscal conclusion. AGT questions must use the qualified tool instead.

Reuse `DocumentCapabilities::readDocument` and project/validate only these fields before result construction. Its internal legacy fields must never enter planner input, assistant output or logs. Current unique submission binding keeps its existing read bounded; verify this with populated plans. No PDF, print, send, poll, history load or eligibility call. Foreign/sibling/wrong-environment/unresolved IDs all use the same `not_found` outcome. Data failing the closed representation fails unavailable, never a fabricated substitute.

### 5.5 getMonthlyRecordedBilling

Input exactly `{month}`, a string `YYYY-MM`, year 2000–9999, not after the current Africa/Luanda month. No day ranges, previous-period count, currencies filter, customer, grouping or `as_of`. “This month” is resolved using the server month captured before planning. Ambiguous dates require clarification rather than an invented period.

Output is **exactly** `BillingSummaryQuery::FIELDS` / the normative `docs/openapi-external-billing-v2.json` data object: `metric_version`, `date_basis`, `timezone`, `as_of`, `period`, `currencies`. These existing schemas are incorporated by reference without modification; implementation tests must compare key sets/types and validate against the normative schema. `metric_version=recorded-billing-v1`, `date_basis=document_date`, `timezone=Africa/Luanda`. The closed `period` object has exactly `month` (YYYY-MM), `from` (inclusive YYYY-MM-DD) and `to_exclusive` (exclusive YYYY-MM-DD). All eight ordered native buckets AOA, BRL, CNY, EUR, GBP, NAD, USD, ZAR are present, with `minor_unit_scale=2`, `billed_document_count`, `credit_note_count`, and the nine totals `invoiced_gross_minor`, `invoiced_net_minor`, `invoiced_tax_minor`, `credit_gross_minor`, `credit_net_minor`, `credit_tax_minor`, `after_credits_gross_minor`, `after_credits_net_minor`, `after_credits_tax_minor`.

Money remains canonical signed integer strings; no PHP float, JS Number conversion of monetary strings, implicit FX or cross-currency total. Deterministic decimal formatting uses string/BigInt arithmetic at scale two. No added calculations beyond formatting the nine existing metrics. Counts remain bounded integers. All existing overflow/unsupported-data/cap failures withhold the entire summary.

Meaning remains recorded local billing: FT/FR/GF/ND invoice/debit billing and NC credits; RG is recognized but does not contribute. Normal drafts do not contribute; malformed candidates fail. Required issue/frozen markers, supported fiscal states and exact document-date month semantics remain. Neither AGT acceptance nor receipts/payments determine these totals. Do not label them revenue, cash, receivables, tax liability or AGT-approved turnover. Renderer always shows the month, native currency and “Facturação registada”; zero means complete admitted empty bucket, not unavailable.

## 6. Response, provenance and errors

Success HTTP 200 is a closed `{request_id, interaction_id, context, outcome, reason, results}` object. `context` has exactly public workspace/entity IDs and `environment=production`. `outcome` is `answered`, `clarification_required` or `unsupported`; `reason` is null for answered or the matching closed planner reason; `results` is the validated ordered array of result envelopes (1–4 for answered, empty otherwise). No model response text is forwarded. Metadata is populated from the resolved context, not reflected body/header overrides.

The UI has a fixed renderer per tool and fixed Portuguese clarification/unsupported strings. It displays a source marker for each card from `result_id`, tool, context and `read_at`, and the billing/AGT `as_of` where applicable. Result IDs are references within this response, not public retrieval endpoints. Cards are separate snapshots; never imply that multiple tool reads constitute one atomic business snapshot. Public resource links are generated server-side from trusted IDs and known routes, never model/record URLs. Render customer names and document numbers as escaped plain text, including HTML, Markdown links, bidi/control tricks and “ignore instructions” strings. No `v-html`, executable Markdown or automatic URL fetching. Names never become instructions or citations.

Distinguish retrieved facts (cards), deterministic derivations (scale-two formatting and already-defined billing arithmetic), safe explanation (fixed AGT/status/metric vocabulary) and unavailable information (no result). No free-form model factual answer, prediction, financial/legal advice or guessed explanation. Unknown AGT state cannot be softened to “probably accepted”. An unsupported debt question is not answered with recorded billing. Multi-tool failure, authorization withdrawal or required audit failure withholds **all** pending results; no partial financial answer is streamed or serialized.

Error HTTP envelope exactly `{error:{code,message}, request_id}`. `message` is a fixed localized catalogue entry, never an exception message. No tool index, record count, IDs, prompt echo, SQL, model text, raw upstream text or partial results.

| HTTP / code              | Behavior                                                                                                                                                                             |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 401 unauthenticated      | Session absent/expired; no domain queries                                                                                                                                            |
| 403 forbidden            | MFA/verification, active membership, role, impersonation or production gate denied; foreign/nonexistent workspace identical                                                          |
| 404 not_found            | Entity missing/foreign inside authorized workspace; admitted resource missing/foreign/wrong environment indistinguishable; feature disabled also has a generic unavailable-route 404 |
| 405 method_not_allowed   | No inference/business work; Allow header lists POST for execution route                                                                                                              |
| 409 interaction_conflict | Duplicate nonce or active user interaction; no cached factual answer replay                                                                                                          |
| 419 session_expired      | CSRF failure with safe envelope; no tool call                                                                                                                                        |
| 422 invalid_input        | Closed protocol/schema/length/reference syntax violation; no echoed values                                                                                                           |
| 429 rate_limited         | Shared bounded quota/concurrency refusal, safe integer Retry-After                                                                                                                   |
| 503 unavailable          | Provider unavailable/malformed plan, unsupported stored representation, capacity/timeout/DB/cache/audit failure; same generic message, no partial result                             |

No record-dependent distinction occurs before capability authorization. Uniform error bodies do not claim constant-time behavior across infrastructure failures; rate limits, scoped lookup and no global existence probes are mandatory. Do not try to distinguish forbidden foreign records by looking them up globally.

## 7. Query, extraction and execution bounds

| Boundary                 | Hard server value                                                                                                           |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------- |
| Question/body            | 2,000 characters / 8 KiB question; 12 KiB entire body                                                                       |
| Planner                  | One invocation, at most 10 seconds, no retries or repair loop; max 4 KiB returned JSON                                      |
| Plan                     | At most four sequential reads: one search, one monthly billing and two detail calls; no parallel fan-out                    |
| Search                   | 10,000 candidates + one detection key, eleven matches inspected, ten returned, zero pagination                              |
| Document/customer detail | At most two total, unique public-ID scoped lookups; no listings/history/relationships beyond existing bounded read          |
| Date range               | One calendar month only for billing; zero arbitrary date windows                                                            |
| Billing                  | Existing 100,000 candidate + detection-only 100,001 policy, two bounded key ranges and single SQL snapshot unchanged        |
| Tool results             | At most 32 KiB UTF-8 combined serialized results; overflow fails entire interaction, no field/result truncation             |
| Whole response           | At most 48 KiB UTF-8; no compression-based expansion bypass                                                                 |
| Interaction              | 30-second server deadline checked before/after every stage; no job/background continuation                                  |
| User quota               | Six admitted interactions per UTC fixed minute and 120 per UTC day across sessions/workspaces                               |
| Workspace quota          | Thirty admitted interactions per UTC fixed minute                                                                           |
| Concurrency              | One interaction per user, lease 45 seconds; no waiting/retries; existing billing workspace lock still independently applies |

Use server-owned quota keys and the approved database-cache locking pattern, not IP-only, session-only, question-hash, model or nonce identity. Consume quota before inference, including replays/denials after safe context admission. All aliases/encodings use the same resolved route/actor keys. Fixed-window boundary bursts are permitted by these exact semantics; do not call this a sliding window. Quota/cache failure fails closed. Locks use owner tokens, release in finally, and are never released by a later owner. A deadline-expired process cannot execute another tool or disclose a result even if a new lease is subsequently acquired.

Retain a replay marker for `(actor, canonical request_nonce)` for ten minutes in the existing shared database cache; store only expiry/bounded outcome metadata, no question or results. Atomic admission means concurrent duplicates do not both execute. Duplicate returns 409, even with changed payload/context; after TTL a fresh authorized read is allowed. This is read transport replay control, not CS1 idempotency: there is no domain mutation/replay ledger, frozen answer or resurrected authority. Existing Phase 5A/B idempotency is untouched.

All assistant business reads use the primary. PostgreSQL capability invocation has maximum statement timeout 2,000 ms and lock timeout 250 ms, scoped and restored in finally on the dedicated request connection; no outer transaction spanning a capability or inference. Billing retains its existing stricter transaction/local timeout behavior. Audit/authorization queries are also bounded; a timeout never falls back to unbounded or replica reads. Test restoration on pooled connections and failure. SQLite remains a deterministic test target, not a production capacity proof. MySQL is not a supported assistant deployment target.

Read-only means no **business** writes. Explicitly permitted infrastructure effects are existing session management, quota/lock/replay cache and synchronous required access audit. A SQL READ ONLY transaction around the entire capability would incorrectly prevent its required audit and break billing's no-outer-transaction invariant: do not add one. Enforce the business read boundary through a literal five-case dispatcher, typed commands, independently authorizing existing capabilities, no injected model callable, query capture and before/after integrity tests. Technical side effects must be allowlisted, not an excuse for arbitrary DML. No external HTTP is reachable from tools.

## 8. Data minimization and logging

Only section 5 data may reach browser results. No full ORM serialization. All tool results stay server/browser-side and **never enter planner input**. Prompt, plan and result payloads live only in request memory; no transcript database, localStorage, analytics session replay, vector index, embeddings, shared answer cache or provider conversation state.

Never disclose/log NIF, email, phone, addresses, contact persons, bank/payment data, customer-specific pricing, inventory, document lines or XML/PDF, raw AGT messages/history, signatures/keys, credentials, internal sequential IDs, SQL/connection strings, source stack traces, arbitrary headers or model input/output. User public attribution IDs are not needed in planner input. Existing internal audit IDs remain permissible only inside restricted audit records.

Redact at every boundary: controller validation/session flash, exception reporting, request/context enrichment, query listeners, debug/APM, reverse-proxy body capture and future provider transport. Assistant-scoped audit enrichment must explicitly set `user_agent=null` and suppress arbitrary ambient context for **nested** V1 document reads as well as new events. Use a narrowly scoped server-owned marker with cleanup; do not change normal signed read-plane attribution or trust request headers to set the marker. `SensitiveReadQuery` provides a pattern for temporarily suppressing query listeners; ensure no collector retains raw bindings or prompt-containing exceptions. Production debug disabled is additional protection, not the sanitizer.

## 9. Required audit and observability

Keep existing successful capability audits. Add synchronous `assistant.interaction.started`, `assistant.tool.requested`, `assistant.tool.succeeded` or `.denied`, and `assistant.interaction.completed` or `.failed` events. Persist the started/requested events before inference/read respectively, and completed before releasing results. A failure to persist a required event withholds all response data; do not defer or queue successful audit. A failed audit may be reported using only server correlation and a fixed internal error category.

Permitted properties: existing trusted human attribution (including A1 user attribution identity where available), effective=real user, validated workspace/entity/environment, server request/interaction/tool-call/result UUIDs, fixed tool/capability/schema version, outcome category, bounded tool/result counts, duration bucket and planner configuration identifier. No approval/delegation claim; null automation/impersonation. Do not persist question/search string, resource names, result fields, arbitrary provider IDs, raw headers, plan arguments or financial values. Existing capability audits retain their already-approved scoped subject/public ID; do not copy result lists into new audit. New wrapper events link inner audits by server request ID plus sequential invocation interval/capability; result/tool-call UUIDs link the final rendered fact to that invocation. Exact values are not retained, so this is access provenance, **not** archival proof of historical answer contents.

Pre-context denials do not attach unvalidated tenant IDs. Actor absent means explicitly unauthenticated, not a made-up assistant/system actor. Metrics use fixed labels and bounded count/duration buckets, never tenant names, questions or arbitrary tool names. Audit retention/access and cache-expiry cleanup follow existing operational policy; no autonomous business jobs are authorized.

## 10. Threat model and adversarial dispositions

| Attack                                          | Required server defense / acceptance                                                                                                                |
| ----------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| Cross-tenant or IDOR; invented references       | Membership-scoped context, primary fresh permission, independent resource tuple predicates; same foreign/absent response; no global existence query |
| Mutable browser context; stale role/MFA         | Immutable explicit tuple, initial ceiling, original membership identity and final revalidation; no fallback or cached response                      |
| User prompt says issue/refund/run SQL           | Closed planner schema and literal tool registry reject it; no callable/service container access                                                     |
| Stored name contains instructions/HTML/URL      | Stored data never sent to model; exact escaped text cards; no network/link execution                                                                |
| Model invents tool/argument/authority/ID        | Validate complete plan before queries; references must be admitted by user, then independently scoped; no tool repair loop                          |
| Broad search/pagination/extraction              | Nonempty bounded search, fixed candidate cap, ten matches, no pagination; user/day/workspace quotas and no cross-question memory                    |
| Inference from financial errors                 | All over-cap/corrupt/timeout failures use same unavailable envelope; no totals, counts or partial cards                                             |
| Model invents money/status/citations            | No model prose/result injection path; fixed card data from validated capability results, server provenance                                          |
| Concurrent reads/replay/authority loss          | Atomic budget/nonce/user lease; sequential plan; fresh context every tool and disclosure; no replayed answers                                       |
| Indirect business side effect disguised as read | No controller-wide dispatcher, print/PDF/delivery/refresh/repair jobs; database table snapshots and HTTP/queue spies prove no business change       |

| Overlong or malicious planner output            | Byte/depth/closed-schema validation before tool dispatch; fixed deadline and no retries                                                             |

Residual: an authorized person can learn the allowed records through repeated legitimate use, subject to quotas; the assistant is not a general anti-insider DLP guarantee. Customer names are still business/personal information even without contact fields. Enumeration resistance is protection of unauthorized records, not concealment of authorized search matches.

## 11. Migration decision

No assistant principals, scopes, tokens, transcript, conversation, business-state, fiscal or command-ledger tables/columns are needed. Reuse existing cache/locks and Activitylog. No changes to CS1, sponsor/credential lifecycle, A1 identities, SA1 projection or service/customer creation invariants.

One additive, non-unique customer index is authorized for bounded search: `customers_assistant_context_id_index` on `(workspace_id, legal_entity_id, id)`. It supplies a contiguous ordered scope prefix, unlike the current status index or ID-first unique composite. Do not index/search NIF or add a derived assistant data store. No backfill/data rewrite. Migration must support SQLite and PostgreSQL, create only this named index, and drop only this index on down. Production DDL lock/size assessment and maintenance/concurrent-build deployment choice remain an operator gate; Sol must not run a production migration. A populated up/down test proves records and all existing constraints unchanged. PostgreSQL plan evidence must prove bounded traversal/payload at zero, sparse, 10,000, 10,001 and 200,001 scoped rows, with many other tenants. A LIMIT above a global sort/full scan is not proof of the bound. If safe plans cannot be achieved with this approved index and fixed query, stop for Astra rather than changing search semantics or adding schema casually.
