## Authority and relationship to signed contracts

This executes the exact next handoff in `phase-2-trust-boundary-review.md`. Phase 1 remains signed; Phase 2 remains approved. Neither report is amended. Their execution isolation, capability authorization, immutable fiscal evidence, current AGT projection and PostgreSQL guarantees remain authoritative.

**Explicit extension E1:** the signed Phase 1 “currently supported principals” statement describes humans and scheduled recurrence only. This design adds a prospective **integration** principal for two existing read capabilities. It does not reinterpret an integration as a user, activate agent/delegation authority, or expand a human's permissions. E1 is the only principal extension authorized by this design; until its implementation passes review, machines remain unsupported. The current `ExecutionContext::resolve(User, …)` is never used with an integration's sponsor to impersonate that sponsor.

The current code has useful boundaries: `ExecutionContext` independently reloads authority; `DocumentCapabilities` centralizes scoped reads and `CurrentAgtState`; typed read/list commands validate inputs; the resource exposes ten fields. Its human assumptions are explicit: integer user `actorId`, `User::findOrFail` audit causers, and web session middleware. Those assumptions require a small read-context abstraction, not a parallel fiscal engine. `AppServiceProvider::configureAuditContext` supplies human/system defaults and accepts explicit properties; integration events must deliberately override those defaults and avoid ambient request headers.

## Four separate decisions

| Boundary                 | Meaning                                                                     | Authoritative source                                                                                            |
| ------------------------ | --------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Credential identity      | Which credential of which stable integration authenticated this call?       | Opaque secret verification and current credential/integration records                                           |
| Credential scope         | Which operations has this individual credential been granted?               | Persisted exact allowlist, intersected with integration grant ceiling                                           |
| Execution context        | In which workspace, legal entity and AGT environment may this call operate? | Immutable integration binding, verified entity ownership, exact explicit route context                          |
| Capability authorization | May this principal execute this operation now?                              | Current credential/integration state, current sponsor authority, scopes, context and capability policy together |

For the initial read, allow only when **all** are true: external adapter enabled; authenticated credential active and unexpired; integration not revoked; original sponsoring membership still exists and is active; sponsor still exists, has verified email and confirmed MFA, and is currently Owner or Administrator in that workspace; entity still belongs to the bound workspace; requested context equals the binding; both integration and credential grant `documents:read`; operation maps explicitly to `documents.read`; and resource/query policy permits the scoped read. No permission array from a caller is authority. Role alone, scope alone and possession of a secret alone are insufficient.

Owner/Administrator sponsorship is a deliberate conservative external-grant policy. It does not change the five-role human read policy. Accountant/Billing/Viewer may retain session reads but cannot sponsor or manage an external grant in this slice. There is no owner bypass of scope, environment, expiry or revocation. No action approval is required for these reads; approval/automation IDs must be null, never fabricated.

## Binding, ownership and initial scopes

A workspace owns an integration. One integration has exactly one legal entity and one environment (`homologation` or `production`), fixed for its lifetime. The creator is the initial sponsor and must meet the policy above. The same software serving another entity/environment receives a different integration and credential. No arrays of environments, default workspace, oldest entity or `unresolved` environment. Production **reads of existing records** remain independent of outbound AGT enablement, as signed in Phase 1.

The integration identity survives token rotation and is the future stable principal key; the credential ID identifies the particular secret used. Labels describe software but do not prove vendor, agent, user or delegation identity. No ownership or sponsorship transfer in this slice: revoke and create a newly authorized integration when responsibility changes.

| External scope   | Existing capability permission | Allowed operations                                           | Explicit exclusions                                                                                               |
| ---------------- | ------------------------------ | ------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| `documents:read` | `documents.read`               | Existing safe document detail and bounded list, GET and HEAD | PDF/export, delivery, customer/catalogue data, aggregates, AGT configuration, credentials, every command/mutation |

There is exactly one recognized external scope. Lists and detail share it because the current safe fields and policy are identical. `invoices:read` is not an alias. Reject `*`, `admin`, `read`, `write`, `invoices:write`, unknown values, duplicate entries, case variants and whitespace-normalized aliases. Explicit empty grants deny all reads. No prefix matching, wildcard matching or implicit future scopes. New capabilities require new reviewed mappings; adding a permission elsewhere cannot enlarge this grant.

## Proposed data model — no migrations applied

Use existing model conventions, integer internal keys, public ULIDs and UTC timestamps. Names below are normative domain names; ordinary class naming adjustments are acceptable if behavior remains identical. No Sanctum/OAuth dependency is assumed or authorized.

| Table                           | Proposed fields and constraints                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `integrations`                  | `id`, unique `public_id`; `workspace_id`, `legal_entity_id`, exact `environment`; `name` max 100; `sponsor_user_id` nullable after user deletion, `sponsor_membership_id` nullable after membership deletion; immutable `creator_principal_kind=user` and `creator_attribution_id` UUID snapshot (A1); `revision` positive, initially 1; `revoked_at`, `revoked_by_user_id` nullable, constrained `revocation_reason`; created/updated timestamps. | `integration_scopes`            | `(integration_id, scope)` composite primary key; FK integration restrict deletion; scope CHECK permits only `documents:read`. No row means no grant. Scope reductions increment parent revision; regrant requires a new integration in this slice.                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `integration_credentials`       | `id`, unique public ULID selector `public_id`; `integration_id`; unique `secret_hash` (64 lowercase hex), `hash_version` fixed `sha256-v1`; `created_by_user_id` nullable and immutable `creator_principal_kind=user` and `creator_attribution_id` UUID snapshot (A1); `created_at`, required `expires_at`; `revoked_at`, nullable revoker and constrained reason; nullable `replaces_credential_id`; `last_used_at` nullable. Never a plaintext/encrypted secret column. CHECK expiry > creation, maximum issuance lifetime validated by action. Index `(integration_id, revoked_at, expires_at)`. Replacement reference must belong to the same integration, enforced by composite FK.                           |
| `integration_credential_scopes` | `(credential_id, scope)` composite primary key; credential FK restrict deletion; exact scope CHECK as above. Credential scope immutable after creation; effective permissions can only shrink via integration grant reduction or credential revocation.                                                                                                                                                                                                                                                                                                                                                                                                                                                            |

Sponsor user/membership FKs use SET NULL on deletion; historical actor attribution UUID snapshots remain independently (A1). This avoids preventing existing membership-removal flows and prevents reattachment to a newly created membership. Execution requires both non-null references and checks membership user/workspace agreement, not just FK existence. Integration/entity/workspace and credential-parent/replacement relationships use restricted deletion; no fiscal or audit cascade. Add supporting referenced unique keys only where missing; inspect actual schema first. Do not broaden or replace fiscal indexes.

Revocation reason codes are `owner_request`, `rotation`, `compromise`, `authority_withdrawn` and `setup_failure`; arbitrary free text is not accepted into security audit. Credential metadata also has `updated_at`; changes to it never imply successful use. Every state-changing lifecycle operation on an existing integration requires its expected revision, locks and compares it, then increments it once on a committed change. An already-terminal revocation is a no-op after fresh management authorization: it returns success without a revision conflict or another state-transition event.

Integration and credential lifecycle is derived from timestamps, avoiding contradictory active booleans. Expiry is `now >= expires_at`, not a cleanup-job side effect. Revocation is terminal. At most two live credentials per integration: one current plus one retiring during rotation. Lifecycle transactions lock the integration first, then affected credentials in ascending ID order, re-read authority/revision and enforce this limit. A dedicated creation operation inserts parent/initial grant/first credential atomically. Concurrent rotations/revocation must serialize; no check-then-insert outside the lock. Revoked/expired rows remain evidence, not reusable slots whose identity is overwritten.

Migration proposal: additive integration/credential/grant tables and supporting ownership constraints, plus the narrowly authorized users.attribution_id migration/backfill in A1. No fiscal backfill or automatically generated integration/secret. Test fresh install and populated fiscal upgrade on PostgreSQL and SQLite. Down migration may drop empty new tables; once integration or credential evidence exists, refuse destructive rollback and require forward repair. Disabling the external feature is the immediate code rollback; retain evidence. No production migration or developer `.env` change in the implementation task.

## Amendment A1 — immutable creator attribution (P3A-01 resolved)

**PHASE 3A IDENTITY CONTRACT — RESOLVED.** This narrow review authorizes one attribution-only user identifier and its migration. It supersedes the ambiguous “creator public-ID snapshot” wording. E1, all authorization boundaries and every other Phase 3 decision remain unchanged. No implementation is performed by this amendment.

### Decision and option evaluation

Use **`users.attribution_id`**, an immutable, globally unique random UUID v4, as the source for copied creator snapshots. Keep `users.id` as the primary key and all existing authentication/session/relationship keys. The attribution identifier is hidden by default and is not added to the general public User contract.

| Criterion                                     | Typed internal integer snapshot                                                                                 | Selected attribution UUID snapshot                                                                                                       |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| Stability after rename/state changes          | Stable within the original database identity namespace                                                          | Stable independently of names, email, role, workspace and database sequence                                                              |
| Deletion/recreation and long-term correlation | Requires preserving original database provenance and avoiding ID reuse/remapping to prevent false attribution   | Copied UUID survives deletion; a new account receives a new identity even with the same email or reused integer ID                       |
| Information disclosure/enumeration            | Safe only when strictly internal; accidental publication exposes sequential identifiers and account correlation | Opaque random value discloses neither account sequence nor creation time; still a correlatable identifier, never permission or anonymity |
| Database integrity                            | No new user field, but historical number has no live FK after deletion                                          | One unique immutable field plus independently retained snapshots; live FKs continue enforcing current relationships                      |
| Audit/credential attribution                  | Fits current internal causer IDs                                                                                | Provides durable typed attribution while preserving existing causer IDs and current sponsor checks                                       |
| Future APIs                                   | Would need a later public-identity design before exposure                                                       | Provides a possible future reference, but no field/lookup exposure is approved now                                                       |
| Future agents/workflows                       | Kind tags still required; user ID cannot identify a machine                                                     | Kind tags still required; human attribution UUID cannot identify a machine, delegation or workflow                                       |
| Migration/authentication                      | No backfill; smallest immediate schema change                                                                   | One bounded user-field backfill; no primary-key, login, MFA, social-login or session-key changes                                         |
| Complexity                                    | Fewer current changes, but postpones portable identity semantics                                                | Small additional schema cost; no identity registry, alias service, per-tenant identity or new authentication system                      |

The internal-only option was a defensible minimal workaround, but is not selected: the original contract explicitly needs enduring creator attribution, and an independent opaque identifier avoids binding future evidence to a mutable database namespace. Sequential IDs remain permitted in existing protected internal audit fields; this amendment authorizes no additional external disclosure of them. Random identifiers do not replace authorization or resource scoping.

### Exact fields and meaning

- `users.attribution_id`: non-null after backfill, globally unique across users in this application database, canonical lowercase hyphenated UUID v4 (`xxxxxxxx-xxxx-4xxx-[89ab]xxx-xxxxxxxxxxxx`). Generate server-side using the installed framework's random UUID v4/CSPRNG facility, not ordered UUIDs, ULIDs, email hashes, integer encodings or client values. Global means independent of tenant; it is not a universal identity across independently operated installations. Backup/restore of this installation preserves it.
- Generate once **before insertion** for every new User, centrally in the model creation path so registration, social authentication, factories and internal creation agree. Existing-account login/linking never regenerates it. Raw trusted imports must supply a newly generated valid value; restore may preserve an existing identity. Ordinary request input cannot set or update it. Do not mass-assign it, expose it through route binding, or make it the authentication identifier.
- Both `integrations` and `integration_credentials` receive **`creator_principal_kind`** (non-null, CHECK exactly `user`) and **`creator_attribution_id`** (non-null UUID). The lifecycle action copies the freshly authorized human creator's `attribution_id` at creation, in the same transaction as the record and its audit. These are snapshot columns, **without a FK to users**. They are not unique across records: one creator may create many integrations/credentials. No name/email snapshot is needed.
- The integration's existing `sponsor_user_id` is also its initial creator relationship because sponsorship transfer is excluded; retain `sponsor_membership_id` for live authority. Each credential's `created_by_user_id` identifies its own issuing/rotating human and may differ from the integration sponsor. These live FKs retain the approved SET NULL deletion behavior. Never substitute the integration creator's snapshot for a later credential creator's identity.
- Protect user attribution IDs and both creator snapshot fields against updates through model methods and database update guards on PostgreSQL and SQLite; guards must allow deletion and approved SET NULL updates to **relationship** columns. Unique/non-null UUID validation and kind CHECKs protect shape, while trusted lifecycle logic proves the snapshot source. Snapshot immutability does not require preventing deletion of the creator.
- Include the snapshot pair in protected integration/credential lifecycle audit properties; record the actual human event actor's typed attribution UUID for rotation/revocation/grant changes without rewriting the original creator. Existing human integer causer/authority fields stay compatible. Machine request actor remains the Integration with its own public ID; the human snapshot never grants machine authority. No retroactive rewrite of historical audit events or fiscal evidence.

**Creator relationship** answers whether the original user record still exists. **Creator snapshot** answers which stable application principal created the record at that time. A deleted or anonymized principal can remain distinguishable in evidence without retaining their name/email or making a currently authorized user resolvable from the snapshot. Never recover a live sponsor by searching for a matching snapshot.

### Account state and disclosure

Rename, email change, MFA changes, role changes and removal from a workspace leave attribution IDs/snapshots byte-identical. Current authority continues to use live user/membership checks. `DeleteUserAccount` already either removes a user or anonymizes a retained row; preserve the UUID on anonymized rows, and retain copied snapshots when a row is deleted. Both paths remove membership authority and must deny integration execution as already specified. Registration after deletion, even with the same email, produces a new UUID. Existing account-retention and workspace-deletion restrictions are not redesigned here.

Hide `attribution_id` in default User serialization and exclude all snapshot/relationship IDs from the external read API's existing ten-field whitelist, error responses and normal Inertia user payload. Lifecycle models must not expose creator snapshots through incidental serialization. Protected audit may retain the UUID under existing access/retention rules; it remains pseudonymous data, not anonymization or permission to retain personal data indefinitely. No public user lookup, token subject, scope, URL parameter or support search is introduced.

Future API disclosure needs a separately approved resource/minimization contract: it may expose a typed opaque attribution reference only where warranted and authorized, never the internal sequential ID. A global UUID can correlate a person across tenants, so knowledge of it must not unlock user profiles, cross-tenant lookup or audit data. A future agent/workflow requires its own principal kind/identity and delegation contract; it cannot reuse a human attribution UUID as authority.

### Narrow migration authorization

A1 extends the prior integration-only migration boundary solely to adding/backfilling/finalizing `users.attribution_id`, its uniqueness and update guard, plus the creator snapshot columns in the already-approved new tables. Do not add `users.public_id`, change existing primary/foreign keys, migrate sessions or add a public User resource.

Run the user attribution migration before integration tables become usable. On a guarded disposable database, prove the following maintenance-mode rollout: pause user creation/updates for deployment; add a nullable UUID column and unique index; backfill only null values in bounded primary-key chunks using server-generated UUID v4 values; preserve all existing non-null values, passwords, timestamps, email, user IDs, memberships and fiscal bytes; verify valid/non-null/unique values; finalize NOT NULL and immutable-update guards. Use the installed Schema APIs, PostgreSQL's native UUID type and an equivalent validated SQLite representation. No database UUID extension is required. Do not regenerate an assigned value on retry. A duplicate-generation failure retries that assignment with fresh randomness within the bounded operation or aborts safely, never overwrites another user.

PostgreSQL transactional migration failure rolls back consistently; any staged retry must preserve committed assignments. SQLite rebuilds must preserve every incoming FK/index and validate foreign-key integrity. Deployment must remain in maintenance until code generating IDs on new users and final constraints are both present; no unsupported rolling-deploy guarantee. Existing users, including retained anonymized rows, all receive identities. Backfill assigns an attribution reference now; it is not evidence of the user's historical creation timestamp. Previously deleted users are not recreated and historical audit rows are not guessed/backfilled.

Rollback may remove this new field only while the new integration/credential evidence tables are empty and no new attribution audit evidence has been recorded; otherwise refuse and use a forward repair. The rollback guard must inspect evidence, not assume safety because integration tables were dropped. Empty-schema rollback/reapply remains testable; production rollback must not mint a second identity for already referenced users. Keep the existing populated integration rollback refusal. No migration is applied in this review.

### Additional acceptance criteria

1. Populated PostgreSQL and SQLite upgrades assign distinct valid UUIDs to all existing users while preserving all original columns, auth/session/membership links and fiscal evidence; retry retains assigned values, empty rollback works, evidence-bearing rollback refuses.
2. 6. User serialization, Inertia identity payloads, session/external document responses and errors omit the new identifiers. No lookup by attribution UUID or new public user route exists. Protected lifecycle audit contains correct typed references, while human/machine actor attribution remains distinct. Run all previously mandated gates in the subsequent implementation.

## Credential format and lifecycle

Opaque bearer format: `fcr1.<credential-public-ULID>.<secret>`, where secret is 32 bytes from the operating system CSPRNG encoded as 43-character unpadded base64url. Generate on the server only; never accept client-chosen secrets, truncate randomness, derive secrets from IDs, reuse a revoked secret or use JWT claims as a substitute for current database authority. Prefix and selector are not secrets but should still be omitted from public errors. Parse exact bounded ASCII grammar before lookup; header length limit 256 bytes.

Store SHA-256 of the **entire canonical bearer string**, with an explicit hash version, and compare digests using constant-time comparison. High-entropy random secrets are not human passwords; a one-way digest is appropriate here. No reversible encryption, recoverable secret, secret suffix, “show existing secret”, or password reset flow. Digest and raw bearer must be hidden from serialization, query logging, audit, exception dumps, telemetry and support exports. For a structurally valid unknown selector, do a dummy same-algorithm comparison and return the same invalid-credential error; do not promise mathematically identical network timing.

Initial credential expiry defaults to 30 days and must be explicitly bounded between one hour and 90 days from creation. No non-expiring credentials or refresh tokens. Rotation creates a new random credential with the same or narrower grants and the same immutable integration binding. New expiry independently obeys the 90-day bound. Its predecessor's expiry becomes the earlier of its original expiry or 24 hours after rotation; an immediate-revoke option must be available. Rotation cannot revive an expired/revoked credential or revoked integration. If two live credentials already exist, another rotation conflicts until the retiring one is revoked/expires. Expired credentials can be replaced through a freshly authorized human management action, not by authenticating with them.

Creation/rotation returns plaintext **once**, only after successful transaction commit, to the authorized management action caller. A future management UI must use an explicit reveal/copy response with private/no-store, no URL/query/flash/session storage, no email and no persisted response replay. Lost response means the secret cannot be recovered: revoke the undisclosed credential and create another. A stale repeat must conflict using the integration revision rather than silently mint another secret. Do not add a business idempotency ledger that stores plaintext. The initial backend handoff tests this lifecycle but exposes no management endpoint/UI/CLI and provisions no real credential.

Future management transport must require an active verified/MFA Owner/Administrator in the bound workspace, a current unexpired work session, non-impersonated human identity, CSRF protection and recent password confirmation (within five minutes) for reveal/creation/rotation. It must pass a trusted management context; these checks cannot be caller-supplied booleans. Owner/Administrator may revoke any integration in their workspace even when its sponsor is unavailable. Revocation is idempotent, audited once as a state transition; an additional request audit may describe repetition. A management caller cannot use integration credentials to mint/rotate/revoke credentials. Public management UX is a separate bounded handoff requiring review.

Persist `last_used_at` only after an authorized successful capability read has been audited, including HEAD. Update monotonically using the later existing/new timestamp, never touching expiry, grants, revocation or secret. No client timestamp. Failed authentication, denied resources and throttled requests do not count as successful use. This is telemetry, not authorization or evidence that a secret is uncompromised. The next slice does not store last-used raw IP/user-agent in the credential table; trusted network/security telemetry has separately controlled retention.

A sponsor becoming inactive, losing the required role, verification or MFA immediately makes execution ineligible at the next authority check. Restoring those prerequisites may resume an unrevoked integration whose original membership still exists; this is deliberate live-authority evaluation, not terminal revocation. Removal/recreation of membership cannot resume it. Security incidents must use terminal revocation, not temporary role changes. No automatic sponsor substitution.

## Stateless authentication and request-resolution flow

The existing `/api/v1/...` session routes remain unchanged. Proposed external routes use a separate prefix `/api/integrations/v1/workspaces/{workspacePublicId}/legal-entities/{entityPublicId}/environments/{environment}/documents` and its `/{documentPublicId}` detail. This is a separate adapter to the same two capabilities, not a new business surface. GET/HEAD only. Feature flag defaults off; disabled routes return safe 404. No cookie fallback or “session OR bearer” guard. Do not advertise an OAuth token endpoint, browser login or generic token-management API.

1. At the external boundary initialize a fresh server UUID request/correlation ID and a clean request-local audit context. Apply TLS/host/proxy and header-size policy; reject plain HTTP at ingress without reflecting secrets or relying on a redirect. Trust forwarding headers only from configured proxies. Do not start a Laravel session, decrypt cookies, use `Auth::login/setUser`, run work-session/Inertia middleware or select a browser workspace. Ignore cookies entirely; they cannot add or subtract machine authority. Ignore browser impersonation cookies because they are not processed; explicit delegation/impersonation/act-as headers or parameters are rejected.
2. Apply a pre-auth network limiter. Accept exactly one Authorization header with the Bearer scheme (scheme case-insensitive, token bytes case-sensitive). Reject duplicate/combined credentials, malformed tokens, query/body credentials and alternative auth mechanisms. No Basic auth, token introspection response or challenge revealing selector existence. Do not log raw request bodies/headers on any of these paths.
3. Resolve the selector on the authoritative database, compare the digest and load current integration/credential state. Never load a user session to identify the principal. Invalid, absent, expired, revoked or disabled credentials/integrations produce the same 401. If database/auth infrastructure is unavailable, return sanitized 503, never session fallback or cached authority.
4. Validate explicit route syntax. Resolve only the bound integration's workspace/entity and compare canonical route IDs and enum to that binding before looking up any unrelated target. Wrong well-formed workspace/entity/environment returns uniform 403 whether it exists or not. Normalize accepted ULID letter case consistently for comparison; neither case nor a selector can change binding. No global entity enumeration. A scope/sponsor-policy failure also returns generic 403 without exposing which prerequisite failed.
5. Resolve a private, immutable integration read context from a non-serializable authenticated proof produced by the verifier. The proof/context carries stable IDs and correlation, never raw bearer bytes or a user impersonation. Apply authenticated quotas. Do not accept credential ID plus arbitrary permissions as a public context factory.
6. Invoke the existing typed command and `DocumentCapabilities`. At the capability boundary, re-read current credential/integration/grants/sponsor/membership/entity in one consistent primary-database authorization snapshot; validate all conditions again. Reusing a previously valid context never bypasses revocation. No replica, positive authority cache, queued permission snapshot or browser state.
7. Reuse the existing scoped query, safe serializer and `CurrentAgtState`. Audit before releasing data, update successful-use metadata, then return the existing envelope with fresh server request ID, explicit public context and private/no-store. HEAD uses the same checks/audit/quota and emits no body. Do not return secret/grant/sponsor IDs in document responses. Error handling must cover the exact external root and descendants, and audit failure must never expose debug details.

**Revocation linearization:** authority is evaluated at the capability's final authorization snapshot. A revocation committed before that snapshot must deny the request; a read already authorized before the commit may finish. No claim that already transmitted bytes can be recalled. Every subsequent check must see revocation immediately on the primary. This avoids holding a tenant-wide exclusive lock while reading documents and defines a testable read-only race. Future consequential operations require their own transactional authorization contract.

## Minimal shared-capability extension

Introduce a read-only context contract in the existing fiscal/application area with methods for workspace ID, legal entity ID, environment, correlation ID, `authorize(permission)`, safe audit metadata and audit causer. Existing human `ExecutionContext` implements it through accessors without changing its factory, readonly data or human/scheduled authorization. New private-constructor `IntegrationReadContext` implements it with the verifier/resolver above. No general pluggable principal registry or arbitrary action dispatcher.

Widen only `DocumentCapabilities::read`, `readDocument`, `listDocuments` and their private query helper to that read-context contract. Replace their hardcoded `User::findOrFail` audit causer with the context's trusted causer: User for current human calls, Integration for machine calls. Keep the human `approveRecurring(ExecutionContext, …)` signature and behavior unchanged. Integration `authorize` denies every permission other than `documents.read`, even if corrupt/unknown grants or a direct internal call request more. Existing `read(context, publicId)` remains compatible.

The integration context must not retain a sponsor as `actorId`, call human `resolve` or permit downcasting to a human context. The sponsor is a current authority constraint and separately attributed human, not the executing actor. Machine read context factories remain non-public to request data, and tests invoke the same verifier/resolver as HTTP without needing HTTP itself. Trusted application PHP is not an adversarial plugin sandbox; do not invent reflection-based tool execution.

## Audit, logging and correlation

Use existing activity infrastructure with explicit typed identity. Integration read events have `actor_kind=integration`, `principal_kind=integration`, stable integration public/internal reference, credential reference, real/effective principal kind and ID both identifying that integration, `human_actor_id=null`, separate `authority_user_id` sponsor, validated workspace/entity/environment, capability/version, operation UUID, server request/correlation ID, outcome, timestamp and safe resource public ID (detail) or bounded page/result metadata (list). There is no impersonation, delegation, approval, workflow or agent identity. Existing human audit fields remain backward compatible; do not overload an integer user ID with an integration ID without its kind.

Lifecycle events distinguish created, credential-created, rotated, credential-revoked, integration-revoked, grant-reduced and denied. Human management actor is the causer of lifecycle changes; integration is the subject. Record before/after grant/revision/expiry changes, reason codes and public references, never secrets/hashes. Successful lifecycle mutation and audit commit atomically; audit failure rolls back and suppresses reveal. Read audit failure releases no data, returns safe 500 and reports a redacted internal failure. Last-used update must not overwrite a concurrent revocation.

For unauthenticated failures record a bounded security event with operation/request ID, generic internal reason and no claimed tenant/actor/selector; do not write a tenant-attributed event based on an unverified token. For authenticated denials use only verified integration identity/binding, never requested foreign identifiers. Rate-limited anonymous traffic may be aggregated in protected security telemetry to resist audit amplification; authenticated capability success/denial is durable. A security telemetry outage must not turn a denial into success.

Server IDs are fresh UUIDs and are never supplied by the client. A client may send `X-Client-Request-ID` matching `[A-Za-z0-9._-]{1,64}` for diagnostic linking; reject invalid values as 422 only after authentication. It is optional, stored separately and never an idempotency, authorization, throttle or server-correlation key. Ignore incoming `X-Request-ID` for server identity. No distributed trace/causation authority is accepted in this slice.

Integration events must suppress the provider's raw ambient user-agent default; user-agent is untrusted and may contain a secret. Likewise prevent URLs/query strings, Authorization/Cookie values, secret hashes, model attribute dumps and exception request snapshots from reaching app/proxy/APM logs. Redact by field name and token-prefix pattern as defense in depth; test both. Public errors contain no raw framework message, SQL, table/constraint names, paths or traces. Protected audit access is workspace-aware; do not add a public audit endpoint. Retain lifecycle/security evidence under the existing governed retention process; no new deletion job or claimed legal retention duration.

## Errors, enumeration and limits

Use the existing `error: {code, message, ...}` / `meta: {request_id}` structure and safe Portuguese messages. Add explicit 503 service-unavailable handling for the external adapter. Successful data/field sets, filters and pagination remain Phase 2's. Do not change the existing session error contract.

| Status    | External behavior                                                                                                                                                                                 |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 401       | Missing/malformed/unknown/wrong/expired/revoked credential or revoked integration: indistinguishable `AUTHENTICATION_REQUIRED`; `WWW-Authenticate: Bearer`, no descriptive token-status challenge |
| 403       | Valid credential but insufficient current authority/scope or any well-formed out-of-binding context: `FORBIDDEN`, no target lookup or existence hint                                              |
| 404       | Unknown external path, disabled adapter, or missing/foreign/sibling/wrong-environment document inside the authenticated binding: `NOT_FOUND`                                                      |
| 405       | Unsupported method on a known route; safe Allow header, never a command execution                                                                                                                 |
| 422       | After authentication: invalid context syntax, unsupported filters, act-as fields or client correlation syntax; safe field errors without echoing supplied values                                  |
| 429       | Quota exceeded: `RATE_LIMITED`, bounded integer Retry-After; no per-tenant counts/identity disclosure                                                                                             |
| 500 / 503 | Safe internal/audit error / dependency unavailable; no data or debug output                                                                                                                       |

HEAD matches GET's status, auth, headers and audit but never has a body, including errors. Distinguishable invalid syntax is not an existence oracle; all well-formed unauthorized context IDs share the same denial. No secret validity detail, credential listing or resource count before authorization.

Use atomic shared fixed-window limits: pre-auth 120 requests/minute per trusted network IP; authenticated 60/minute per stable integration; additionally 300/minute per workspace across integrations. Every GET/HEAD attempt reaching a bucket counts, including later denied/invalid requests. Consume all applicable authenticated buckets; reject if any is exhausted, use the longest applicable retry interval. Rotation and multiple credentials share the integration budget; client-request IDs and route IDs never define identity. Human session limits stay unchanged. Keys use internal stable IDs and a namespaced one-way digest of network identity, not bearer bytes or public request values. No per-process array/file cache in a multi-worker deployment.

The implementation may use the existing database cache with atomic framework locks/counters, verified against the installed version and PostgreSQL under concurrent workers. No new dependency. It must fail closed with safe 503 if the configured shared limiter is unavailable or unfit for production, rather than silently using per-process limits. Thresholds are explicit initial operational defaults; changing them cannot change authorization. Trusted-proxy, TLS and multi-worker shared-store configuration are deployment gates. CORS is not authentication: no cross-origin browser client support is introduced; browser-embedded secrets are outside the intended server-to-server contract.

## Compromise response and future compatibility

On suspected token disclosure, a verified non-impersonated workspace administrator immediately revokes that credential; uncertain breadth means revoke the whole integration. Disable the external adapter globally for systemic compromise. Invalidate no fiscal facts and do not delete evidence. Review protected read/audit records by integration, credential and time, including successful use after suspected disclosure; notify affected owners through the separately authorized incident process. Create a replacement only after the recipient's storage is secured. Never rely on changing browser passwords, removing cookies or waiting for expiry to invalidate a machine credential.

A copied bearer secret authenticates as its integration until revoked/expired; vendor labels, source IP and user-agent do not prove who physically possesses it. TLS, secure client-side secret storage, constrained grants, expiry and revocation limit this risk. No claim of sender-constrained credentials, mTLS, OAuth consent, delegated end users or autonomous approval.

Stable integration IDs and explicit context permit a future external software or agent client to reuse HTTP syntax, but this phase grants no agent identity or authority. A future agent requires a separately approved principal/delegation/approval contract; user-supplied `agent_id`, `on_behalf_of` or workflow IDs cannot alter attribution. Customer/catalogue/analytics reads, delivery, exports and all mutations remain later bounded contracts. Read requests need no consequential idempotency ledger; Phase 1's future ledger remains unchanged.

## Acceptance and adversarial criteria

The Sol implementation must prove these properties, not merely route success:

1. Token format/entropy source, strict parser and digest comparison; no recoverable secret field. Wrong/unknown/revoked/expired credentials have identical status/body shape. Plaintext absent from DB, logs, audit, snapshots and serialized models; one-time reveal lost response cannot be replayed/recovered.
2. Credential ownership and lifecycle action checks are independent of HTTP. Reject non-admin, foreign admin, expired work session, stale recent confirmation, support impersonation and machine callers. Rotation cannot expand scope/binding, revive a revoked integration or exceed two live credentials. Concurrent create/rotate/revoke plus stale expected revision yields one valid committed transition and atomic audit.
3. Cookie-only external call is 401; valid bearer plus another user's session still acts only as its integration; invalid bearer plus valid session stays 401. Browser workspace changes, session impersonation and cookie order cannot change machine scope. Explicit act-as input rejected. Existing session API continues to work unchanged.
4. Cross-workspace, sibling entity, wrong/unknown environment and valid-but-ungranted context IDs deny uniformly. Own/foreign missing document returns same 404. Upper/lowercase valid ULID input resolves consistently. Quarantined records never appear.
5. Forged scope arrays, wildcards, arbitrary principal kind, guessed credential IDs, sponsor IDs and ambient Context cannot construct authority. Direct shared-capability invocation after credential/integration revocation, expiry, sponsor downgrade/removal, lost verification/MFA or grant reduction denies. Membership delete/recreate does not resurrect sponsorship. Test deliberate temporary-ineligibility/restoration semantics separately from terminal revocation.
6. PostgreSQL process barriers prove revocation-before-final-snapshot denies; already-authorized read may complete; all subsequent checks deny. No replica/cache staleness. Independent rotation/revocation and monotonic last-used races cannot restore revoked access. Composite ownership/replacement constraints reject cross-integration/entity links.
7. Integration read audit uses integration causer/kinds and separate sponsor; management audit uses the actual human. Missing/failed audit withholds successful data/secret, rollback is complete for lifecycle actions. Foreign context and unverified selector never pollute tenant audit. Correlation server IDs are fresh; client IDs are separate and bounded. Provider defaults cannot label integrations human/system or leak user-agent/token data.
8. Exactly two external GET/HEAD routes, disabled by default; every unsupported verb safe. Both methods enforce current permission, same 10-field schema, status provenance, no mutation/outbound work, bounded pages/filters and constant query count. Error root/descendant/debug/audit-failure cases retain safe envelopes and no-store; HEAD bodies empty.
9. Concurrent requests over multiple processes share quotas; two credentials and rotation cannot multiply integration quota, multiple integrations hit the workspace cap, untrusted proxy headers cannot spoof network identity. Shared-store failure returns 503. Over-limit requests do not perform document work or mark successful last use.
10. Populated migration preserves fiscal hashes/row counts and existing sessions. Rollback of empty new tables works, populated rollback refuses. OpenAPI describes separate bearer security, explicit binding, only these routes/fields, HEAD, safe errors, retry headers, no cookies and no credential issuance API.
