# Phase 7B.3c-1 — provider verification and authenticated active lifecycle

Date: 2026-10-09. **Design only; ready for one bounded implementation followed by independent review.** This document does not authorize live verification, provision customer grants, enable inference, or implement gateway credential consumption.

Current production inference and inference egress are hard-disabled in `config/assistant.php`. The catalogue is VAP-only; it does not supply a customer grant. Existing legacy acknowledgement/admission code still needs the frozen package's narrowly specified coexistence adaptations before this runtime increment is complete. Accepted schema tests prove structural enforcement, not authenticated provider verification.

## 2. Meaning and scope

**ACTIVE = PROVIDER-VERIFIED**, meaning that the exact stored credential successfully authenticated one approved metadata lookup, returned the exact reviewed model identity and required account-routing claims, and passed fresh local promotion checks. It does not mean Messages/inference permission, paid balance, ownership of an account, exclusive upstream workspace access, legal compliance or authorization to consume customer secrets in `VapAiGateway`.

Three separate authorities remain: encrypted storage; provider observation and local active lifecycle; future inference authorization. Only customer-managed Anthropic API-key verification is designed here. VAP credentials remain under separate operational custody; never copy them into tenant storage. OpenAI is 7B.4; custom/compatible destinations are 7B.5. No fallback provider, model, account or ownership mode.

## 4. Authorization and layered switches

Every admission, JIT read, send prerequisite and promotion repeats primary-database authorization: exact actor and original active owner membership, verified email, confirmed MFA, work session, POST/CSRF, reauthentication within 300 seconds, no delegation/impersonation, no bearer, queue or CLI initiator. Explicit public workspace and entity resolve independently; entity belongs to workspace; environment is exactly production; deployment matches. Mutable browser selection is irrelevant. Emergency disable authority cannot verify, decrypt or promote.

Require current customer-managed mode and matching selected profile/connection; enabled non-revoked connection; exact pending, unexpired, non-destroyed credential; matching revisions, wrap revision, selection and active generation. Fresh operator/owner approval, entitlement, account grant, disclosure/acknowledgement and immutable profile/verifier digests must all match and remain valid. Bind the complete sorted authority-reference set, not only a top-level enabled bit. An ABA disable/re-enable or replace/reselect advances revisions and invalidates the original operation.

Add default-false verification-wide and Anthropic-verification egress switches, separate from inference switches. Independent purpose-specific operator approval remains mandatory; a config boolean cannot substitute. Root emergency/circuit denial overrides approval. Deployment-local policy/trust configuration must remain immutable during an operation; a rolling configuration change requires closing verification admission and draining requests before replacing manifests/keys. DB policy/control changes advance the signed revisions under root locks. Missing signer, custody, policy, mapping, disclosure, positive quota or complete approval makes verification unavailable before secret access/DNS. Unrelated deterministic assistant use may remain available; no fallback verification mode.

## 5. Exact Anthropic wire contract

The normative operation remains VC1's `anthropic-model-metadata-v1`:

- `GET https://api.anthropic.com:443/v1/models/{exact-approved-model-key}`. Path component comes only from the immutable code manifest, safely encoded as one component. No query, request body or runtime model discovery.
- Exact fixed headers: `anthropic-version: 2023-06-01`, `Accept: application/json`, `Accept-Encoding: identity`, `x-api-key` from the restricted plaintext scope, and `anthropic-workspace-id` from the reviewed account mapping. No caller headers, cookies, User-Agent content, tracing baggage, business IDs or question.
- Exactly one exchange, no redirect, proxy, retry, connection reuse or content decompression. HTTPS only, peer/hostname verification, TLS at least 1.2, approved host/SNI, port 443. Resolve the complete bounded address set; any prohibited/private/reserved result denies; pin one approved public address and compare actual peer address/port in cURL prerequisite before request bytes.
- Entire operation at most 10 seconds by monotonic clock, including local work. DNS at most 1 second, 16 addresses and 4,096 bytes; DNS+connect/TLS at most 2 seconds; wire at most 8 seconds and always bounded by remaining operation time. Each local transaction lock timeout at most 250 ms, statement timeout at most 1 second and remaining deadline. No automatic transaction retries.
- Header aggregate 16 KiB, single line 4 KiB, at most 64 fields; body 64 KiB; JSON depth 8. Enforce during reception, before allocation growth. Reject extra final blocks, folded/control-bearing/ambiguous headers, duplicate authority headers, compressed content, duplicate JSON keys, invalid UTF-8, trailing content and incompatible media type. Optional UTF-8 charset on `application/json` is permitted. Ignore unknown bounded metadata; never persist or display it.
- Success requires exactly HTTP 200, validated JSON object with `type=model`, exact approved returned `id`, and exactly one valid organization and workspace claim matching independent account mapping. Organization is canonical UUID; workspace is `wrkspc_` followed by 1–120 ASCII alphanumerics. No alias-target substitution, null/default workspace inference or credential-prefix guessing.

This proves authenticated visibility of the approved metadata identity and account routing only. It does not prove inference access, billing suitability or model readiness. If a real endpoint omits required claims, fail `account_context_unproven` and return for Astra review; do not use an Admin API or Messages fallback. The current `claude-haiku-5-5` manifest string is not altered or declared available to a real customer.

Reuse the security logic of `AssistantProviderTransport` through the narrow extraction already permitted by VC1, with differential legacy tests. Do not call its POST/Messages entry for verification. Any extraction must retain legacy options, DNS subprocess limits, actual-peer validation and FPM behavior. No general URL fetcher. Laravel AI SDK 0.11.2, cached `AiManager`, Laravel HTTP, Guzzle history/retry middleware and SDK inference methods are not the approved verification path.

## 6. Plaintext custody and lifetime

Admission reads metadata only. After it commits, the verifier claims its one-use request handle, enters a short canonical transaction, freshly checks authority, reads only the exact bound envelope through raw prepared PDO, reconstructs the immutable binding and authenticates the existing AES-256-GCM wrapped-DEK/payload structure. Use the existing KEK allowlist/private-file rules and bounded parser; no APP_KEY fallback, Eloquent casts, new envelope format or call to `inspectForStorageTest()`.

Plaintext exists only from that restricted decryption until the synchronous fixed transport finishes or aborts. It is transient private state marked with `SensitiveParameter`, nondumpable and nonserializable, and never available in an application result. Release DEK, key, plaintext, constructed headers, response buffers, cURL handle and closure references in `finally`, including exceptions, timeout and disconnect. It does not enter SQL parameters, query listeners, models, Context/hidden Context, queues, cache, session, events, audit, logs, exceptions, SDK configuration or persistent clients. Do not toggle global query logging around concurrent sensitive queries; direct prepared PDO avoids the application query-event boundary.

PHP/cURL may retain copies until memory reuse: this is bounded reference retention, not guaranteed memory zeroization. Core dumps, APM argument capture, profilers, HTTP debug, cURL verbose/header dumps and trace baggage must be disabled for the production verification path and checked in deployment rehearsal. No secret fingerprints or fragments in telemetry. Raw thrown transport errors are discarded, not chained or reported. Redaction tests use distinct key/DEK/envelope/body/header sentinels.

No singleton/static issuer, receipt-key cache, secret-bearing SDK manager or shared request registry. Do not enable Octane, queue verification or other long-lived-worker execution. Sequential A→B→A and interleaved-fiber isolation tests are mandatory even for FPM; separate operational review is required before long-lived worker support. No request handle survives a fork because original PID is checked.

## 7. Three-phase protocol and receipt authority

```text
Owner POST (future thin entry; not exposed by this increment)
 → exact request/context + fresh owner authorization
 → A: canonical locks, policy/CAS, quotas, attempt + allocations + required audit
 → commit/release
 → short fresh JIT transaction → restricted decrypt [PLAINTEXT BEGINS]
 → release locks → DNS + pinned TLS
 → short send prerequisite: fresh checks + send-authorized audit/commit
 → one bounded GET → strict typed observation → close/release secret [PLAINTEXT ENDS]
 → private successful path registers one promotion identity
 → C: claim/remove identity, canonical locks, complete freshness check
 → private canonical receipt signing with FINAL disposition
 → matching attempt finalization + atomic active rotation + required audits
 → commit → safe result
```

B produces the trusted in-memory observation, not an earlier redeemable durable receipt. The final authenticated receipt includes finalized time, disposition and committed generation, so its MAC is minted in C. This is the frozen refinement of “evidence before promotion”: signing an incomplete receipt in B or updating its disposition later is prohibited.

The registry uses object identity, not merely UUID equality. It binds exact context and HTTP request objects, original actor/membership, PID, current fiber (including main-thread identity), attempt/operation IDs, captured snapshot and deadline. It is private to the session, strongly bounded to this single operation, removed on claim and cleared on exit. Cloning, serialization, forged DTO construction, valid persisted MACs, another container instance or a copied object in another PID/fiber cannot register or consume authority. Even rollback cannot restore the permit. No DB flag or persisted receipt creates a registry entry.

The final send transaction is the linearization point: if revoke/disable wins first, send is forbidden; if send authorization commits first, one request may still transmit before a subsequent revoke. There is no promise to unsend network bytes atomically with PostgreSQL. Mark “authorized/possibly transmitted,” not “provider received.” Revocation still defeats later promotion. Recheck remaining time after prerequisite commit; no retry after an ambiguous interruption.

## 8. Receipt encoding, key custody and history

Use the exact 47-position array, types, sorting, domain prefix, decimal strings, nulls and UTC microseconds from the frozen evidence's `canonicalization.field_order` and R3 vectors. No additional fields or reordered encoding. Authority references are bounded to 16 and sorted by the frozen kind/ID order; serialized input is at most 8,192 bytes. HMAC-SHA-256, domain prefix `facturac:tenant-ai:verification:v1` followed by one LF, and constant-time `hash_equals` remain mandatory.

Binding groups are schema/issuer/evidence/attempt/deployment/realm; exact stored workspace/entity/environment; connection/credential/version/creation/wrap; expected settings/connection/selection/prior and proposed generation; actor A1/original membership; profile/digest/provider/family/endpoint/verifier; complete authority references/owner approval/account mapping/disclosure/acknowledgement/selection and entitlement revisions; observed organization/workspace/claim strength/model/outcome; admitted/send/observed/finalized/expiry/disposition/committed generation/key ID. No group is inferred from a mutable browser/session or accepted solely because present in DB.

Public IDs copy **EXACT STORED BYTES**, matching `^[0-7][0-9a-hjkmnp-tv-z]{25}$`; no LOWER, UPPER or case-insensitive binding. Internal membership ID stays internal evidence. Receipt UUID is the one-use evidence identity; no extra nonce column is required. Database evidence uniqueness, terminal immutability, exact deferred reciprocal binding and active generation complement the private runtime registry; SQL does not validate MACs.

Dedicated 32-byte random signing material is supplied through a protected canonical private file, separate from every KEK, provider key, APP_KEY and their files/allowlists. Configuration contains only reviewed IDs/paths/validity and deployment/policy binding, never raw key bytes. Reuse the custody checks: canonical absolute private root outside all served/symlinked directories, no group/world writable ancestors, regular non-symlink mode-private bounded file, inode/device continuity across open/read, exact length. Unknown ID cannot choose a path. Missing/unreadable/misbound key denies before admission/decrypt; no generated default.

Normal rotation: close/drain verification, install a new independently generated protected key and immutable trust entry, switch the active signing ID, retain old IDs as verify-only for existing authentic active history, then reopen only under separate approval. A verify-only historical key is not a retired/untrusted key. Removal or compromise makes dependent active history unusable; no resigning/backfill from DB. Reconciliation/reverification needs a separately authorized flow. Compromise response closes egress, withdraws trust, disables affected local authority and investigates metadata; host/key compromise can forge MACs and is not solved by SQL. Test keys and `offline_fixture` realm never appear in production trust; production requires `provider_tls` independently of MAC validity.

Promotion expiry is the earliest of observation+5 seconds, operation+10 seconds, credential/profile/approval expiry and current authority validity. Check both monotonic time and primary DB time under locks. Historical committed evidence remains evidence after expiry; expiry prevents new promotion, not retroactive erasure. Verify old active receipt's MAC, stable tuple, promoted disposition and activated generation before rotation; do not incorrectly require its historical admission revisions to equal current revisions forever.

## 9. Accounting and duplicate suppression — no invented charge

**CR1 amendment notice:** CR1 (§18) clarifies global actor scope and adds its mandatory shared lock; other accounting rules remain unchanged.

The frozen §13.7 rule is retained literally: each admitted probe reserves the selected immutable profile's positive `reservation_micro_usd` and output envelope. `ai3c_check_attempt` compares them exactly to the profile. These are nonrefundable conservative local capacity reservations, **not actual provider charges**. The existing VAP profile's 552,816 micro-USD is not automatically copied into verification and its `reservation()` method is not a verification price calculator.

For any future real customer profile, the verification manifest must explicitly approve this operation's conservative reservation, equal to that profile's frozen reservation, and provide a separately approved provider-specific request-cost ceiling no larger than it. Without authoritative cost-bound evidence, admission stays unavailable. This is a provider-specific cost-bound strategy with an explicit local reserve, not zero-cost admission. Neither a successful GET nor absent usage fields proves free service. No new numerical price is invented here. An independently approved reservation different from the selected profile, or zero reservation, would require a frozen-design review; implementation must stop rather than alter the equality/positive CHECK.

Actual input/output tokens and money remain NULL; body bytes are zero, token estimate NULL. Successful metadata observation finalizes accounting as `usage_unknown` with verification outcome `provider_authenticated_model_visible`. Unknown counters advance once; no reserve refund on unsent/failure/timeout/success/cancellation. Five shared attempt/output windows plus two customer aggregate and two customer account money windows use the one existing ledger and immutable allocations. Overlapping windows are ceilings, never summed as payable money. Preserve checked integer arithmetic and legacy liability reconciliation.

Independent verification limits under primary root locks: one unfinished admitted probe per connection; one admission per trailing 60 seconds per connection; five per trailing 3,600 seconds per workspace; five per trailing 3,600 seconds per actor A1 across workspaces. Use exact partial indexes and LIMIT 1/5 probes, not unbounded counts. Stable connection quota bounds each credential; rotation/replacement cannot reset it. Provider-wide limits are the approved provider/account budget controls plus deployment shared ceilings and emergency circuits, not a newly invented per-provider counter. No approval means no available provider budget. Workspace/actor/shared ceilings defeat connection or actor churn.

Future UI duplicate clicks encounter the same current-state CAS, unfinished-attempt unique constraint and cooldown. No client idempotency key causes resend; an authorized status lookup can return the existing safe operation status. Same terminal finalization is no-change, divergent replay fails. 429/5xx, timeout and malformed results require a new explicit owner action after normal limits, never automatic retry/backoff. Provider Retry-After is not interpreted as authority or an instruction to sleep.

## 10. Canonical transaction order and active lifecycle

**CR1 amendment notice:** For Phase A admission only, CR1 (§18) prepends the actor advisory lock to the row-lock order below. Later phases retain the existing order without CR1.

Primary PostgreSQL READ COMMITTED; one attempt per transaction, with bounded lock/statement/deadline limits. Order is: deployment roots in UUID order → remaining provider/model controls in UUID order → all budget UUIDs → settings by workspace → connection UUIDs → all credential UUIDs **in UUID order** → approval primary keys → acknowledgement primary keys → windows by budget, scope rank (deployment month/day, workspace month/day, user day), C-byte scope key, UTC start → attempt/allocations → required audit. Discover IDs without locks, then reload and validate after acquiring locks. Never acquire an earlier lock class late or lock “active first.”

C checks all of A plus original actor/membership/request, current owner authority, exact entity/deployment, candidate lifecycle/wrap/expiry, old selection/generation, all policy/reference revisions/validity, account mapping and disclosures, outstanding attempt/send mark, matching observation, trusted key/realm, one-use registry and both clocks. Any mismatch denies promotion. No DB field can override a stale context.

First activation increments generation from zero. Rotation A→B retires/revokes A, sets its three encrypted envelope fields to NULL, activates B with generation g+1, advances connection revision/generation and settings selection/revision exactly once, finalizes B's authenticated promoted receipt, and records retirement/destruction/promotion/selection audits in one transaction. Retire A before B reaches the immediate unique index; force deferred integrity before commit. Any statement/audit/commit failure restores A, its envelope, selection and generation. No external secret deletion occurs before commit. The already admitted reservation survives; the in-memory permit is still consumed.

New active-aware lifecycle handles candidate allocation with active/replaced history, exact-version revocation and emergency disable while preserving 3b below-active behavior. Candidate revoke leaves A intact. Active revoke destroys its envelope, increments connection generation/revision, clears selection and disables affected settings atomically; no upstream key-revocation claim. Disable clears selection/advances appropriate revisions without requiring destruction or erasing historical verification. An exact old-version revoke cannot follow selection to B. Emergency revocation remains possible even when old receipt history is forged/untrusted; ordinary promotion must refuse that history.

## 11. Failures, races and safe results

| Observation/race                                                 | Required result                                                                                                                                      |
| ---------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |

| 403                                                              | `provider_denied`; no universally-invalid-key claim and no promotion.                                                                                |
| 404 or mismatched model                                          | `model_unavailable`; no alias fallback or entitlement inference.                                                                                     |
| 429, 5xx, connection failure                                     | `provider_unavailable`; preserve prior unverified/failed candidate lifecycle; no retry.                                                              |
| Timeout before or after send authorization                       | `timeout`; distinguish possibly transmitted internally; no false verification/refund/resend.                                                         |
| DNS/TLS/port/redirect/proxy/bounds rejection                     | `transport_policy_rejected`; no alternative transport.                                                                                               |
| Malformed JSON/media/status/headers                              | `malformed_response`; raw input discarded.                                                                                                           |
| Missing/mismatched account claims                                | `account_context_unproven`; no inference from DB account name.                                                                                       |
| Owner, tenant, entity, mode, policy or approvals change          | Fixed local denial or rejected-stale/policy success disposition; no credential promotion.                                                            |
| Verify A, then replace by B                                      | A cannot become active or update B's test metadata.                                                                                                  |
| Revoke/workspace-disable/connection-disable wins before C        | Promotion refused, even if the provider succeeded.                                                                                                   |
| Valid success arrives after expiry                               | Signed expired disposition only if safe finalization remains possible; never activation.                                                             |

Map test metadata only to frozen existing values: success; auth_failed for 401; protocol_failed for malformed/model/account mismatch; unavailable for transient failures; unknown for timeout/local uncertainty. A transient response does not reset a prior failed state to valid/unverified. 403 does not become 401. Record fixed attempt outcome for every admitted failure when safe; stale targets receive no metadata write. Success accounting and lifecycle verification are deliberately different fields.

Safe application results are verified-and-active, verification-rejected, verification-unavailable, verification-rate-limited, credential-state-changed and verification-expired. Future endpoints must first enforce scoped authorization so missing/foreign/unauthorized identities are indistinguishable; do not expose raw upstream statuses, bodies, account IDs, current foreign revisions, SQL or receipt MAC. No endpoint is added now.

## 12. Audit, observability and disclosure

Use `RequiredAudit` in the same transaction as admission, send authorization or state transition. Events remain the signed allowlist: verification_attempted/succeeded/failed, verification_send_authorized, credential_promoted, promotion_rejected, credential_replaced/revoked/destroyed and selection_changed under the existing assistant AI namespace. Remote success with stale local authority emits verification_succeeded and promotion_rejected, never credential_promoted.

Allow only server operation/correlation UUID, actor A1, explicit public workspace/entity, production/deployment, connection/version/profile, fixed provider/mode/purpose/outcome, attempt/evidence reference and relevant old/new revisions/generation. Account reference is opaque approved local ID. No full receipts, account headers, raw query values, request/response, User-Agent, model metadata, financial data, ciphertext, wrapped keys, secret material, signing paths or arbitrary error descriptions. No deferred/best-effort audit. Audit failure before send prevents send; failure at promotion rolls back state. Recovery cannot erase evidence or fabricate a success audit.

Saving disclosure concerns encrypted local custody only. Verification acknowledgement separately states that this exact credential and fixed model/workspace-routing metadata will go to Anthropic, with no question or business data, and consumes conservative local quota even on failure. Future inference acknowledgement is separate. Match provider, customer ownership, account/profile, purpose, data category and disclosure revision exactly. No VAP acknowledgement reuse, automatic consent migration or provisioning of real approvals.

## 13. Frozen-schema fit and required compatibility work

No new table, column, index, constraint, migration or regenerated vector is required. Existing attempt fields hold all snapshot/receipt values; immutable profiles, grants and controls hold approved metadata; request-local registries hold ephemeral authority. Frozen CHECKs/partial indexes/deferred bindings enforce the structural state; runtime enforces provenance, freshness and actual protocol success. A structurally forged active row remains possible for an appropriately privileged DB writer but cannot self-authorize the designed application service.

Before completion, implement only the frozen package's known legacy coexistence work: predicate-aware legacy acknowledgement upsert after its old unique constraint changed; discriminator-scoped legacy lookups/writes; purpose-aware recovery; root-fenced shared usage updates and reviewed immutable legacy mapping; correct control revision transitions. These are required compatibility work, not an inference feature. Preserve all legacy profile amounts, bounds, outputs, finalization and closed activation gates. PostgreSQL is mandatory for successor runtime; SQLite keeps its reviewed closed successor boundary while historical tests remain fast. Do not invent SQLite active parity or edit frozen guards for convenient fixtures.

If these changes cannot be made within the frozen invariants, stop with the precise conflicting constraint and needed Astra decision. Never silently correct the SQL, normalize IDs, re-sign historical receipts, manufacture evidence or erase liability.

## 18. CR1 — cross-root verification admission amendment

Date: 2026-10-09. Narrow security-design correction; no runtime implementation. This section supersedes only the actor-quota scope and admission-lock order in §§9–10 and supplements the implementation handoff in §15. The historical B1 implementation report/evidence and six-admission reproduction remain unchanged. No migration, frozen SQL, receipt format, R2/R3 or reconciliation amendment is required.

### Identity, objective and topology

**Canonical actor: exact stored `users.attribution_id` UUID (A1). Final quota key: A1 only.** `User::newUniqueId()` generates this identity; the attribution migration supplies global uniqueness within the application database and immutable guards. It is not the internal user ID, membership, workspace ULID, email or session. One user may own multiple workspaces associated with different deployment roots. Membership/root selection does not create another principal.

Deployment roots are operational policy/accounting partitions in a shared application identity realm, not independent identities. `TenantAiSchema` makes roots unique by deployment/kind/subject; it does not make users root-specific. Existing tests explicitly support multiple deployments in one database. The original actor-across-workspaces ceiling limits repeated probing, compromised-admin abuse and possible provider cost amplification. Connection cooldown addresses duplicate clicks; workspace and account ceilings protect separate resources. Root hopping must not multiply the actor allowance. Root-local reinterpretation is rejected on that basis, not because stricter is automatically better.

The five-per-hour quota is global across tenants, legal entities, roots, providers/policies, ownership modes, connections and credential versions **within one authoritative control-plane PostgreSQL database**. None of those dimensions enters the quota key. Five admissions in tenant A affect that actor in tenant B. Future approved providers share the actor ceiling; no new provider is implemented now. Rotation/replacement does not reset it. All other independent ceilings remain required.

Multiple Laravel processes/hosts are supported when all participating roots resolve A1 and perform admission against the same authoritative primary database and retained history. Actor lock, count, reservations, attempt, allocations and audit must use one physical writer connection in one transaction. Replicas, per-root database switching, independent writable databases, sharding this ledger and active/active multi-primary admission are outside this guarantee. The repository provides no cross-database identity/admission federation. Copying A1 into another database does not create shared locking.

This is the approved topology boundary, not a claim that production topology was inspected. Before live verification, operations must attest that all participating instances share this authority and restored/test clones cannot admit production work. If the product needs the same actor quota across independent databases, stop for broader control-plane design; CR1 does not pretend PostgreSQL locks solve that. A single-authority implementation can proceed without building such a distributed system. Existing activation gates stay closed.

### Mechanism selection and exact key

An existing durable actor row exists, but locking it first would invert account deletion: `DeleteUserAccount::execute()` locks global roots at line 256, then deletes/anonymizes the user. A new user-row → root path could cycle against root → user. User-row locking also contends with unrelated authentication/account writes. Moving that row lock after roots would require a wider user-writer lock graph review. Neither is approved here.

A single deployment root is insufficient; an arbitrary root as global sentinel changes its meaning. Locking every root introduces an unbounded lock set and root-creation races. Approve instead a dedicated **transaction-scoped advisory lock**, which does not lock user rows or change schema. PostgreSQL documents automatic transaction-end release and distinct two-int/single-bigint key spaces. See [explicit locking](https://www.postgresql.org/docs/18/explicit-locking.html#ADVISORY-LOCKS) and [advisory functions](https://www.postgresql.org/docs/18/functions-admin.html#FUNCTIONS-ADVISORY-LOCKS).

Exact protocol:

1. Resolve current authenticated User from primary; validate and use exact canonical stored lowercase UUID A1. No caller attribution, case normalization or membership-derived identity. Missing/deleted/mismatched user denies. Deactivation/anonymization is checked through the unchanged fresh authorization gates; it never deletes or refunds retained A1 attempts. A recreated account receives a new A1 under existing identity rules, not reuse of a deleted identity. CR1 is a per-principal control, not cross-account person detection.
2. SHA-256 the ASCII domain `facturac:tenant-ai:verification-admission:actor:v1`, one LF byte, then the 36 A1 bytes. No trailing newline, salt or tenant/root/provider suffix.
3. Interpret the first four digest bytes as unsigned big-endian integer u. Signed int4 key is u when u < 2147483648, otherwise u − 4294967296. No runtime-dependent hash.
4. In the outermost admission transaction, before any row lock, run a separate parameterized statement: `SELECT pg_advisory_xact_lock(?::integer, ?::integer)`, binding namespace **1180058417** (hex 46564331, ASCII FVC1) and that key. Reserve this two-int namespace exclusively for CR1. No existing production advisory caller was found in the inspected app tree.

Public test vector: A1 `00000007-0000-4000-8000-000000000001` produces SHA-256 `ba49cd8544874863fabe24e38266577bdaf9d68060143548171dc6faecb96d64`; unsigned prefix 3125398917; signed key **-1169568379**. This is identity metadata, not a receipt key. Receipt canonicalization remains untouched.

Same A1 always takes the same key across hosts/roots. Different actors normally differ. A truncated-hash collision only causes conservative extra serialization/possible timeout; counts still filter exact A1, so quotas are not pooled and no extra admission is granted. Never choose an alternate/random key on collision. No process-local mutex, session advisory lock, config-selected namespace or public test override.

### Atomic admission and canonical order

Require an outermost READ COMMITTED transaction, no caller-held transaction/row locks, savepoint admission or automatic retry. Set lock timeout at most 250 ms and statement timeout at most 1 second, both bounded by remaining operation deadline. Timeout, deadlock victim, cancellation or connection loss rolls back admission and returns a fixed safe failure; never continue an aborted transaction or fall back to a different lock.

The admission order is now: **one A1 advisory lock → deployment roots in UUID order → remaining provider/model controls in UUID order → budget UUIDs → settings by workspace → connection UUIDs → credential UUIDs → approval PKs → acknowledgement PKs → windows by budget / existing scope rank / C-byte key / UTC start → attempt and allocations → required audit**.

After acquiring these locks, freshly revalidate all existing authority, membership, session, policy, candidate, revisions, generation and approvals. Fresh user/membership reads are ordinary primary reads, not new user-row locks. Obtain database UTC instant q with `clock_timestamp()` after waiting/revalidation, rather than transaction-start `now()` captured before the wait. Use q for admitted_at and the rolling threshold. If discovered/locked accounting windows do not match q’s UTC day/month, roll back without admission; never charge a previous period or reacquire an earlier lock class out of order.

Count with a **subsequent SQL statement after advisory acquisition**, never a lock/count CTE sharing a pre-wait snapshot: exact A1, contract_version gateway_v1, purpose connection_probe, admitted_at > q minus 3600 seconds, ordered by admitted_at/id, LIMIT 5. No deployment, tenant, provider, policy, candidate, state or outcome qualifier. Keep the historical reproduction's no-upper-bound predicate: future-dated retained admissions count conservatively during clock regression. The exact lower boundary has left the rolling hour. No fixed/calendar-hour substitution or history rewrite.

If five rows are returned, refuse. Otherwise check unchanged connection/workspace/account/shared limits and atomically persist/reserve admission, allocations and required audit. Commit releases the advisory lock. Only afterward may JIT secret decryption/provider verification begin. Phase B, send prerequisite, Phase C promotion and recovery never reacquire the actor lock.

A successfully committed admission counts despite later 401, timeout, unsent failure, cancellation, stale promotion, recovery or success. Admission rollback leaves no attempt/reservation/audit and consumes no quota. No refunds after commit. Retained admission history, not successful receipts, is counted.

Proof at count four: T1 holds A1, observes four and commits fifth. T2 obtains A1 only after commit/rollback. Its later READ COMMITTED statement sees five after commit and rejects; after rollback it may admit. Timeout also denies without a write. Final count cannot exceed five. Controlled no-timeout tests must show exactly one new admission and one quota refusal.

Candidate/revoke/replace/disable, promotion, JIT/send rechecks, recovery, reconciliation and accounting/control writers retain root-first ordering and **never acquire CR1 while holding roots**. Account deletion likewise never requests CR1. Thus no root-holder waits back on the new actor lock. Same-actor admissions serialize before roots; different actors do not share this lock except collisions, although existing common roots/budgets legitimately serialize them. One operation admits one actor; batch admission is excluded.

This is an acceptable design-level lock graph, not a claim that unrelated code can never deadlock. Runtime review must inspect callbacks/observers and nested entry points; deny entry from a transaction already holding user/root/control locks. Existing root fencing and timeout fail-closed behavior remain mandatory. No long DB/advisory lock spans provider latency.
