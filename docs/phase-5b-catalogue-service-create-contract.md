# Phase 5B — bounded catalogue service creation

Design date: 2026-10-08. Astra design only. This document and its normative OpenAPI authorize a bounded future Sol implementation, not deployment, provisioning or external enablement. No runtime, migration or UI is implemented by this design.

## 1. Authority, inspected domain and scope

This executes the exact next Astra handoff in `phase-5a-trust-boundary-review.md` and the supplied Phase 5B request. Governing Phase 1–5A contracts, reports/reviews, A1/SA1 and evidence remain authoritative. Their completed reads from the immediately preceding review are reused; the Phase 5A implementation, final review/evidence and current substrate were inspected alongside the actual catalogue code. The master roadmap places customer/catalogue commands before draft preparation and separately gates fiscal issuance. No later roadmap step is included.

Inspected `CatalogueItemController`, `StoreCatalogueItemRequest`, `CatalogueItem`, `CatalogueItemPolicy`, `CatalogueCapabilities`, its read resource/commands, catalogue/stock/transport-identity migrations, `SupportedTaxTreatment`, `SaveCompanyProfile`, `LegalEntity`, fiscal currency configuration, catalogue/register/pricing/tax tests; and Phase 5A's context, boundary, canonicalization, ledger/capacity migration, audit, human adapter and process tests. Laravel best-practices guidance applies. `.ai/rules` is absent. No dependency or framework API change is needed.

The actual domain has one `catalogue_items` row for either product or service. It contains base supply price and currency, tax components and unit text inline. There is no required price row, tax-record FK, unit-record FK or separate service table. `price_list_items` are optional negotiated/list overrides, not necessary for service creation. There is no unit or tax activation/ownership registry to resolve. Do not invent these relationships to satisfy hypothetical race cases.

The current UI creates via its controller, sets currency from the legal entity, maps supported tax treatments and disables stock for services. Code is unique across **all catalogue types and active states within a legal entity**. Name is not unique. Company creation initializes AOA; fiscal documents support other currencies, and existing catalogue storage/read can represent them, but that does not require this initial service-write contract to support them.

New capability: **`catalogue.services.create`**, version **1**. New independent scope: **`catalogue:services:create`**. New effect: exactly one non-stock service row. Existing products, price lists, inventory and fiscal objects are not mutated. No other command is designed here.

## 2. CS1 — smallest closed-registry extension

**The Phase 5A protocol can be reused; its current implementation cannot be reused unchanged.** Concrete customer coupling exists in `IntegrationCommandContext::authorize` (scope), `CommandIdempotency` (command/version), `CommandAudit` (capability/event/Customer subject), `ExternalCommandBoundary` (route/DTO), the customer canonical envelope and the migration's command INSERT guard. Copying these classes for services is forbidden.

CS1 approves only an explicit two-entry trusted enum/descriptor in the existing application area:

| Property                        | Existing entry, unchanged     | New entry                                   |
| ------------------------------- | ----------------------------- | ------------------------------------------- |
| Capability / ledger command     | `customers.create`            | `catalogue.services.create`                 |
| Required exact scope            | `customers:create`            | `catalogue:services:create`                 |
| Capability version              | 1                             | 1                                           |
| Canonicalizer                   | `command-json-v1`             | `command-json-v1`                           |
| Defaults policy in fingerprint  | `customer-create-v1`          | `catalogue-service-create-v1`               |
| Resource suffix                 | `customers`                   | `catalogue-services`                        |
| Effect subject / creation event | Customer / `customer.created` | CatalogueItem / `catalogue.service.created` |
| Domain-unique conflict          | `CUSTOMER_CONFLICT`           | `CATALOGUE_CONFLICT`                        |

This is a closed server mapping, not a plugin registry, string permission dispatcher, arbitrary callback transport or client-selectable command field. No unknown enum/capability/version is executable. Existing customer callers retain their current entry by a compatibility wrapper/default; service wrappers explicitly select the service entry. A caller cannot substitute a request/header/query string for a descriptor. The same authenticated machine context may support several grants, but **every adapter, ledger invocation and persistence action independently authorizes its fixed exact capability**. Identity is not command authority.

Parameterize the one existing ledger protocol and required-audit implementation with that trusted entry. Preserve the sealed identity, lock sequence, primary database, expiry clock, current authority, transaction, replay, result encoding, capacity, timeout and error rules. Generalize audit subject acceptance only to the two explicit subject classes with descriptor/class checks. Domain persistence verifies its live reservation's complete binding **including exact command/version and origin credential**, not just operation UUID. Strengthen the existing customer reservation check accordingly; this changes no authorized customer behavior and prevents a service reservation being used for a customer.

Keep the existing `ExternalCustomerCommand`, all existing customer canonical bytes, defaults, responses, errors, audit fields and tests. The new service adapter uses the same canonical envelope encoder and ledger, with its own normalized input. Common strict JSON/decoded-duplicate/transport parsing may be extracted once, preserving the existing customer parser/error ordering. Do not run all request types through a customer DTO.

Only the exact new decoded resource pattern selects the service entry. Existing customer and unknown-path handling/order remain unchanged; unrecognized paths cannot guess a service command from a scope, payload or alias. Recognized unsupported service verbs use that service authority before 405. No changes to read middleware/context or read quotas.

CS1 is an additive capability/guard extension, not an amendment to customer idempotency semantics, A1, SA1 or any read contract. Historical Phase 5A documents remain historical and byte-preserved. If Sol cannot preserve the customer protocol while making this bounded extension, it must return the specific conflict to Astra.

## 3. Identity, permission and environment

Effective authority remains verified machine identity → credential AND parent exact grant → immutable workspace/entity/environment binding → fresh original sponsor membership/role/verification/MFA → specific capability. Use Phase 5A's existing stateless hash-only bearer, current owner/administrator sponsor and original membership checks. No creator-snapshot authority, browser workspace, session fallback, impersonation, delegation or agent authority. Grant issuance/rotation stays human owner/admin with current MFA, work session and recent password confirmation. Standing human approval of this exact narrow grant is sufficient; no per-service approval ceremony. Defaults grant nothing new.

`catalogue:read`, `customers:create`, documents/customer/AGT/analytics reads and all unknown/wildcard/admin/write scopes fail service create. Service create fails customer create and every read capability unless separately granted. It grants no product or inventory mutation. Future policy changes must maintain tested parity between explicit-context catalogue creation permission and the existing human role policy; never consult a sponsor's mutable current workspace to implement that policy.

Service creation is **production-context only**, because catalogue records are legal-entity master data with no environment partition, just as Phase 4A explicitly documents. A homologation credential must not create a master record that production UI/reads can see. This is independent of AGT enablement or legal-entity AGT readiness. No homologation master table or environment column is introduced. Backend lifecycle validation rejects the new scope for homologation before secret creation; malformed raw grants also fail execution before catalogue, defaults or ledger SQL.

Both existing external switches remain false. Both must be true to admit any command. PostgreSQL is the production command database; SQLite is only the isolated test path and other drivers fail closed. Context mismatch denies identically for foreign and nonexistent bindings before business lookup. Existing retained-integration deletion restrictions and original sponsor deletion semantics remain.

## 4. Closed service input and field inventory

All seven possible submitted values are strings. Unknown properties, nulls, nested structures and aliases reject. Whole-body bound and parser depth remain 4096 actual UTF-8 bytes / depth four. Each normalization below is pure, request-independent and frozen for this version. ASCII edge trim means only SP/HT/CR/LF.

| Stored/domain concept                | Classification    | Exact external rule                                                                                                                                                                                     |
| ------------------------------------ | ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `code`                               | Required          | ASCII edge trim and uppercase, then `[A-Z0-9][A-Z0-9._-]{0,59}`. Preserve punctuation and leading zeroes. This is the existing unique reference, not a new external-ID field.                           |
| `name`                               | Required          | NFC, ASCII edge trim, 1–255 Unicode code points; no remaining C0/C1 controls. Preserve case/internal whitespace.                                                                                        |
| `description`                        | Optional          | Same text normalization, 1–255 code points if supplied; omission stores null. Present empty/null reject. Plain text, not executable markup or a template.                                               |
| `unit_of_measure`                    | Optional          | Omission `UN`; ASCII edge trim/uppercase, then `[A-Z][A-Z0-9._-]{0,9}`. It is a bounded unit label/code, not a DB identifier or certification of an AGT unit.                                           |
| `unit_price_minor`                   | Required          | Canonical nonnegative integer-minor-unit string as §5. No `unit_price` decimal alias.                                                                                                                   |
| `currency_code`                      | Required          | Exactly `AOA`; no trimming/case folding. AOA must match the locked entity base currency on first execution.                                                                                             |
| `tax_treatment`                      | Required          | One exact frozen domain token in §6. No aliases, case folding or whitespace normalization.                                                                                                              |
| `type`                               | Server controlled | Always `service`; even `type=service` is forbidden request input.                                                                                                                                       |
| `is_active`                          | Server controlled | Always true for this external create.                                                                                                                                                                   |
| `tracks_stock`                       | Server controlled | Always false. Both `tracks_stock` and `track_stock` inputs reject.                                                                                                                                      |
| `stock_scale` / reorder level        | Server controlled | Existing storage scale 3, inert for service; `reorder_level_units=null`. No stock record/movement/quantity created. All stock inputs forbidden.                                                         |
| Tax type/code/percentage/exemption   | Server derived    | Exact profile from authoritative enum after §6 verification; never accepted as parallel fields, even if consistent.                                                                                     |
| Public/internal ID, workspace/entity | Server derived    | ULID/internal key and captured explicit context; no caller ownership or IDs.                                                                                                                            |
| Timestamps                           | Server derived    | Existing server persistence timestamps.                                                                                                                                                                 |
| Accounting/other associations        | Forbidden/absent  | No separate accounting code/ledger, supplier, cost, warehouse, lot, batch, external reference, price-list/customer price, environment, balances or relationship expansion. Reject every unlisted field. |

There are no separate business-name, tax-record, unit-record or service-price foreign keys. The explicit `type=service`, `tracks_stock=false`, null reorder threshold and lack of stock calls are executable invariants, not cosmetic labels. Neither an external nor a human service DTO may hold product-only state. Tests poison all protected fields and aliases and assert no rows/jobs/events in stock, price-list, document, payment or delivery systems.

The description limit intentionally follows the actual VARCHAR(255) column. Current UI validation permits 500; PostgreSQL cannot durably store those values. Do not widen the column. For the shared **service-create** path, convert over-255 description and unsafe price input into ordinary field validation errors before persistence; preserve all previously storable valid UI service inputs, redirects, active-state choice and unit/text normalization. This is a narrow storage-integrity correction, not authorization to alter product or catalogue-update workflows. Do not truncate descriptions or repair existing rows.

## 5. Price and currency semantics

Base price is the per-unit **pre-tax supply price**, not final invoice price, negotiated price, valuation, revenue or amount due. `unit_price_minor` is a JSON **string** matching `0|[1-9][0-9]{0,18}` with numeric value at most **9223372036854775807**. Compare length/lexical digits before any integer conversion. Persist on the certified 64-bit runtime without float, decimal rounding, exponent parsing, saturation or PHP overflowing multiplication. Zero is allowed. Negative, `-0`, plus sign, leading zeroes, whitespace, decimal point, exponential and JSON numeric values reject with 422. Escaped digits decode normally before canonicalization.

Scale is exactly two: `"10000"` means AOA 100.00. This is not the three-decimal stock scale. No FX, currency conversion or inferred multi-currency price is performed. The fingerprint contains the canonical string, never an integer/float variant. Large catalogue prices may be unfit for a later quantity/total calculation; unchanged fiscal validation must still decide that later operation. Creation does not certify future issuance eligibility.

For this initial command, AOA is the sole external currency because the current company-creation path initializes AOA and catalogue base-price creation follows the entity currency. This is a deliberate smaller write contract, **not copied from Phase 4D's eight output buckets** and not a claim that all existing catalogue rows are AOA. AOA must still be enabled in authoritative fiscal configuration. A non-AOA/missing/unsupported entity configuration fails generically 503 for a new command; caller currency other than exact AOA is schema 422. Do not silently relabel money or change company currency. More currencies need an explicit later contract.

On new effect only, select the bound entity using the primary connection with **FOR SHARE**, after common context locks, and keep the lock through commit. Unlike Phase 5A's KEY SHARE, SHARE blocks non-key currency updates. Read/validate currency under that lock; a currency writer that committed first determines the checked value, and one arriving later waits. Company profile writers already use transactional entity locks. Unsupported administrative updates in tests use real independent transactions; do not add a currency-management route. Do not strengthen customer transactions or hold a new lock on completed replay merely for this domain check.

Once committed, item currency/price remain the recorded creation values; later company currency changes do not rewrite the item or stored acknowledgement. Replay performs current identity/capability authorization but **does not revalidate current catalogue/tax/currency defaults or load the item**. Pure version-1 input validation remains available for old results.

The existing UI accepts decimal major-unit strings. Its service adapter must convert the validated decimal using string split/padding and a signed-BIGINT range comparison before casting; no floats and no rounding. Preserve its current accepted syntax/max input length. The existing multiplication can overflow for some 18-digit strings; reject those as `unit_price` validation errors. Do not route product creation/update through a new converter as unrelated work. API and UI converge on one validated integer-price service persistence action.

## 6. Tax and units: actual authority, not imagined registries

The authoritative vocabulary is `SupportedTaxTreatment`; map using its methods, not a parallel tax engine:

| Token         | Stored type | Code | Percentage (decimal cast) | Exemption |
| ------------- | ----------- | ---- | ------------------------- | --------- |
| `IVA_NOR_14`  | IVA         | NOR  | 14.00                     | null      |
| `IVA_ISE_M00` | IVA         | ISE  | 0.00                      | M00       |
| `NS_M02`      | NS          | null | 0.00                      | M02       |
| `IVA_ISE_M04` | IVA         | ISE  | 0.00                      | M04       |

These are current application configurations, not a new statement of Angolan tax law, taxpayer entitlement or AGT homologation. Service creation does not modify company tax regime or certify that a treatment is lawful for a transaction. Current catalogue validation uses this vocabulary, not an entity-regime eligibility matrix. Preserve that behavior; do not invent a regime-to-service tax policy in this phase. Fiscal operations retain all their independent checks.

Unknown treatment token is 422. Exemption reason is encoded by the selected token; no arbitrary percentage/reason/name/record ID is accepted. Any extra component field, including a contradictory or redundant exemption, is 422. No silent legacy inference is used for machine input. A selected token that cannot resolve to the exact pinned profile in the installed authoritative enum, or fails a strict `fromComponents` round trip, causes 503 before new persistence. Freeze these mappings with tests; future mapping changes require version/contract review rather than silently reinterpreting an old token.

Pure canonical input validation recognizes the frozen four-token vocabulary independently of a live effect's domain availability. A completed authorized replay remains possible after configuration drift; a new effect fails closed if its authoritative mapping no longer matches. This avoids both storing unsupported taxes and making retained acknowledgements depend on mutable domain configuration.

There is no mutable tax-row activation flag, cross-tenant tax FK or transactionally editable percentage table. **Tax-record update/deletion races are not applicable** to this implementation. Instead test real concurrent entity tax-regime changes: the creation SHARE lock serializes them, while the selected enum profile remains unchanged by regime mutation. Code deployments must not run incompatible mappings for this protocol concurrently; pause commands for a mapping-changing deployment and obtain Astra approval. Unit tests must inject/simulate a resolver mismatch to prove fail-closed behavior, not invent a production table for the test.

Units likewise have no controlled registry or activation/tenant ownership. The optional bounded unit label above is sufficient; nonexistent/inactive/cross-context unit IDs cannot be resolved and are forbidden fields. **Unit-row races are not applicable.** A future units registry needs another design. Tests cover invalid labels and forbidden unit IDs; no name-to-ID lookup, unit creation or stock conversion occurs.

## 7. Shared application path and atomic effect

Introduce one typed service-create input and shared service persistence capability in the existing application area. Its external adapter applies §4; its human adapter preserves existing UI semantics except the two demonstrably unrepresentable storage cases in §4/5. The UI controller's **service-create branch only** delegates to it; the existing product branch, updates, deactivation and imports remain unchanged. This is convergence on shared persistence, not a second API-specific catalogue engine. Reuse `SupportedTaxTreatment` and the actual CatalogueItem model/uniqueness.

Capture a separate trusted human service context using the existing human factory/fresh-primary membership pattern and actual catalogue-create role policy (owner/admin/accountant/billing). It must not take machine scopes or permit a customer-only context to stand in for catalogue authorization. Small common identity/policy helpers may be extracted with preservation tests; no generic permissions supplied by callers. Mutable browser entity selection happens once in the UI adapter, never in machine execution. Existing verified/MFA session and impersonation restrictions remain.

For machines: common locked authorization → namespace lookup/replay → shared-capacity admission/reservation → service-specific locked entity/config validation → explicit single-row insert → required service-created audit → immutable minimal result/finalization/counter/last-used → final current authorization/expiry/deadline → commit → response. For human service creation, use its own transaction and required creation audit, without a fabricated machine idempotency guarantee.

Success requires `save()` returning true **and** persisted model state. Verify the saved row has the expected context, service discriminator, no-stock flags and normalized price/currency/tax fields before finalization; no success for a cancelled model event or partially populated record. No required child rows exist today. If inspection finds a genuine required relationship not represented here, stop for Astra rather than acknowledging incomplete state or introducing another table. Optional price-list/stock relationships must remain absent.

Disable automatic CatalogueItem logging on that create instance only, write the required minimized service-created audit in the same connection/transaction, then restore ordinary instance logging. Do not globally suppress model events. Other model logs, products and later updates retain existing behavior. Audit cancellation, buffering, disablement, wrong connection and thrown errors abort human and machine creation. No job, email, webhook, stock movement, fiscal numbering or AGT call is emitted.

## 8. Idempotency, duplicates, bounded storage and concurrency

Keep Phase 5A's namespace: integration + workspace + legal entity + environment + exact command + version + SHA256(parsed opaque key). Rotation shares integration identity. Same key on customer and service commands denotes different operations; neither can replay the other's result. Same key/payload for this command produces the same stored 201 body/operation UUID and one effect. Same key/different normalized payload is 409 `IDEMPOTENCY_CONFLICT`; no prior ID/hash disclosure.

Canonical service envelope uses the same AGT canonical JSON encoder, `command-json-v1`, exact capability/version, canonical integration public ID, explicit context and `catalogue-service-create-v1`. Its input has **all seven keys**, including normalized default `unit_of_measure=UN` and `description=null` for omission. Price stays string, currency exact AOA, tax the frozen token. Field ordering/JSON escaping/NFC/allowed trims are equivalent; changed price/name case/internal spaces/code/unit/description/treatment are not. Present null remains invalid input; it is not an alternate wire encoding for omitted description. No secret, raw key, payload or fingerprint is exposed/logged. No AGT canonicalization changes.

Different keys targeting the same `(legal_entity_id, code)` compete on `catalogue_items_entity_code_unique`: one wins, the loser rolls back ledger/effect/success-audit/counter and gets generic **409 CATALOGUE_CONFLICT**, with no existing item details. That includes collision with an inactive item or product. Different entity may reuse code; identical names may coexist with different codes. There is no upsert, merge, resurrection, fuzzy match or separate service-only uniqueness. Exact named-constraint classification only; other database errors are 503.

Reuse one outermost primary READ COMMITTED transaction, user/member SHARE → integration/credential UPDATE → exact applicable grant SHARE → workspace/entity KEY SHARE. For a new service effect add the entity SHARE check from §5; no additional global lock. Customer/service requests on the same integration intentionally serialize. Across integrations, entity SHARE locks are compatible; the unique code constraint decides duplicates. Preserve 1s lock/2s statement/5s transaction limits and deadline, no automatic retry and safe connection-setting restoration/discard.

Current authority governs every replay. Before-lock withdrawal denies; withdrawal blocked behind a successful transaction may commit afterward. An already committed response may finish after revocation, but the next replay must deny. Preserve origin credential/sponsor snapshots after deletion; no result depends on a live item. Rename/deactivation/later deletion of the created item must not change acknowledgement or recreate it. Postcommit transport loss is reconciled by same-key retry; no new key recommendation or uncertain-commit auto-execution.

Shared quotas remain **IP60 / integration10 / workspace30 per native minute**, across **both command types**, credentials, aliases, verbs, replay/conflict and admitted malformed/denied traffic. No separate service quota or new identity prefix. Read budgets remain separate. Shared retained-success capacity remains **100000 total operations per integration across both commands**; no counter per command, reset, TTL, purge or key reuse. Failed/denied attempts create no durable reservation. At cap, either command's authorized completed replay works; any new operation fails generic 503. Retention remains indefinite until separately reviewed policy.

## 10. Audit, correlation and errors

Reuse required command attempted/authorized/replayed/idempotency-conflict/denied/failed events with the trusted descriptor's capability/version. Domain creation event is `catalogue.service.created`, log name `catalogue-item`, explicit CatalogueItem subject. Exactly one business-effect event per successful creation; replay produces no second creation event. Required authorized/created/replayed audits are transactional, attempted is before transaction, known rollback/conflict is after rollback and uncertain commit remains `outcome_unknown`.

Preserve Phase 5A machine/sponsor/current/origin identity, A1 immutable attribution, standing-grant approval and server/client correlation versus stable operation UUID. Preserve real/effective human identity for the human path. No agent, delegation or workflow identity is invented. Set User-Agent null. Use the **verified bound environment**, including a denied homologation credential; a mismatched requested path never overwrites verified context. Do not store raw requested foreign context. Add both environment-denial regression directions.

No service name/code/description/unit/price/currency/tax payload, full input/result, key/digest/fingerprint, SQL/binding/constraint name, raw URL/header or credential enters audit properties or logs. Internal subject/identity references are allowed under existing audit semantics. Extend DTO redaction and descriptor-aware sanitized uniqueness classification. Do not log enum-mapping exceptions with payloads. Infrastructure redaction remains a release gate.

Pure HTTP/schema validation failure remains Phase 5A behavior: quota charged when identity was reached, no invented operation or domain-success audit. A structurally valid authorized request records attempted; effect-time validation/configuration failure rolls back and records generic failed/rolled_back. Authenticated 401/403 records denied with verified attribution. Scope/context checks precede business queries. Audit failure returns generic failure, never a success with missing evidence.

**POST `/api/integrations/commands/v1/workspaces/{workspacePublicId}/legal-entities/{entityPublicId}/environments/{environment}/catalogue-services`**. Proposed route name `integrations.commands.v1.catalogue-services.create`. No alternate endpoint, GET list/detail alias, session API mutation route or new management surface. Normative schema: [openapi-external-catalogue-service-create-v1.json](openapi-external-catalogue-service-create-v1.json), together with this contract's normalization, numeric and cross-field semantics.

Inherit unchanged Phase 5A HTTPS/single bearer, no cookie/session/CSRF fallback, 4096 actual bytes, JSON-only optional UTF-8 charset/no compression, depth four/decoded duplicate members, opaque printable 1–128-byte Idempotency-Key, bounded client correlation, no queries or unknown fields, no method override, private/no-store/Vary Authorization, generic Portuguese envelope and fresh server request ID. Disabled access is generic 404 before auth/quota/business work. No Location, product discriminator, price/tax/unit/customer or current item snapshot. It grants no catalogue read authority.

Mapping/currency configuration drift, capacity, audit, unsupported driver, timeout/integrity/DB failure yield 503, never partial success or detailed infrastructure errors. Error shape/message is exactly Phase 5A's. Customer responses retain CUSTOMER_CONFLICT and its unchanged spec.
