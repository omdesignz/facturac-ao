## Adversarial assessment

### Recorded meaning, money and calendar

The metric is `recorded-billing-v1`: locally issued FT, FR, GF and ND totals, plus a separate NC total and arithmetic after credits. RG does not add billed money. Ordinary drafts add zero money but consume capacity; a draft carrying issuance markers is inconsistent and fails the whole read. Every non-draft candidate must have a recognized local state/type, complete issuance/freeze/document-number markers, supported currency and consistent nonnegative integer totals. Local `issued`, `received`, `processing`, `valid`, `invalid` and `contingency` states remain recorded issuance facts. No query predicate requires qualified AGT acceptance.

Real domain tests issue all supported billable types and linked credit notes, including a credit in another month. A credit belongs to its own document month; the source month is not rewritten. Real partial/full/multi-source receipts, withholding allocation and refused overpayment leave this metric unchanged. Proven acceptance, rejection, processing cancellation, unknown/partial/conflicting reconstruction and stale proven acceptance likewise preserve recorded totals and frozen bytes; SA1 separately controls receipt authority. Neither an AGT processing cancellation nor invalidity is silently treated as a local invoice void. There is no supported mutable issued-document void/delete operation here: issued update/delete is rejected. An unsupported local state is rejected by the SQL whitelist; it does not become an exclusion that hides money. Pro-formas/transport documents live outside this fiscal candidate relation; unsupported fiscal type `FA` fails closed.

This therefore measures neither revenue, cash collected, receivables nor AGT-accepted turnover. No payment/settlement/AGT join can accidentally reclassify the sum. `BillingDefinition` shares the existing type arithmetic, and the query checks that its supported type set remains exactly FR/FT/GF/ND before executing.

AOA, BRL, CNY, EUR, GBP, NAD, USD and ZAR are separate, ordered, always-present scale-two buckets. Each has its own counts and nine money strings. Empty buckets are zeros; a credit-only bucket can have negative after-credit values. There is no cross-currency total or FX conversion, and base-currency/exchange-rate changes cannot relabel amounts. Tests assign distinct values above JavaScript's safe-integer range to every currency. PostgreSQL `SUM(bigint)` is validated as a canonical nonnegative decimal string bounded by signed 64-bit maximum before integer subtraction; neither aggregation nor JSON serialization uses a float. SQLite overflow fails generically. A malformed issued currency, inconsistent amount or overflow withholds all eight buckets, including otherwise valid currencies. Ordinary drafts' unused monetary attributes are not financial evidence.

Membership is a half-open range on the domain DATE, `document_date >= first_day AND document_date < next_month_first_day`; created, updated, issued and payment timestamps do not determine it. Tests cover January/February/March edges, leap day, year rollover, an application UTC setting and Luanda's January 1 while UTC is still December. Current-month committed future-dated documents are intentionally included; future months are rejected. Only `Africa/Luanda` is supported: entity timezone is checked before the read and again in the SQL snapshot. Unsupported timezone is a failure, not an implicit conversion. `as_of` comes from the same SQL statement's UTC observation time.

### Exact ranges, capacity and snapshot

Let S be the visible, context/month-qualified sequence ordered uniquely by `(document_date,id)`. The first materialized range P is the first min(50000, |S|) keys. If it is empty, the null scalar boundary admits no tail. Otherwise its last composite key b partitions S into P and the strict suffix `key > b`. The second range takes the first 50001 keys of that suffix. Their UNION ALL, global order and LIMIT select exactly the first min(100001, |S|) keys of S. Strict comparison prevents overlap; date plus unique ID resolves ties. No premise that IDs grow with dates is needed.

The independent streaming reference in the tests spells the original single-range query separately and compares every actual key, requires a strictly increasing sequence and exhausts both iterators. Cases cover 0/1/100/49999/50000/50001/99999/100000/100001/200001, nonmonotonic dates, same-date ties, month edges, mixed currencies/types/states and drafts/RG/control rows on both boundaries. Corrupt candidates at positions 50000, 50001, 100000 and 100001 are not filtered away. Sparse rows and deleted/moved draft neighbors cannot leave an ID-gap assumption because ranges use values, not contiguous arithmetic IDs.

At 100000 physical candidates a valid month returns complete totals. At 100001 and 200001 the count rejects all financial data. Candidate 100001 is detection-only **for acceptance**, as explicitly clarified in Round 2: the internal fold may touch it, but no truncated result is published. Excluded drafts/RG still count. The same generic 503 covers cap, timeout and integrity failure; it contains no count, bound, candidate key or partial bucket. This is a visible-row bound, not a promise that MVCC dead-tuple/index-page work equals that count.

Both ranges, payload retrieval, integrity flags, aggregate, timezone and observation time execute in one primary PostgreSQL statement snapshot inside a dedicated top-level read-only transaction, with no retry. No incompatible read can occur between key discovery and monetary lookup. Existing process tests cover genuine source issuance/credit/receipt/poll/rebuild transactions on either side of the read. S1 now proves commits inside the statement as well: all five in-flight results equal the full old currency array, and the next uninstrumented read sees the committed change (or unchanged state after rollback). The fixture explicitly binds its mutable draft to production; ordinary new drafts otherwise start unresolved. This test setup grants no new production draft/issuance API.

Issued fields cannot legitimately change currency/value/status/date through an update; domain rejection/frozen-evidence tests cover that boundary. Draft issuance supplies the legal transition that changes fiscal state, currency and value in the concurrency attack. No invented void operation or raw mutation of issued fiscal evidence was added to satisfy a test.

## Roadmap recommendation after Phase 4D approval

The master roadmap's next category after read-first resources is **safe mutations**, before high-risk fiscal APIs, webhooks or agents. Its numbering differs from this repository's phased contracts. Recommend the next local slice as **Phase 5A — non-fiscal customer creation and command idempotency, Astra Medium design only**. This is a deliberate small first write, not authorization for every customer/catalogue/draft mutation in the master roadmap.

Why this slice: customer creation already exists in the Inertia application, while the current controller/policy/form request derive authority/entity from browser workspace state. They cannot simply be exposed under a token. A small shared application command can preserve that business behavior while establishing explicit write context, grants, input minimization, atomic audit and replay boundaries before more complex draft/fiscal commands. Existing entity/NIF uniqueness must be inspected as a concurrent invariant; automatic delivery flags, negotiated pricing and default price-list behavior must be explicitly handled rather than inherited from broad model fillable fields.

This **plans the transition from external reads to external writes**; design alone makes no such runtime transition. New boundaries include durable business effects, machine write authority, transaction-time authorization, duplicate/lost-response handling, privacy of persisted commands/replays and operation audit atomicity. Phase 1's idempotency protocol is mandatory: stable integration/context/capability-version key identity, typed canonicalization/hash version, no floats/duplicate JSON keys, bounded concurrent identical requests, differing-payload conflict, authority revalidation on replay, atomic result/audit and recovery after rollback or uncertain delivery. Current read scopes and read contexts confer no write authority.

Human approval: this review authorizes neither implementation nor live grants. Astra must explicitly settle whether customer creation requires per-operation approval or a narrowly delegated standing grant from an authorized human; the read-only credential contract cannot answer it. Recommend retaining deliberate human approval of the design and subsequent provisioning/grant boundary, and keeping any machine invocation non-agentic. Do not inherit approval or delivery authority from the integration's creator. Sol may implement only after that bounded design is signed off.

Operational prerequisites remain PostgreSQL version/unique-constraint/concurrency certification, transactional durable audit and recovery/retention tests, secret/redaction/logging controls and a separate external-enablement review. AGT homologation is not needed to design a non-fiscal customer command, but no local test clears the outstanding fiscal/production prerequisites. External access remains globally off throughout the proposed local design/implementation.
