## 2. Root cause

The SQL explicitly orders candidate fiscal rows by document_date/id before LIMIT 100001. This order comes from BillingSummaryQuery, not an ORM/global scope, dashboard reuse, API sorting parameter or GROUP BY. Candidate selection already has the correct workspace, legal entity, production environment and half-open document-date predicates. No date function, defective cast, partial-index mismatch or missing SQL tenant predicate caused the failure. Predicate text order is not the problem.

The approved index has exactly the correct leading equality keys followed by range/order keys: `(workspace_id, legal_entity_id, environment, document_date, id)`. It is not redundant or incorrectly shaped. However, the current candidate SELECT requests document type/status/number, issue/frozen timestamps, currency and three amounts as well as ID. That payload is not covered by the index, so an ordered scan must fetch heap rows before the limit.

At the dense fixture, the LIMIT slightly exceeds the estimated full month population; it offers little estimated early-stop benefit. The older index is much smaller and can cheaply identify matching tenant/date entries. PostgreSQL chooses its bitmap path, visits the heap in page order, filters environment and sorts the wide qualifying rows to recover date/id order. This is a planner-cost diagnosis supported by the measured query-shape comparison, not a claim to have traced every rejected internal planner path. PostgreSQL documents the tradeoff between ordered index access and heap access plus sorting, especially when a large fraction of a population is selected. [PostgreSQL 18 ordering](https://www.postgresql.org/docs/18/indexes-ordering.html).

Fresh ANALYZE already runs after both fixture stages. Retained dense estimated rows were 99073 versus 100000 actual; this review reproduced a dense estimate of 99843. Stale statistics or a gross dense cardinality error therefore do not explain the failure. The sparse estimate of one versus 100 reflects the very rare date cohort and is a fixture limitation, but its ordered index plan passes. No higher statistics target is selected as a remedy.

The fixture strongly favors the older index: all original records have one workspace, entity, environment and status, and only three dates. The older index is 7104 KiB versus 62 MiB for the new index at 1.1 million rows. Repeated old keys and lack of an ID suffix are consistent with much denser storage; its missing environment key costs no selectivity in that initial all-production fixture. PostgreSQL 18 can use trailing conditions in multicolumn indexes, including skip-scan opportunities when intervening keys have few distinct values. The recorded plan proves the date index condition, not a particular internal skip-scan algorithm. [PostgreSQL 18 multicolumn indexes](https://www.postgresql.org/docs/18/indexes-multicolumn.html).

There are two independent sources of temporary I/O:

1. The dense candidate date/id sort is an external merge over 100000 rows, using 9992 KiB of disk under work_mem=4MB.
2. Both candidates and checked are explicitly MATERIALIZED and reread for count, validity and totals. Their wide intermediate tuples also spill. The final eight-currency hash aggregate itself uses 32 KiB and reports Disk Usage 0. Do not describe this as the final hash aggregate spilling.

The retained root plan reports 3744 temporary blocks written. Raising work_mem would mask avoidable wide sorting/materialization and multiply memory exposure across concurrent workspaces; it is not the selected fix.

## 4. Selected query-only remedy

Preserve one primary statement inside the existing dedicated read-only transaction, with final authorization before it and durable audit after it. Preserve the exact financial classification, stored integer amounts, flags, month and timezone semantics, metadata and output allowlist.

Use this relational structure:

1. **Bounded covered keys:** select only ID and document_date from fiscal_documents with the explicit workspace/entity/environment and date-range predicates, ORDER BY document_date,id, LIMIT 100001. This is a single-use derived relation/CTE. Do not fetch the nine fiscal payload fields here.
2. **Bounded payload:** for each selected key, retrieve at most one fiscal row by its unique ID and the same explicit workspace/entity/environment tuple. PostgreSQL uses a correlated LEFT JOIN LATERAL subquery with LIMIT 1. Project only fields required for existing validity checks and billing arithmetic. No second month-wide payload scan. The repeated date predicate is unnecessary at this point: the key was selected in this same statement and the ID/tuple identify the identical MVCC row. Keep the date predicate in key selection, not as a second range search for each point fetch.
3. **One fold:** apply the existing issue-marker/type/status/currency/money validity expression; count every selected physical candidate, including ordinary drafts and RG; compute both financial counts and six native sums in one aggregate. No WHERE/HAVING removes drafts, RG or invalid rows before the candidate/validity accounting. Normal draft financial contributions are zero. Reuse BillingDefinition's arithmetic/classification rather than duplicating a second definition.
4. **Small control/result relation:** group only by the eight known currencies plus, if needed, one internal null control group for unsupported/draft currency. An invalid issued currency still marks the whole request invalid; the null control group is not an external currency or fallback AOA bucket. Fold candidate count and invalidity across all groups before ignoring that control group. This keeps grouping bounded even with many corrupt currency codes. The API still returns exactly its eight approved buckets.
5. **Same-statement metadata:** derive global count/validity from this small result (window aggregates or a small reused aggregate relation), attach entity timezone and statement_timestamp, then retain all current range checks and zero-bucket serialization. Empty months must preserve the metadata/control result. Never reread or materialize the 100001 wide rows just to compute count or MAX(validity).

The LEFT payload join preserves the selected-key count even if a lookup unexpectedly lacks a row; such a missing payload must fail the existing required-marker check, not reduce the count or manufacture a zero result. Unique ID and a single statement snapshot normally establish exactly one matching payload per key. The per-key LIMIT expresses a bounded relational lookup, not a planner hint or multiple application queries. No Eloquent row hydration, PHP loop of queries or independent currency queries is authorized.

The contract requires a bounded ordered candidate relation and explicitly permits a derived relation/CTE. It does not require the current pair of wide `AS MATERIALIZED` tuplestores. The replacement retains ORDER BY and LIMIT as a relational boundary while streaming keys into the fold. Only a small folded result may need reuse/materialization. PostgreSQL supports folding a side-effect-free CTE used once into its parent. [PostgreSQL 18 CTE materialization](https://www.postgresql.org/docs/18/queries-with.html).

A covered Index Only Scan may still perform heap visibility checks on recent rows; zero Heap Fetches is not an acceptance requirement. The fresh 100000-row experiment did perform 100000 visibility heap fetches and still passed the cost bounds. No VACUUM-only assumption or extra covering payload columns is required. [PostgreSQL 18 index-only visibility](https://www.postgresql.org/docs/18/indexes-index-only-scans.html).

For SQLite correctness tests, use the same key selection, checks and fold, with a left unique-ID/context join where PostgreSQL uses the bounded LATERAL lookup. SQLite need not implement LATERAL syntax. Keep all financial expressions shared; only the driver-specific payload-access syntax differs. Its plan cannot certify PostgreSQL performance. This follows the existing explicit two-engine query boundary, not a new business engine.

Do not remove candidate ordering even though an uncapped sum is mathematically order-independent: section 8 expressly signs deterministic date/id selection before the sentinel. Likewise, do not remove the named candidate-index requirement. This contract explicitly requires the approved index; the exception in the review request therefore applies. Payload point access may use any appropriate existing unique index. No exact total plan tree or particular payload-index name is contractual.
