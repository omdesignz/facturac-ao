## 2. Capability and authority

The sole new capability is `customers.create`; the sole new scope is **`customers:create`**. No wildcard, generic write/admin grant, scope implication or role inferred from a token is permitted. Create grants neither customer reads nor updates/deletes, catalogue/document/AGT/analytics access. Every prior read scope fails to authorize create. A credential can possess several explicitly granted scopes, each independently evaluated.

The chain is:

`verified machine identity → credential AND parent scope → immutable workspace/entity/environment binding → current original sponsor authority → customers.create authorization → idempotency → shared creation action → atomic result and audit`

A new sealed, non-serializable `IntegrationCommandContext` is distinct from `DocumentReadContext` and `IntegrationReadContext`. A narrow common credential verifier may be extracted from existing identity code, with unchanged read behavior and regression coverage. Never add write authority to a read context or permit caller-built arrays/DTOs to establish authority. Proposed class names are implementation guidance; the separation and checks are normative.

The command context comes exclusively from the existing hashed `fcr1` bearer credential, verified using the primary database and constant-time comparison. It captures stable integration identity, credential identity, original sponsor user/membership, explicit workspace/entity/environment, server request ID and optional validated client correlation ID. The route must match that binding. Browser cookies, `current_workspace_id`, Inertia context, session users and token-creator relationships supply no machine authority. Ignore cookies as credentials; reject attempted delegation/impersonation inputs. No agents, workflows or delegated actors are enabled.

Only **production** context is authorized: customer master data has no homologation partition. Deny non-production before a customer, price-list or command-ledger lookup. Path substitution cannot change a credential's environment. The existing backend credential creation/rotation validation must reject `customers:create` on homologation, including a mixed read/write grant. Test malformed/tampered database grants at execution too.

At the locked transaction boundary, revalidate: both enablement flags; live credential/hash version/expiry/revocation; live integration; exact binding; original sponsor and original membership links; active membership in that workspace; sponsor verified email, configured and confirmed MFA; current owner/administrator role; exact scope in both parent and credential grants. Removed membership followed by a new membership is not restoration of the original grant. Creator snapshots never substitute for a sponsor. Null/deleted sponsor denies. Clock expiry is checked again after lock waits and immediately before final persistence/replay release.

### Human approval and first-party convergence

An explicit standing human grant is sufficient for this minimal non-fiscal command; no per-customer approval ceremony is introduced. Grant issuance retains `IntegrationManagementContext`'s owner/administrator, verified/MFA, active work-session and recent password-confirmation requirements. Its existing required lifecycle audit records who granted the exact scope. Default scopes remain unchanged. Existing integrations receive no new grant automatically; rotation cannot widen authority. Because the existing backend has no general grant-widening operation, gaining create authority requires explicit creation of a new appropriately scoped integration through that backend. This phase tests that backend; it does not provision live credentials or add a provisioning surface.

Extract a shared `CustomerCommands::create` / creation action and typed input under the existing application structure. Both the existing UI store adapter and new machine adapter must call it. Share core validation, tenant-constrained default selection, explicit attribute mapping, persistence and required creation audit. Do not wrap `CustomerController::store` in bearer authentication or duplicate its business rules.

The UI adapter may select its workspace/entity using the established browser flow **once**, then construct a trusted human command context and revalidate that captured membership/role inside the transaction under user/membership share locks held through commit. Human commands do not acquire an integration lock or use machine scopes. It preserves current verified-session/workspace middleware, owner/administrator/accountant/billing roles, form fields, defaults, validation presentation and redirect behavior; it does not acquire machine grant requirements. Machine authority is intentionally narrower than those human roles. Existing impersonation restrictions remain; the new command context must not create a bypass. No UI redesign or new form nonce is required. The external idempotency protocol applies to the new machine command, not a fictitious retry guarantee retrofitted using a server-generated key on existing forms. UI creation must still be atomic with its required audit. Existing update/delete/import paths are not expanded in this slice.

## 3. External request and field minimization

The JSON root is one object, with only these three properties:

| Field                       | Treatment       | Exact meaning and normalization                                                                                                                                                                                                                                                                                                     |
| --------------------------- | --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `name`                      | Required string | The existing customer's name/display/business name, not a new legal-name or customer-type model. NFC normalize, strip only leading/trailing ASCII SP/HT/CR/LF, require 1–255 Unicode code points, reject remaining C0/C1 control characters. Preserve case and internal spaces. No case folding, transliteration or fuzzy matching. |
| `tax_identification_number` | Required string | Strip ASCII SP/HT/CR/LF at edges, ASCII uppercase; then existing rule `[A-Z0-9]{9,32}`. Preserve leading zeroes; no numeric coercion, punctuation removal or invented tax-authority verification.                                                                                                                                   |
| `country_code`              | Optional string | Omission becomes `AO`; strip the same edge whitespace, ASCII uppercase, exactly `[A-Z]{2}`. This preserves current domain validation; it is not a claim of ISO registry membership. Empty/null are invalid, not omission.                                                                                                           |

All submitted values must be strings. Arrays, numbers, booleans and null are rejected. Unknown properties, including unknown nested objects, are rejected even when null. No client-supplied internal/public ID, tenant, environment, active flag, customer type, separate legal name, external reference or revision.

Server values for external creation: generated ULID `public_id`, captured workspace/entity, `is_active=true`, `payment_terms_days=0`, `credit_limit_minor=null`, `auto_send_documents=false`, withholding type/rate null; address/email/phone null; timestamps from the server. Email/phone/address have **no normalization or write semantics in this API**, because they are forbidden. Neither a contact nor a delivery permission can be smuggled through an alias. No customer-specific prices are created.

Default price-list assignment remains the existing domain behavior: use the entity's default list, or null when none exists; do not silently switch external creation to a different pricing policy. No extra active filter is invented. Select at most two defaults, scoped by **both workspace and entity**, in one statement. If two exist or a selected list has inconsistent ownership, fail the external command generically with no write; reconcile the existing data through authorized first-party administration. The current schema does not enforce a single default, so silently selecting an arbitrary one is not acceptable for the new command. Do not add a price-list uniqueness migration or redesign `makeDefault` in this phase. A default change after this selection does not alter the recorded creation; the selected value belongs to the first successful execution, never to replay. A deletion race must either preserve referential integrity or roll back; it cannot attach a foreign list. The ordinary one/default-none UI behavior remains; keep its existing explicit-list validation and first-party field permissions. This new external ambiguity check is not a permission to rewrite existing customers or general pricing rules.

The pure command/schema validator and shared domain validation must be callable without an HTTP request. External normalization is a strict adapter contract; preserve existing UI normalization and accepted form surface. Shared action accepts only validated typed input and a trusted context, with explicit mapping rather than `$request->all()` or model fillable serialization.

### Business duplicates

The actual unique boundary is **`(legal_entity_id, tax_identification_number)`**, including inactive customers and regardless of country. Preserve it. The customer composite workspace/entity constraint also remains. A new key/integration does not bypass NIF uniqueness. There is no fuzzy name match, merge, upsert, resurrection or existing-customer lookup response. A duplicate yields generic `409 CUSTOMER_CONFLICT` with no existing public ID, activity state, name or other detail. This reveals only failure of an authorized create in its own context, not customer existence in another context. Same NIF in another entity is allowed under existing rules. Prevalidation is never the concurrency guarantee: the named database constraint decides races.

No optimistic revision is required for creating a new row. This is not approval to omit stale-write checks from future updates; their signed Phase 1 requirement remains and any update capability needs a separate design.

## 4. HTTP boundary and normative OpenAPI

The normative machine-readable specification is [openapi-external-customer-create-v1.json](openapi-external-customer-create-v1.json), together with the behavioral requirements in this contract. There is no embedded second copy to drift.

**`POST /api/integrations/commands/v1/workspaces/{workspacePublicId}/legal-entities/{entityPublicId}/environments/{environment}/customers`**

The new `/api/integrations/commands/v1/` family has its own command boundary/error renderer. It must not collide with the signed V1/V2 read middleware. Production is the only accepted environment. Accept either case for valid ULID path values, normalize them to lowercase, and bind them to the verified identity; do not place raw paths in fingerprints.

Both `integrations.enabled` (existing global switch) and new `integrations.commands_enabled` (`EXTERNAL_COMMAND_INTEGRATIONS_ENABLED`, default false) must be true. Both remain false in checked-in defaults. Enabling reads alone cannot enable commands. Disabled requests yield the same generic 404 before authentication/business work. No token is issued by the route.

Stateless bearer authentication only; no `web`/session guard, CSRF exception that enables browser fallback, cookies as authority, CORS enablement or method override. JSON body max **4096 bytes**, enforced on actual bounded input (read at most 4097) rather than trusting Content-Length. Only `application/json`, optionally `charset=utf-8`, with no content encoding/compression; reject multipart, form, file and compressed bodies. Empty/malformed/invalid-UTF8/non-object JSON is 400. Reject duplicate member names **after decoding escapes**, before lossy JSON-to-array conversion. Limit parser depth to 4 and reject non-string property values without recursively accepting arbitrary payloads. Normalizers such as global TrimStrings/ConvertEmptyStringsToNull must not mutate this route's input before strict parsing.

No query parameters, including empty or repeated unknown parameters. Unknown JSON fields fail 422 without reflecting their attacker-controlled names. Body size/media checks can precede authentication after the IP budget; authenticated scope/context checks precede domain or ledger access. Do not let automatic Laravel binding look up a customer or infer a tenant before authorization.

`Idempotency-Key` is required. Its HTTP field value, after standard outer HTTP optional-whitespace removal, must be **1–128 printable ASCII bytes (`0x20`–`0x7e`)**; case and all remaining bytes are significant. It is opaque, not a UUID parser, comma-separated list or structured quoted string. A UUID/random high-entropy key is recommended, not required. Reject detectable repeated header fields; never split a comma-containing value into several keys. Infrastructure must preserve a single field value rather than choosing an arbitrary duplicate. Whitespace-only, non-ASCII and over-length values fail 422. Header names are case insensitive; key contents are not. This is the Phase 1 printable-ASCII protocol, not a new restrictive identifier alphabet.

Missing/invalid key fails before a ledger record. Optional `X-Client-Request-ID` follows existing `[A-Za-z0-9._-]{1,64}` rules. It has no authority or idempotency effect. Every response gets a fresh server UUID `X-Request-ID`; never trust a caller's server-ID header. All responses are JSON except empty HEAD bodies, use `Cache-Control: no-store, private` (directive order not significant), `Vary: Authorization`, no cookies/redirects and no debug exception content.

GET/HEAD/PUT/PATCH/DELETE/OPTIONS are not command operations. On the recognized enabled resource path, run the same IP/authenticated quotas and identity/scope/context denial ordering before **405 with `Allow: POST`**; HEAD suppresses the body. They never reserve keys, inspect customer existence or execute creation. No read-resource GET alias, automatic successful OPTIONS or browser form override. Unknown paths are generic 404. Parsing errors/unsupported methods must not bypass command-family redaction or become tenant oracles.

### Response and errors

First execution and authorized replay both return **201**, with exactly:

```json
{
    "data": { "public_id": "01arz3ndektsv4rrffq69g5fav" },
    "meta": { "operation_id": "f98ee06e-70bf-4b2e-a6e4-5437db577c25" }
}
```

The body is generated once, stored as canonical UTF-8 JSON and replayed byte-for-byte. Public ID is the created customer's lowercase ULID, operation ID is a stable random UUID. No name/NIF/contact/internal ID/current customer representation or Location header. `Idempotency-Replayed: false` on first success and `true` on replay; fresh transport request ID stays in the header, outside the immutable body. HTTP Date and transport headers need not be identical. This historical acknowledgement is deliberately smaller than a customer read and does not grant read authority. Later rename, deactivation or deletion does not alter the stored acknowledgement or recreate a customer.

Errors have exactly `{"error":{"code":"…","message":"Não foi possível concluir o pedido."},"meta":{"request_id":"<server UUID>"}}`. No field-value echo, exception text or extra validation bag; the client knows the bounded schema. The constant message applies to every code.

| HTTP | Codes and semantics                                                                                                                                                                                                     |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 400  | `INVALID_REQUEST`: malformed/root/duplicate-member JSON or ambiguous transport.                                                                                                                                         |
| 401  | `UNAUTHENTICATED`: missing/invalid/expired/revoked credential or revoked integration; no credential existence detail.                                                                                                   |
| 403  | `FORBIDDEN`: sponsor, scope, binding, production-context or delegation failure; same envelope for existent/nonexistent foreign context.                                                                                 |
| 404  | `NOT_FOUND`: disabled family or unknown route.                                                                                                                                                                          |
| 405  | `METHOD_NOT_ALLOWED`, `Allow: POST`; HEAD body empty.                                                                                                                                                                   |
| 409  | `IDEMPOTENCY_CONFLICT` for a completed key with another fingerprint; `COMMAND_IN_PROGRESS` with `Retry-After: 1` for bounded integration/claim contention; `CUSTOMER_CONFLICT` for the named NIF uniqueness constraint. |
| 413  | `PAYLOAD_TOO_LARGE`.                                                                                                                                                                                                    |
| 415  | `UNSUPPORTED_MEDIA_TYPE`: unsupported content type/encoding.                                                                                                                                                            |
| 422  | `VALIDATION_FAILED`: invalid key, schema/fields/lengths/query/correlation/path syntax.                                                                                                                                  |
| 429  | `RATE_LIMITED`, `Retry-After` seconds to the fixed-minute boundary, 1–60.                                                                                                                                               |
| 503  | `SERVICE_UNAVAILABLE`: other database/audit/cache/default-ambiguity/capacity/timeout/integrity/unsupported-driver/uncertain-commit failure. No partial success body.                                                    |

Errors do not include operation IDs from another payload/key, counts, capacity, SQL, plans, raw request material or existing resource IDs. On any 503/connection loss, retry the **same key and payload** after backoff; do not claim that a possibly committed operation failed and tell the client to use a new key. A known precommit rollback leaves no completed result, but the wire error remains conservative.

## 5. Idempotency protocol and state machine

The stable principal is the **integration**, not a rotating credential or sponsor. Namespace:

`integration_id + workspace_id + legal_entity_id + environment + command(customers.create) + capability_version(1) + SHA256(key bytes)`

The version belongs to command semantics, not raw URI spelling. No cross-integration/tenant/entity/environment/capability reuse. Authentication and pure validation precede fingerprinting; fresh locked authorization precedes ledger observation. Credential ID is origin attribution, not part of uniqueness. Rotation to an active create-scoped credential on the same integration can replay; reducing its scope, revoking either applicable credential/parent, expiring it or losing sponsor authority denies replay. Replaying is release of a past result under current authority, not re-execution or reversal of that result.

### Canonical command `command-json-v1`

Build this typed object from validated, normalized input and verified context; SHA-256 its canonical bytes:

```json
{
    "canonicalizer": "command-json-v1",
    "command": "customers.create",
    "version": 1,
    "principal": {
        "kind": "integration",
        "public_id": "<lowercase integration ULID>"
    },
    "context": {
        "workspace_public_id": "<normalized workspace public ID>",
        "legal_entity_public_id": "<normalized entity public ID>",
        "environment": "production"
    },
    "input": {
        "name": "<NFC normalized name>",
        "tax_identification_number": "<normalized NIF>",
        "country_code": "AO"
    },
    "defaults": "customer-create-v1"
}
```

Object keys sort lexicographically by UTF-8 bytes; no insignificant whitespace; UTF-8 strings use deterministic JSON escaping with unescaped Unicode/slashes; integers are base-10 without floating conversion; booleans/null have literal encodings; arrays would retain order but are not accepted in this command. Pin golden byte/hash vectors. Include all accepted consequential input, context, principal, version and defaults-policy version. Exclude bearer/key/request IDs/header ordering/raw URI and volatile database values. Omitted country and explicit normalized AO are equivalent; reordered JSON keys, equivalent string escapes, edge whitespace and NIF/country casing normalize identically. Name case/internal whitespace and a different country/name/NIF remain consequential. Absent/null are not collapsed beyond the explicit country default (null is invalid). Do not hash raw JSON.

The default policy version means “resolve the existing entity default during the first successful execution.” A changed default does not change the fingerprint or re-run defaults on a completed replay. Fixed field defaults are part of that named frozen policy. Changing them later requires a new command/default version and Astra review. Preserve supported old canonicalizers for replay; an unknown/corrupt recorded version fails closed, never executes again.

Reuse the proven deterministic encoding primitive only behind a separately versioned command wrapper; do not modify AGT signing/canonical bytes. NFC can use the already installed `Normalizer` / Symfony polyfill; no new package. Idempotency hashes are internal integrity material, not authorization, customer deduplication or safe logging substitutes for PII.

| State observed after current authorization | Behavior                                                                                                                                                        |
| ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Absent                                     | Transactionally reserve, create, audit and commit completed result once.                                                                                        |
| Other transaction executing                | Wait within lock bound, then replay/conflict if it commits; otherwise 409 in-progress with retry hint. If it rolls back, the next authorized attempt may claim. |
| Completed, same canonical hash/version     | Replay stored 201/body only after required replay audit; no domain/default/duplicate query or business mutation.                                                |
| Completed, different hash                  | 409 idempotency conflict; no original body/resource identifier.                                                                                                 |
| This transaction aborts before commit      | Reservation/customer/result/success audit/counter increment all roll back. A later authorized same-key attempt can execute.                                     |
| Commit succeeds but response is lost       | Durable completed record determines replay. Never reset/expire/reclaim it.                                                                                      |
| Commit outcome unknown                     | Generic 503 or connection loss; no automatic second mutation. Retry performs authoritative lookup.                                                              |

An uncommitted reservation never becomes a durable abandoned lease. `executing` is transaction-local; the only committed ledger state is `succeeded`. No polling endpoint, asynchronous worker, lease-stealing logic, “failed → execute again” durable state or background recovery job is introduced. Killing the process before commit relies on PostgreSQL rollback; after commit the result survives. A changed payload may claim a key whose earlier attempt truly rolled back and never became durable, but after success that key is permanently bound. Clients should use a new key for changed intent.

## 6. Transaction, locking and crash semantics

Machine command execution requires an **outermost primary PostgreSQL transaction** at READ COMMITTED; reject ambient/nested execution rather than returning a result before an enclosing commit. SQLite is permitted only for fast tests; MySQL is not certified for this new external command. Existing local/UI database configuration is not changed. No network call, AGT job, email, outbox effect or external callback is part of this command.

Use explicit bounded locking, database uniqueness and one transaction, not a cache mutex or application check-then-insert. The approved conservative choice is **serialization per integration**, acceptable for this phase's 10/minute command budget. This also avoids credential last-used lock-upgrade deadlocks. It is not a global tenant lock and does not make a read request take command locks. Future throughput changes require review.

1. Outside the business transaction: flags, size/media and IP admission, credential verification, integration/workspace quotas, preliminary current scope/context/sponsor checks, strict method/query/body/key validation and canonicalization. Persist required `external.command.attempted` with a fresh request-attempt UUID. No key/payload in that audit. No ledger row for malformed, unauthenticated or unauthorized requests.
2. Start READ COMMITTED transaction on the primary; `SET LOCAL lock_timeout='1s'`, `statement_timeout='2s'`, `transaction_timeout='5s'` on certified PostgreSQL 18. No automatic transaction retry. Transaction timeout may terminate the connection: discard/reconnect safely, do not mistake it for a successful commit. Also enforce a bounded application execution deadline; no sleeping, long CPU work or two-phase prepared transactions.
3. Based on initially verified identity, acquire sponsor user **FOR SHARE**, original membership **FOR SHARE**, integration **FOR UPDATE**, credential **FOR UPDATE**, exact parent/credential scope rows **FOR SHARE**, then workspace/entity references with key-share protection. Explicit separate primary-key queries avoid nullable outer-join locking. Lock multiple IDs in ascending order if needed. Revalidate the whole identity/binding/sponsor/scope tuple from these locked rows, including no stale user/MFA/role models. No lookup by a caller's foreign tenant ID. A missing/mismatched row denies; no reattachment to a replacement membership.
4. Look up/claim the exact ledger namespace using its unique index. Reserve with a conflict-safe database insert, not an existence check assumed to be exclusive. If a competing insert wins, READ COMMITTED subsequent lookup must observe its committed result. Completed record comparison/replay occurs before live NIF/default validation. Lock waits are bounded; integration serialization may return `COMMAND_IN_PROGRESS` even for another command/key on the same integration. That response asserts **contention**, not existence of this key or another customer's record. Other lock/deadlock failures are generic 503 and roll back.
5. Record `external.command.authorized` inside the transaction. For a new operation, execute shared creation with explicit mapped values, the exact scoped domain constraints and default selection. A concurrent NIF insert under another integration is decided by the existing unique constraint. Do not catch a failed PostgreSQL statement and continue the aborted transaction; roll back, classify only the named constraint and write a safe failure audit separately.
6. Require creation audit persistence on this same connection/transaction. Serialize and validate the minimal result **before commit**, finalize the immutable ledger, let the success-transition database trigger increment the bounded capacity counter atomically, and update credential last-used metadata monotonically. For replay, require its separate audit and last-used update, with no creation/counter increment. Recheck expiry using PostgreSQL `clock_timestamp()` after waits and before completion, not transaction-start `CURRENT_TIMESTAMP` or a frozen application clock. Commit before releasing any success bytes.
7. On known rollback, write safe failed/denied/conflict audit outside the aborted transaction. If that audit fails, return generic 503; never turn logging failure into success. On uncertain commit outcome, label failure `outcome_unknown`, not “rolled back”; retry uses the durable ledger. There is no guaranteed post-crash failure audit after SIGKILL: an attempted event with no successful operation is an actionable incomplete attempt, not evidence of successful mutation.

Required audit and customer/ledger must use the same database connection; reject buffering/disabled/unsaved/cancelled/throwing audit and connection mismatches. The command connection must also bound preliminary identity and attempted/failure-audit statements to 2 seconds and restore connection settings afterward; cache admission retains its own existing bounded lock protocol. No after-commit required audit and no out-of-transaction last-used write that can turn a committed success into an unclassified exception.

Revocation/role/MFA withdrawal updates conflict with the locked rows. If withdrawal commits before command authorization acquires and validates its locks, the command/replay denies. If a valid command acquires locks first, it may commit and withdrawal follows; it does not retroactively cancel the customer. This is the linearization contract. Expiry is checked at the final authorization point; there is no impossible promise about the wall clock during the last commit instruction. Withdrawal paths must be tested against the actual existing lifecycle/account/membership/MFA writers. Unexpected deadlocks abort safely within bounds; no silent retry with stale context. Do not weaken their locks or alter unrelated lifecycle semantics to make a race pass.

PostgreSQL row-lock conflict behavior and transaction-scoped release support this protocol; [official locking documentation](https://www.postgresql.org/docs/18/explicit-locking.html). Conflict handling and a subsequent READ COMMITTED statement are intentionally separate; [INSERT](https://www.postgresql.org/docs/18/sql-insert.html) and [transaction isolation](https://www.postgresql.org/docs/18/transaction-iso.html). Timeout scope and session termination must be handled as documented in [client connection defaults](https://www.postgresql.org/docs/18/runtime-config-client.html).

Unique constraint on **`(integration_id,workspace_id,legal_entity_id,environment,command,capability_version,key_hash)`**; unique operation UUID; ordinary index for integration/created-at operational reconciliation. The namespace index is the replay lookup, not a scan. Existing composite entity/workspace and credential/integration indexes are reused. Insert checks must enforce actual binding even if an application caller is defective. No public list/search of these rows.

Guard changes to namespace, fingerprint, origin, snapshots, completed result/body/status and timestamps. Forbid deletes and completed-row mutation, apart from the live sponsor FK becoming null through deletion. Reject attempted reattachment or changing one non-null sponsor to another. PostgreSQL deferred constraint trigger must verify the **current row at transaction end** is succeeded; it must not inspect stale `NEW.state` captured by the earlier insert. This prohibits committing an abandoned executing row. See [constraint-trigger timing](https://www.postgresql.org/docs/18/sql-createtrigger.html). SQLite can exercise application rollback/immutability, but cannot substitute for PostgreSQL deferred-commit enforcement. Tests must explicitly label that limitation.

### `external_command_capacity`

One row per integration, PK/FK RESTRICT; `completed_count` nonnegative integer capped at **100000**. Lazily created at zero under the integration lock. A database trigger on the executing→succeeded transition increments it exactly once, in that same transaction, with a conditional update below the cap; failure aborts completion. The application must not separately increment it. Read its single row before new creation to reject a full integration early; the trigger remains the final admission guarantee. Never decrement/reset on revocation, rotation, customer deletion or replay. The ledger is authoritative; the transition trigger prevents a successful operation from omitting its increment. Offline reconciliation of any legacy/manual counter mismatch must fail closed and never erase history or reset the counter to reopen admission. Application tests and PostgreSQL rollback/concurrency tests must prove exact count correspondence. Counter guard forbids decrement/delete; insert is zero and updates are +1 only. No per-request full-ledger count. This small admission counter bounds durable records without an unsafe key expiry; it is not business analytics.

At capacity, existing authorized replays still work; new commands fail generic 503 before creation. Capacity is internal, not a response header/count/error subtype. Raising it or adding deletion/compaction requires Astra/operational review. Many new integrations cannot be created through this endpoint; live provisioning remains a separate human-controlled gate. Global storage/attempt-audit monitoring remains operational, not a claim of infinite retention at zero cost.

### Retention, deployment and rollback

Keep the small successful record and response indefinitely in this bounded phase, including revoked integrations. This is a conservative application safety rule, not a legal retention opinion. Do not expire keys or delete completed rows and allow their reuse. Any later response compaction must retain an immutable non-reexecuting tombstone and get a separate response/retention contract; it is not implemented now. The 100000 admission bound avoids promising unlimited ledger growth. No PII request payload is retained beyond the authoritative customer row.

Migrations must use the established database-specific guard pattern, preserve all original checks and add only the scope value. Apply to disposable SQLite/PostgreSQL first; inspect generated schema and raw-SQL bypass attempts. Existing MySQL local compatibility may use equivalent additive DDL, but the command remains rejected there; do not claim its concurrency is certified. If the existing migration helper cannot safely support this additive schema, stop for review, not remove constraints.

Before eventual deployment: backup/restore rehearsal, pause integration/command writers while installing checks, inspect existing scope validity, bounded DDL lock/statement timeouts, verify grants remain unchanged and both flags disabled. New tables start empty; do not invent historical command records from old customers. Rollback refuses when any new scope grant (including on revoked credentials), operation/capacity evidence or command audit exists; never delete evidence to make down() succeed. Empty migration rollback/reapply must pass. Deployment is not authorized by this design.

## 9. Quotas, bounds and method abuse

Reuse the existing database-backed atomic fixed-minute limiter with **distinct command-prefixed identities**, without changing read budgets or native-clock semantics:

- source IP: **60/minute**, before authentication/size parsing;
- verified stable integration: **10/minute**, across credentials, paths, replay/conflict/validation and supported/unsupported methods;
- verified bound workspace: **30/minute**, across its command integrations.

No independent credential allowance that rotation resets. Consume both verified buckets before sponsor/scope denial; use identity-derived workspace, not a foreign path. Replays and conflicts consume the same budget as first execution. Malformed unauthenticated/oversized/media failures consume IP budget only; structurally invalid requests that reach verified identity consume all applicable budgets. Flags-disabled requests perform no business/quota-store work. Limiter failure fails closed 503. A fixed-minute boundary permits its documented adjacent-window burst; tests must use native-clock boundaries rather than frozen Carbon assumptions.

URI encoding, query/body ordering, key variations, HEAD/GET/OPTIONS and bearer rotation do not create new quota identities. V1/V2 reads remain on read quotas; read paths cannot invoke this command, so using a read budget cannot bypass the write budget. 409 in-progress does not reserve a second durable row. Failed/denied attempts never accumulate ledger records; successful rows are capped as above. Bound input, constant-indexed lookups, per-integration serialization and database timeouts are additional protections, not substitutes for quota admission. No scan/list of customers or ledger is needed to create/replay.
